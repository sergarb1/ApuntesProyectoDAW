## 📬 La idea en una frase

> No necesitas siempre una base de datos relacional: lo que guardas decide la
> herramienta. Datos con relaciones → SQL; documentos flexibles → NoSQL;
> archivos → sistema de archivos; datos temporales → en memoria. Y en tu
> proyecto DAW, lo normal es SQL.

Es como un cajón de herramientas: no arreglas una silla con un martillo solo
porque sea la herramienta más famosa. Cada tarea tiene su herramienta. Los
datos son igual: según lo que guardes, usarás una cosa u otra. La habilidad no
es conocer todas las marcas: es saber cuál toca en cada caso.

## 🧰 Cuatro opciones según lo que guardas

| Qué guardas | Herramienta |
|---|---|
| Datos estructurados con relaciones (usuarios ↔ pedidos) | **SQL** |
| Documentos flexibles (catálogos, configuraciones) | **NoSQL** |
| Archivos (imágenes, PDFs) | **Sistema de archivos** o cloud storage |
| Datos temporales (sesiones, caché) | **En memoria** (Redis, etc.) |

¿Ves el patrón? No hay una herramienta "mejor": hay una herramienta **para
cada tipo de dato**. Las imágenes no necesitan una base de datos relacional:
viven en una carpeta. Una sesión que expira en 20 minutos no necesita ser
guardada para siempre: se queda en memoria. Solo los datos que se relacionan
entre sí (un usuario con sus pedidos) piden SQL.

<Aclaracion pregunta="¿Necesito siempre una base de datos relacional?">
  No. Depende de lo que guardes:

  - **Datos estructurados con relaciones** (usuarios ↔ pedidos) → SQL
  - **Documentos flexibles** (catálogos, configuraciones) → NoSQL
  - **Archivos** (imágenes, PDFs) → Sistema de archivos o cloud storage
  - **Datos temporales** (sesiones, caché) → En memoria (Redis, etc.)

  Para un proyecto DAW, lo normal es SQL (MySQL, PostgreSQL, SQLite).
  Es lo que se enseña, lo más documentado, y suficiente para el 90% de los
  casos.
</Aclaracion>

## 💬 Qué es SQL y qué es NoSQL

**SQL** son las siglas de **Structured Query Language** (Lenguaje de Consulta
Estructurada): es el idioma que usan las bases de datos relacionales, esas
que trabajan con tablas conectadas por claves (lo que has diseñado en los
puntos 04 y 05). Su superpoder es la **coherencia**: las reglas (email único,
precio positivo) se cumplen siempre, pase lo que pase.

**NoSQL** (Not Only SQL, "no solo SQL") es una familia de almacenes que
renuncian a la rigidez de las tablas a cambio de **flexibilidad**: documentos
que pueden tener campos distintos entre sí, sin un esquema fijo. Útil para
catálogos, configuraciones o prototipos donde cada "elemento" es distinto.

| | SQL (relacional) | NoSQL |
|---|---|---|
| Forma | Tablas con filas y columnas fijas | Documentos flexibles |
| Superpoder | Coherencia y relaciones | Flexibilidad y velocidad en datos sueltos |
| Reglas estrictas | Sí, siempre | Más laxas |
| Momento ideal | Usuarios, pedidos, recetas... datos conectados | Catálogos, configuraciones, prototipos |

## 🏆 ¿Cuál elijo para mi proyecto DAW?

Para un proyecto de clase, la respuesta suele estar entre tres candidatos de
la familia SQL:

| Motor | Ideal para | Nota |
|---|---|---|
| **SQLite** | Prototipos y proyectos pequeños | Un solo archivo, cero configuración, perfecto para empezar |
| **MySQL** | Proyectos web "de verdad" | El clásico de los institutos y de la mayoría de las webs |
| **PostgreSQL** | Proyectos que crecerán o necesitan potencia | El más completo de los tres, también el que más pide configurar |

Regla de oro: si no tienes una razón fuerte, **elige SQL** (MySQL o SQLite)
porque es lo que se enseña, lo más documentado, y suficiente para el 90% de
los casos. No dejes que el "shiny" de NoSQL te distraiga de tu objetivo: que
tu MVP funcione y esté documentado. Elegir NoSQL "porque es moderno" sin que
tus datos lo pidan es elegir el martillo porque brilla.

## 🧠 Mini-chequeo

**Pregunta 1.** Tus datos son "usuarios con sus recetas y comentarios",
todos conectados entre sí. ¿Qué herramienta es la adecuada?
A) NoSQL · B) SQL · C) En memoria.

**Pregunta 2.** Una imagen de portada de una receta se guarda mejor en:
A) el sistema de archivos · B) una tabla SQL con relaciones · C) en memoria.

**Pregunta 3.** Para un proyecto DAW sin razones especiales, lo normal es:
A) SQL (MySQL, PostgreSQL, SQLite) · B) NoSQL siempre · C) un archivo de texto.

<details>
<summary>...Respuestas...</summary>

1. **B**. Datos estructurados con relaciones piden SQL: tablas conectadas por
   claves y reglas estrictas.
2. **A**. Los archivos (imágenes, PDFs) viven en el sistema de archivos o en
   cloud storage; en la base de datos guardas la referencia (la URL).
3. **A**. Para DAW, SQL es lo que se enseña, lo más documentado y suficiente
   para el 90% de los casos.
</details>

## ✅ Resumen en 3 frases

1. Lo que guardas decide la herramienta: SQL para datos relacionados, NoSQL
   para documentos flexibles, archivos para imágenes y PDFs, memoria para
   datos temporales.
2. SQL da coherencia (las reglas se cumplen siempre); NoSQL da flexibilidad
   (documentos sin esquema fijo).
3. Para tu proyecto DAW, elige SQL (MySQL, PostgreSQL o SQLite) salvo que tus
   datos pidan otra cosa: es lo enseñado, lo documentado y suficiente.

> 🐛 **Vocabulario rápido**

| Término | Idea general |
|---|---|
| **SQL** | Structured Query Language: idioma de las bases de datos relacionales (tablas y claves) |
| **NoSQL** | Familia de almacenes flexibles sin esquema fijo ("no solo SQL") |
| **Sistema de archivos** | Carpetas y archivos normales: el sitio de imágenes y PDFs |
| **En memoria** | Datos temporales que no necesitan sobrevivir al apagado (sesiones, caché) |
| **Base de datos relacional** | Almacén de tablas conectadas por claves foráneas |
| **MVP** | Producto Mínimo Viable: lo que tu proyecto necesita para funcionar |
