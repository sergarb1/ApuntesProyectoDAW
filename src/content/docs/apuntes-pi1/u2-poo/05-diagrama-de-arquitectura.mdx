## 📬 La idea en una frase

> No necesitas un documento de 50 páginas: con un diagrama de cajas y flechas
> basta para dejar claro cómo se conecta tu aplicación.

Es el plano de la casa que vimos en el punto 01: en una sola hoja se ve cuántas
habitaciones hay y por qué pasillos se llega de una a otra. Tu diagrama de
arquitectura es esa hoja para tu proyecto.

## 📦 Qué es un diagrama de arquitectura

Un diagrama de arquitectura dibuja las **piezas grandes** de tu aplicación y
**cómo se conectan**:

- Las **cajas** son las piezas grandes: el navegador del usuario, el servidor
  donde vive tu web, la base de datos donde se guarda la información, los
  servicios externos.
- Las **flechas** son la comunicación: qué pieza le pide algo a qué pieza.

No es un diagrama de detalle: es un plano a vista de pájaro. No dibujas cada
pantalla ni cada función, solo las grandes estancias y sus puertas. La regla:
si una pieza no cambia la forma en que se conecta tu app, no está en este
diagrama.

## 🧰 Herramientas para dibujarlo

Tienes tres opciones, todas válidas:

| Herramienta | Qué es | Cuándo usarla |
|---|---|---|
| **Draw.io** | Editor de diagramas online y gratis | Para entregar una versión limpia y compartirla |
| **Mermaid** | Diagramas escritos como texto (se usan en Markdown) | Para tener el diagrama versionado junto a tu documentación |
| **Lápiz y papel** | El método de siempre | Para bocetar en las primeras reuniones de equipo |

Ninguna es obligatoria. El objetivo es que el diagrama exista y se entienda;
la herramienta es lo de menos (verás la aclaración al final).

## 🔭 Leyendo un diagrama de arquitectura

Este es el diagrama de arquitectura típico de una aplicación web:

```
[Navegador] → [Servidor web] → [API] → [Base de datos]
                                  ↓
                          [Servicio de correo] (para emails)
```

Vamos a leerlo en voz alta:

- **Navegador**: lo que el usuario abre (Chrome, Firefox...). Es la interfaz de
  usuario de la que hablábamos en el punto 03.
- **Servidor web**: el ordenador remoto donde vive tu aplicación, el que
  responde cuando alguien pide una página.
- **API**: siglas de *Application Programming Interface* (Interfaz de
  Programación de Aplicaciones). En palabras llanas: **la puerta acordada** por
  la que las piezas se piden cosas entre sí, en un formato que ambas entienden.
  Aquí es donde vive la lógica de negocio.
- **Base de datos**: donde se guarda la información de forma permanente (los
  usuarios, las recetas, los pedidos).
- **Servicio de correo**: un servicio externo que manda emails (por ejemplo,
  el correo de confirmación del registro). Por eso cuelga de la API con una
  flecha hacia abajo: es un extra, no la carretera principal.

Las flechas dicen quién llama a quién: el navegador pide al servidor, el
servidor pide a la API, la API lee y escribe en la base de datos. Esa dirección
importa: dibujarla al revés es dibujar otra historia.

<Aclaracion pregunta="¿Tengo que dibujarlo con una herramienta profesional?">
  No. Un lápiz y un folio valen exactamente igual si el diagrama se entiende.
  Lo importante es que las cajas tengan nombre, las flechas indiquen quién le
  pide a quién, y que tu equipo y tu profesor lo lean sin que les expliques
  nada.

  Empieza en papel, acuérdate de dibujarlo, y si necesitas entregarlo bien
  presentado ya pasarás a Draw.io o Mermaid. El peor diagrama es el que no
  existe.
</Aclaracion>

## ⚠️ Errores comunes al dibujarlo

| Error | Por qué es un problema |
|---|---|
| Demasiadas cajas | El plano deja de ser de vista de pájaro: nadie lo entiende |
| Flechas sin dirección | No se sabe quién le pide a quién |
| Olvidar al usuario | El navegador no aparece y el diagrama no cuenta la historia entera |
| Confundir arquitectura y detalle | Dibujar cada pantalla en vez de las piezas grandes |
| No actualizarlo | El diagrama dice otra cosa distinta del proyecto real |

El diagrama no es un adorno: es tu herramienta de comunicación con el equipo
(punto 08) y de decisión con criterio (punto 07). Si está desactualizado,
miente; si miente, no sirve.

## 🧠 Mini-chequeo

**Pregunta 1.** En un diagrama de arquitectura, las flechas indican:
A) qué pieza le pide algo a qué pieza · B) la velocidad de la web · C) el orden
de creación de los archivos.

**Pregunta 2.** La API (Interfaz de Programación de Aplicaciones) es:
A) un antivirus · B) la puerta acordada por la que las piezas se piden cosas ·
C) la base de datos.

<details>
<summary>...Respuestas...</summary>

1. **A**. Las flechas dibujan la comunicación: quién llama a quién. Las otras
   opciones no tienen que ver con el diagrama de arquitectura.
2. **B**. La API es el formato acordado para pedir cosas entre piezas. No es
   antivirus ni base de datos, aunque hable con ella.
</details>

## ✅ Resumen en 3 frases

1. El diagrama de arquitectura dibuja con cajas y flechas cómo se conectan las
   piezas grandes de tu aplicación.
2. Se dibuja con Draw.io, Mermaid o lápiz y papel; la herramienta importa menos
   que el diagrama exista y se entienda.
3. Un ejemplo típico: `[Navegador] → [Servidor web] → [API] → [Base de datos]`,
   con las flechas indicando quién le pide a quién.
