> 🗺️ **Estás en:** 📓 **U6 · Implementar la lógica** → 09 · Cierre

> En este punto no aprendemos nada nuevo: lo convertimos todo en práctica. Y,
> como siempre, algo no va a funcionar. 😈

A lo largo de esta unidad has aprendido a priorizar por valor (no por
dificultad), crear un esqueleto incremental que crece por capas, organizar
el código en una estructura de carpetas clara, comentar el porqué, refactorizar
desde el principio, manejar atascos con estrategias concretas, identificar
lo crítico (auth, datos) y usar una checklist antes de cerrar cada tarea.
Ahora toca demostrar que no solo lo has leído: toca **usarlo**.

## ⭐ Sé el Proyecto

Ponte en la piel de la funcionalidad "registro de usuarios" de tu proyecto.
El equipo tiene que decidir cómo implementarla. ¿Qué enfoque eliges?

- **Opción A — "El monolito perfecto"**: "Escribo el registro completo en
  un solo archivo de 500 líneas: validación, hash, BD, email, JWT, todo
  junto. Así controlo todo y no hay errores de comunicación entre partes."
- **Opción B — "El esqueleto incremental"**: "Iteración 1: endpoint POST
  /api/users que devuelve 201 con datos mock. Iteración 2: conectar BD real.
  Iteración 3: validación y hash. Iteración 4: JWT. Iteración 5: email.
  Cada iteración se prueba y se commitea."
- **Opción C — "Lo difícil primero"**: "Empiezo por el algoritmo de
  recomendación personalizada con machine learning. El registro lo hago
  al final, que es fácil."

<details>
<summary>...Respuestas...</summary>

**La opción B.** Es la única que entrega valor desde la primera iteración,
permite detectar errores pronto y no apuesta todo a una carta. La A crea
deuda técnica inmediata; la C es el error del estudiante que programó lo
difícil primero y suspendió. Tu funcionalidad quiere ser la B.

</details>

<summary>...Respuestas...</summary>

**Pablo tiene el proceso ganado, y Laura tiene un punto válido al final.**
Refactorizar *mientras* programas (extraer una función duplicada, renombrar
una variable confusa) cuesta segundos y ahorra horas. Pero Laura no está
equivocada: no refactorices *por refactorizar*. Refactoriza cuando el
código te dice "aquí hay duplicación" o "esta función hace tres cosas".
El equilibrio: haz que funcione *bien* (tests pasan, sin duplicación
evidente), no "funciona y ya limpiaré luego".

</details>

## ⚡ Laboratorio de Tortura

**Duración estimada: 30-40 minutos.** Objetivo: detectar el fallo de una
implementación que *parece* correcta... y no lo es.

**Contexto.** Te pasan este código de un endpoint de registro para que lo
revises antes de mergear:

```javascript
// POST /api/users
async function registrar(req, res) {
  const { email, password } = req.body;
  
  // Validación
  if (!email || !password) {
    return res.status(400).json({ error: "Faltan datos" });
  }
  
  // Comprobar si existe
  const existe = await db.query("SELECT * FROM users WHERE email = ?", [email]);
  if (existe.length > 0) {
    return res.status(409).json({ error: "Email ya registrado" });
  }
  
  // Guardar
  const hash = await bcrypt.hash(password, 10);
  await db.query("INSERT INTO users (email, password_hash) VALUES (?, ?)", [email, hash]);
  
  // Respuesta
  res.status(201).json({ message: "Usuario creado" });
}
```

**Instrucciones.** Detecta **mínimo 4 fallos** (seguridad, validación,
manejo de errores, buenas prácticas) y propón la corrección. Después,
descubre el **fallo intencionado**.

<details>
<summary>Pista 1</summary>

Revisa el punto 04 (comentarios): ¿qué explica este código y qué *no*
explica? ¿Hay algún "porqué" importante ausente?

</details>

<details>
<summary>Pista 2</summary>

Revisa el punto 07 (priorizar lo crítico): ¿qué pasa si `bcrypt.hash`
falla? ¿Y si la BD está caída? ¿El try/catch está presente?

</details>

<details>
<summary>Pista 3 (casi la respuesta)</summary>

El fallo intencionado es que **no hay try/catch alrededor de las operaciones
asíncronas (bcrypt, BD): si la base de datos falla o bcrypt lanza excepción,
el servidor crashea y devuelve 500 genérico sin log útil**. Además, la
validación de email es inexistente (formato), y la respuesta de éxito no
devuelve el ID del usuario creado (necesario para el frontend).

</details>

<details>
<summary>...Solución completa...</summary>

**Corrección modelo.**
```javascript
async function registrar(req, res) {
  try {
    const { email, password } = req.body;
    
    // Validación robusta
    if (!email || !password) {
      return res.status(400).json({ error: "Email y contraseña son obligatorios" });
    }
    if (!/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(email)) {
      return res.status(400).json({ error: "Formato de email inválido" });
    }
    if (password.length < 8) {
      return res.status(400).json({ error: "La contraseña debe tener al menos 8 caracteres" });
    }
    
    // Comprobar existencia
    const existe = await db.query("SELECT id FROM users WHERE email = ?", [email]);
    if (existe.length > 0) {
      return res.status(409).json({ error: "Email ya registrado" });
    }
    
    // Hash y guardado
    const hash = await bcrypt.hash(password, 10);
    const result = await db.query("INSERT INTO users (email, password_hash) VALUES (?, ?)", [email, hash]);
    
    // Respuesta con ID
    res.status(201).json({ id: result.insertId, email, message: "Usuario creado" });
    
  } catch (err) {
    console.error("Error en registro:", err);
    res.status(500).json({ error: "Error interno del servidor" });
  }
}
```

El fallo intencionado era la ausencia de manejo de errores: código que
funciona en el "camino feliz" pero crashea en producción. Si no lo cazas,
tu usuario lo hace por ti. 😉

</details>

## 🧠 Atrévete a Pensar

Preguntas abiertas. Piensa primero, mira la solución después.

1. "Refactorizar desde el principio" suena bien, pero ¿cómo evitas caer en
   la parálisis por análisis (refactorizar infinitamente sin avanzar)?
2. El punto 07 dice "auth y datos primero". ¿Qué haces si el cliente
   (frontend) necesita un endpoint que *aún* no has implementado para
   seguir trabajando?
3. ¿Cuándo un comentario explicando el "porqué" es realmente útil y cuándo
   es ruido? Pon un ejemplo de cada caso.
4. Si tuvieras que explicar esta unidad entera en un tuit (280 caracteres),
   ¿qué dirías?

<details>
<summary>...Sugerencias de respuesta...</summary>

1. Regla práctica: refactoriza **solo** cuando ves duplicación real (misma
   lógica en 2+ sitios) o una función hace >1 cosa. No refactorices "por
   si acaso" o por estética. Tiempo límite: 5 min por refactor.
2. Define el **contrato de la API** (punto 03 de U3) *antes* de separaros.
   El frontend usa datos mock mientras el backend implementa. Contrato =
   documentación viva, no excusa para esperar.
3. Útil: "// Usamos bcrypt(10) porque OWASP recomienda cost ≥10 para 2024".
   Ruido: "// Creamos la variable usuario". Si el código se lee solo, no
   comentes el qué.
4. Respuesta libre. Ejemplo: "Empieza fácil → esqueleto → capas → comenta
   porqué → refactoriza ya → atasco: divide/busca/salta → auth primero →
   checklist. Código que funciona > código perfecto."

</details>

## 💬 Entrevista de trabajo

Te acaban de contratar como "backend developer junior". Estas son las
preguntas que te harán en la entrevista:

1. **"Explícame qué es refactorizar como si yo fuera tu abuela."**
2. **"¿Por qué validar en el servidor si ya valido en el frontend?"**
3. **"Mi endpoint POST /api/users a veces devuelve 500 sin mensaje.
   ¿Qué tres cosas revisas *ya*?"**
4. **"¿Qué le dices a un compañero que mete la lógica de negocio dentro
   del controlador?"**
5. **"¿Para qué sirve una estructura de carpetas si al final todo es
   JavaScript?"**

<details>
<summary>...Modelos de respuesta...</summary>

1. "Abuela, refactorizar es como reorganizar la cocina: los cuchillos
   van al cajón de cuchillos, las especias al estante de especias. La
   comida sale igual, pero la próxima vez que cocines no tardas 20 minutos
   buscando el pimentón."
2. "Porque el frontend miente: el usuario puede desactivar JS, manipular
   el localStorage, o llamar a tu API directamente con curl. El servidor
   es la última barrera: *siempre* valida."
3. "(1) ¿Hay try/catch en las operaciones asíncronas? (2) ¿Los logs
   muestran el error real (stack trace) o solo 'Error 500'? (3) ¿La BD
   está viva y accesible desde el contenedor/servidor?"
4. "Que el controlador debe ser *delgado*: recibir request, llamar al
   servicio, devolver response. La lógica de negocio (reglas, cálculos,
   validaciones complejas) va en **servicios**. Así se testea, se reusa
   y no se rompe al cambiar de framework web."
5. "Porque dentro de 6 meses *tú* no vas a recordar dónde está cada cosa.
   Una estructura clara dice: 'las rutas están aquí, la lógica allí, los
   modelos allá'. Es el mapa que evita que el proyecto se convierta en
   una casa donde el baño está en la cocina."

</details>

## 🤷 Preguntas Tontas

> ❓ **Pregunta** — "¿Y si mi proyecto es tan pequeño que no necesita
> estructura de carpetas?"
> **Respuesta** — Incluso en un proyecto de 3 archivos, separar rutas de
> lógica de datos te obliga a pensar en responsabilidades. Y si el proyecto
> crece (que crecerá), ya tienes el hábito. Empieza bien, escala sin dolor.

> ❓ **Pregunta** — "¿Tengo que escribir tests *antes* del código (TDD)?"
> **Respuesta** — TDD estricto es difícil al empezar. Lo práctico: escribe
   el test *justo después* de que la funcionalidad funcione, antes de
   pasar a la siguiente. Así tienes red de seguridad sin bloquearte.

> ❓ **Pregunta** — "¿Qué pasa si mi refactor rompe algo que ya funcionaba?"
> **Respuesta** — Por eso existe el control de versiones: `git diff`,
   `git stash`, `git checkout`. Y por eso los tests son tu red: si el test
   falla, la refactor rompió algo. Si no tienes tests, no refactorices
   código crítico sin antes escribir el test.
