<StoryIntro icono="📖" titulo="Contexto de este capítulo">
  Ya sabes priorizar: auth y entidad principal primero. Pero, ¿cómo pasas de
  "quiero un login" a tener código que funciona? La respuesta no es "escribir
  todo el login de una vez". Es **crecer por capas**.

  Este capítulo te enseña a convertir una funcionalidad en una sucesión de
  pasos tan pequeños que cada uno se puede probar en segundos. Si un paso no se
  puede probar, es demasiado grande.
</StoryIntro>

## 📬 La idea en una frase

> Un esqueleto incremental es como montar un mueble de IKEA: no intentas
> atornillar todas las piezas a la vez. Montas el armazón, compruebas que
> aguanta, añades los estantes, compruebas, pones las puertas. Cada paso se
> verifica antes del siguiente.

## 🧱 La estrategia: iteraciones que se prueban

Cada funcionalidad se divide en **iteraciones mínimas verificables**. Una
iteración no es "hecho el login". Una iteración es:

- **Iteración 1:** El servidor arranca y responde "OK" en `/health`.
- **Iteración 2:** `POST /api/auth/register` devuelve 201 con un usuario mock
  (sin BD aún).
- **Iteración 3:** El registro guarda en BD real y devuelve el usuario creado.
- **Iteración 4:** `POST /api/auth/login` devuelve token JWT válido.
- **Iteración 5:** Middleware `auth` protege rutas y rechaza sin token.

**Regla:** si no puedes hacer `curl` o click y ver el resultado en &lt;30 segundos,
la iteración es demasiado grande. Divídela.

## 📋 Ejemplo completo: del esqueleto al CRUD

Imagina que tu entidad principal es **Producto** (una tienda online).

| Iteración | Qué haces | Cómo lo pruebas |
|---|---|---|
| 1 | Servidor Express/Fastify/Next.js levanta en `localhost:3000` | `curl localhost:3000/health` → `{"ok":true}` |
| 2 | Ruta `GET /api/productos` devuelve array vacío `[]` | Navegador / Postman → `[]` |
| 3 | Modelo `Producto` conectado a BD (Mongo/PostgreSQL/SQLite) | `GET /api/productos` → `[]` (pero de BD real) |
| 4 | `POST /api/productos` crea y devuelve el producto | `curl -X POST -d '{"nombre":"Zapatos"}'` → `201 + objeto` |
| 5 | `GET /api/productos/:id` devuelve uno | `curl /api/productos/1` → objeto |
| 6 | `PUT /api/productos/:id` actualiza | `curl -X PUT ...` → objeto actualizado |
| 7 | `DELETE /api/productos/:id` borra | `curl -X DELETE ...` → `204` |
| 8 | Validación de entrada (nombre obligatorio, precio > 0) | `POST` sin nombre → `400` |
| 9 | Auth: solo usuarios logueados pueden crear/editar/borrar | Sin token → `401` |

**Nota:** las iteraciones 1-3 son "esqueleto" (infraestructura). Las 4-7 son
"CRUD". Las 8-9 son "robustez". **No saltes a la 4 sin haber pasado la 3.**

## 🎭 Datos mock vs datos reales: cuándo cambiar

Una duda frecuente: "¿Uso datos falsos al principio o conecto la BD ya?".

**Respuesta:** empieza con **datos mock (hardcoded o en memoria)** para las
iteraciones 1-2. Te permite validar rutas, controladores y serialización sin
luchar con migraciones, conexiones o seeds.

**El momento de cambiar a BD real:** cuando la ruta y el controlador funcionan
con mocks. Ahí cambias el repositorio/servicio por el real. Si algo falla,
sabes que es la BD, no tu lógica.

```
MOCKS (iteraciones 1-2)          BD REAL (iteración 3+)
┌─────────────────────┐          ┌─────────────────────┐
│ const productos = []│  ───►    │ await Producto.find()│
│ return productos    │          │ return productos    │
└─────────────────────┘          └─────────────────────┘
   Rápido, sin deps               Lento, pero real
   Para validar estructura        Para validar persistencia
```

## 🧠 Mini-chequeo

**Pregunta 1.** Estás en la iteración 3 (conectar BD). El `GET /api/productos`
devuelve error 500. ¿Dónde miras primero?
A) El controlador · B) La conexión / modelo / migración · C) El frontend.

**Pregunta 2.** Una iteración "se puede probar" significa:
A) Pasan los tests unitarios · B) Puedes hacer una petición HTTP y ver respuesta
   esperada en &lt;30s · C) El código compila sin errores.

<details>
<summary>...Respuestas...</summary>

1. **B**. Si las iteraciones 1-2 funcionaban con mocks, el fallo al cambiar a
   BD real está en la capa de datos (conexión, schema, migración).
2. **B**. La verificación manual rápida (curl, Postman, navegador) es el
   criterio pragmático. Los tests unitarios llegan después.

</details>

## ✅ Resumen en 3 frases

1. Divide cada funcionalidad en **iteraciones mínimas verificables**: cada una
   se prueba con una petición HTTP en &lt;30 segundos.
2. Empieza con **datos mock** para validar estructura (rutas, controladores);
   cambia a BD real solo cuando la capa superior funciona.
3. El orden es: **infraestructura → CRUD → validación → auth → siguiente
   entidad**. No saltees pasos.

> 🐛 **Vocabulario rápido**

| Término | Idea general |
|---|---|
| **Iteración verificable** | Paso de código que puedes probar con curl/Postman/navegador ahora mismo |
| **Mock** | Dato falso (hardcoded) que simula la respuesta real para no depender de BD |
| **Esqueleto** | Las iteraciones de infraestructura: servidor, rutas, conexión BD |
| **Capa de datos** | Modelo / repositorio / ORM: lo que habla con la base de datos |
