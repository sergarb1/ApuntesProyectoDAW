## 📬 La idea en una frase

> No empiezas por lo difícil ni por lo bonito: empiezas por lo que **desbloquea
> lo demás**. Como construir una casa: primero los cimientos, no la chimenea.

Es como mudarte a un piso vacío. Si empiezas colgando cuadros, no tienes donde
dormir. Si montas la cama primero, esa noche ya descansas. Tu código funciona
igual: **haz primero lo que te permite probar lo siguiente**.

## 🎯 Prioriza por valor, no por dificultad

El error clásico es atacar lo que parece "impresionante" (un algoritmo
complejo, una gráfica chula, notificaciones push) y dejar lo "aburrido" (login,
CRUD básico, listados) para el final. Resultado: a tres días de la entrega
tienes una funcionalidad bonita que nadie puede usar porque no hay usuarios ni
datos.

La regla de oro: **haz primero lo que más valor aporta al proyecto y que menos
dependencias tiene**.

Normalmente, ese orden es:

1. **Autenticación básica** — sin login, no hay usuario que use la app.
2. **CRUD de la entidad principal** — la operación más básica sobre tu recurso
   clave (productos, tareas, incidencias, recetas...).
3. **Interfaz mínima** — lo justo para que se vea algo en pantalla y puedas
   probar a mano.
4. **Mejoras iterativas** — refinar, añadir validaciones, pulir UI, añadir
   deseables.

```
PRIORIZACIÓN POR VALOR Y DEPENDENCIAS
┌─────────────────────────────────────────────────────────────┐
│  ALTO VALOR + BAJAS DEPENDENCIAS  →  PRIMERO (MVP)          │
│  └─ Auth básica, CRUD entidad principal, listado simple    │
├─────────────────────────────────────────────────────────────┤
│  ALTO VALOR + ALTAS DEPENDENCIAS  →  SEGUNDO (core)         │
│  └─ Relaciones entre entidades, búsquedas, filtros         │
├─────────────────────────────────────────────────────────────┤
│  BAJO VALOR + BAJAS DEPENDENCIAS  →  TERCERO (nice to have) │
│  └─ Perfil de usuario, ajustes, modo oscuro                │
├─────────────────────────────────────────────────────────────┤
│  BAJO VALOR + ALTAS DEPENDENCIAS  →  FUERA / DESPUÉS        │
│  └─ IA, chat tiempo real, analíticas avanzadas             │
└─────────────────────────────────────────────────────────────┘
```

## 🏗️ Empieza con un esqueleto

No implementes todas las funcionalidades a la vez. **Crea una ruta que devuelva
un "Hola mundo". Luego añade autenticación. Luego la primera entidad. Ve
creciendo por capas.**

Piénsalo como levantar un edificio: no pones las ventanas del piso 5 antes de
tener la estructura del piso 1.

```
Iteración 1: "Hola mundo" desde el servidor (¿levanta el servidor? OK)
Iteración 2: Endpoint GET /api/entidad-principal (datos mock) (¿responde? OK)
Iteración 3: Conexión a base de datos real (¿guarda y lee? OK)
Iteración 4: CRUD completo de la entidad principal
Iteración 5: Autenticación JWT / session
Iteración 6: CRUD de la siguiente entidad
... así hasta terminar
```

Cada iteración **debe poder probarse**. Si no se puede probar, no está terminada.

## 🧠 Mini-chequeo

**Pregunta 1.** Tu proyecto es una app de gestión de tareas. ¿Qué implementas
primero?
A) Notificaciones push cuando se acerca una fecha · B) Registro e inicio de
sesión + crear/leer tareas · C) Estadísticas de productividad con gráficas.

**Pregunta 2.** La "parálisis del editor en blanco" se rompe:
A) Esperando a tener la idea perfecta · B) Escribiendo cualquier cosa que
funcione, aunque sea pequeña · C) Leyendo más tutoriales.

<details>
<summary>...Respuestas...</summary>

1. **B**. Auth + CRUD de la entidad principal son alto valor y bajas
   dependencias. Las notificaciones y estadísticas dependen de que existan
   usuarios y tareas.
2. **B**. La acción genera claridad. La perfección es enemiga de lo hecho.

</details>

## ✅ Resumen en 3 frases

1. El mayor obstáculo no es la complejidad técnica, es saber **por dónde
   empezar**: prioriza por valor y dependencias, no por dificultad.
2. Haz primero lo que **desbloquea lo demás**: auth básica → CRUD entidad
   principal → interfaz mínima → mejoras.
3. Crece por **iteraciones probables**: cada paso debe poder probarse antes de
   pasar al siguiente.

> 🐛 **Vocabulario rápido**

| Término | Idea general |
|---|---|
| **MVP** | Minimum Viable Product: lo mínimo que tiene sentido y funciona |
| **Entidad principal** | El recurso clave de tu app (tareas, productos, usuarios...) |
| **CRUD** | Create, Read, Update, Delete: las 4 operaciones básicas de datos |
| **Dependencia** | Algo que necesita estar hecho antes para que esto funcione |
| **Iteración** | Un ciclo completo: código → prueba → funciona → siguiente |
