## 📬 La idea en una frase

> Auth y datos son los **cimientos**. Los cimientos se echan antes de poner las
> ventanas, no después. Si los cimientos fallan, la casa se cae da igual lo
> bonita que sea la fachada.

## 🏗️ Por qué auth y datos son críticos (y van primero)

| Funcionalidad | Por qué es crítica | Qué pasa si la dejas para el final |
|---|---|---|
| **Autenticación (login/registro)** | Es la **puerta de entrada**. Sin usuario identificado, no hay datos personales, no hay permisos, no hay "mis tareas", "mis productos". | Rompes todas las rutas que asumían `req.usuario`. Tienes que tocar controladores, middleware, frontend, tests. |
| **Autorización (roles/permisos)** | Define **quién puede qué**. Un admin no ve lo que ve un user. | Fugas de datos: usuarios ven/borran/editan lo ajeno. Seguridad rota en producción. |
| **Modelo de datos principal (entidad core)** | Es el **corazón del dominio**. Todo gira alrededor: listados, búsquedas, relaciones, reportes. | Cambiar el schema a mitad de proyecto = migraciones, seeds rotos, controladores rotos, frontend roto. |
| **Conexión BD + migraciones** | Es la **infraestructura viva**. Si falla, nada persiste. | Descubres problemas de conexión, tipos, índices, constraints cuando ya tienes código encima. |

**Conclusión:** auth y datos son **trasversales**: tocan casi todo el código.
Hacerlos al final = reescribir casi todo el código.

## 🎯 El orden correcto de implementación (revisitado)

```
SEMANA 1-2: CIMIENTOS (críticos, trasversales)
├── 1. Servidor + health check + logs
├── 2. Conexión BD + migración inicial (schema entidad principal)
├── 3. Auth: registro + login + JWT/session + middleware protect
├── 4. CRUD entidad principal (protegido con auth)
│
SEMANA 3-4: NÚCLEO (funcionalidad de valor)
├── 5. Relaciones (entidades secundarias, población)
├── 6. Búsquedas, filtros, paginación
├── 7. Validaciones robustas + manejo errores global
│
SEMANA 5+: MEJORAS (deseables)
├── 8. Features avanzadas (notificaciones, IA, export, etc.)
├── 9. UI pulida, modo oscuro, accesibilidad
├── 10. Tests, docs, despliegue, rendimiento
```

**Nunca** hagas el paso 8 antes del 4. Nunca hagas el 6 antes del 3.

## 🔐 Auth mínima viable (checklist)

No necesitas OAuth2, 2FA, refresh tokens, roles complejos. Para el MVP:

- [ ] **Registro**: email + password (hasheado con bcrypt/argon2) → 201 + usuario.
- [ ] **Login**: email + password → 200 + token (JWT) o cookie session.
- [ ] **Middleware `auth`**: verifica token, adjunta `req.usuario`, 401 si inválido.
- [ ] **Logout**: invalida token (blocklist) o limpia cookie.
- [ ] **Rutas protegidas**: todas las que tocan datos del usuario usan el middleware.

```javascript
// auth.middleware.js - EJEMPLO MÍNIMO
export async function auth(req, res, next) {
  const token = req.headers.authorization?.replace('Bearer ', '');
  if (!token) return res.status(401).json({ error: 'Token requerido' });

  try {
    const payload = jwt.verify(token, process.env.JWT_SECRET);
    req.usuario = await Usuario.findById(payload.sub).lean();
    if (!req.usuario) return res.status(401).json({ error: 'Usuario no existe' });
    next();
  } catch (e) {
    return res.status(401).json({ error: 'Token inválido o expirado' });
  }
}
```

## 🗄️ Datos: modelo principal primero, migraciones desde día 1

1. **Define el schema de tu entidad principal** (Producto, Tarea, Incidencia...)
   con **todos los campos obligatorios** del MVP. No "añadiré campos después":
   añadir campos = migración = riesgo.
2. **Ejecuta la migración AHORA**. Verifica que crea la tabla/colección bien.
3. **Seed básico**: 3-5 registros de prueba para desarrollar sin ir a la BD a
   meter datos a mano cada vez.
4. **Índices** en campos que filtrarás/ordenarás (email, estado, fechaCreación).

## ¿Y si mi proyecto no necesita login (es público)?

<Aclaracion pregunta="¿Y si mi proyecto no necesita login (es público?)">

  Entonces tu "crítico" no es auth, es **la entidad principal + acceso público
  controlado** (rate limiting, validación estricta, anti-spam). El principio
  sigue: **identifica qué es transversal (toca todo) y hazlo primero**.
  En una API pública, lo transversal es: validación de entrada, rate limiting,
  manejo de errores global, schema de la entidad principal.

</Aclaracion>

## ✅ Resumen en 3 frases

1. **Auth y datos (entidad principal) son cimientos: van PRIMERO.** Son
   trasversales (tocan todo); hacerlos al final obliga a reescribir casi todo.
2. Auth MVP = registro, login, token, middleware protect, logout. Nada de
   OAuth/2FA/roles complejos hasta que el core funciona.
3. Define schema completo de la entidad principal, migra y seedea en semana 1.
   Cambiar el modelo después es la mayor fuente de roturas.

> 🐛 **Vocabulario rápido**

| Término | Idea general |
|---|---|
| **Transversal** | Funcionalidad que afecta a muchas/o todas las partes del sistema (auth, BD, logging) |
| **Cimientos** | Base técnica sobre la que se construye el resto; si falla, todo falla |
| **Middleware auth** | Filtro que verifica identidad antes de llegar al controlador |
| **Migración** | Cambio versionado en estructura de BD (crear tabla, añadir columna, índice) |
| **Seed** | Datos de prueba insertados automáticamente para desarrollar |
