## 📬 La idea en una frase

> La checklist no es para el profesor: es **para ti**. Cada punto que saltas
> es una apuesta a que "no pasará nada". En la defensa, las apuestas se
> pagan caras.

## ✅ La checklist (7 + 1 puntos)

Marca cada casilla **honestamente** antes de cerrar la tarea / hacer commit /
decir "terminado".

### 1. ✅ Funciona el camino feliz
- [ ] La petición correcta (GET/POST/PUT/DELETE) con datos válidos devuelve
  200/201 y el formato esperado.
- [ ] La respuesta incluye los campos que el frontend necesita (IDs, fechas,
  relaciones pobladas).

### 2. ✅ Valida entrada y rechaza lo inválido (400, no 500)
- [ ] Body requerido validado (campos obligatorios, tipos, rangos, formatos).
- [ ] Parámetros de ruta validados (ID existe, formato correcto).
- [ ] Query params validados (paginación, filtros, ordenación).
- [ ] **Nunca** devuelves 500 por datos malos del cliente. Siempre 400 con
  mensaje claro.

### 3. ✅ Maneja "no encontrado" (404) y "sin permisos" (403/401)
- [ ] GET/PUT/DELETE de recurso inexistente → 404 con mensaje.
- [ ] Usuario sin login → 401. Usuario sin rol/permiso → 403.
- [ ] Usuario A no puede modificar/borrar recurso de Usuario B → 403.

### 4. ✅ Protege integridad de datos (BD)
- [ ] Constraints en BD: `NOT NULL`, `UNIQUE`, `FOREIGN KEY`, `CHECK` (precio > 0).
- [ ] Borrado en cascada / restrict configurado según regla de negocio.
- [ ] Transacciones si la operación toca varias tablas/colecciones.

### 5. ✅ Rendimiento básico (no O(N²) ni N+1)
- [ ] Índices en campos de filtro/orden/búsqueda frecuente.
- [ ] Paginación en listados (nunca `findAll` sin límite).
- [ ] `select` / `lean()` / proyección para no traer campos innecesarios.
- [ ] Evita N+1: popula relaciones en la query, no en bucle.

### 6. ✅ Código limpio y mantenible
- [ ] Sin código duplicado (extraído a utilidad/service).
- [ ] Funciones &lt; 30-40 líneas, anidamiento &lt; 3 niveles.
- [ ] Nombres semánticos (no `data`, `res`, `x`, `temp`).
- [ ] Comentarios solo en **porqué** (regla de negocio, decisión, workaround).

### 7. ✅ Commits atómicos y mensaje claro
- [ ] Un commit = un cambio lógico (no "fixes", "changes", "wip").
- [ ] Mensaje: `tipo(ámbito): descripción breve` (ej. `feat(productos): añadir filtro por categoría`).
- [ ] No commits con código comentado, `console.log` de debug, archivos `.env`.

### 8. ✅ **Prueba manual completa** (el "smoke test")
- [ ] Prueba el endpoint con Postman/curl: happy path + 3 casos de error.
- [ ] Prueba desde el frontend real (navegador): fluye sin errores en consola.
- [ ] Prueba edge case: vacío, límite, caracteres raros, concurrencia básica.

## 🧩 Caso práctico: el estudiante que programó lo difícil primero

<CasoPractico titulo="El estudiante que programó lo difícil primero">
  Miguel decidió que su proyecto tendría un sistema de recomendación
  usando machine learning. Pasó tres semanas implementando un algoritmo
  de recomendación que nunca llegó a funcionar bien. Para entonces,
  apenas tenía el login y el registro hechos.

  En las últimas dos semanas, tuvo que hacer a toda prisa: CRUD de
  productos, carrito de compra, pasarela de pago simulada, y la interfaz.
  Todo mal hecho, sin tests, con bugs evidentes.

  **Resultado**: suspendió. Su proyecto prometía mucho, pero entregó poco.

  **Lección**: haz primero lo que sabes que funciona, lo que aporta valor
  seguro, lo que el tribunal va a ver y probar. Las funcionalidades
  "avanzadas" son el postre, no el plato principal. Si no tienes un plato
  principal sólido, el postre no importa.

  **Qué haría hoy**: empezar con el CRUD de productos (su entidad principal),
  luego el carrito, luego la autenticación, luego la interfaz. Y solo si
  sobra tiempo, experimentar con el algoritmo de recomendación.
</CasoPractico>

## 🎯 Cómo usar esta checklist en tu día a día

1. **Imprímela o tenla en segunda pantalla**. No la memorices: úsala.
2. **Al terminar una funcionalidad**, recorre los 8 puntos. ¿Alguna casilla en
   blanco? Vuelve al código. No hagas commit hasta que todo esté ✅.
3. **En la revisión semanal con el profesor**, enseña la checklist marcada.
   "Esta funcionalidad pasa la checklist completa". Eso da confianza.
4. **En la defensa**, si te preguntan "¿has probado X?", respondes: "Sí,
   está en mi checklist punto 8, probé happy path + 3 errores + frontend".

## ¿Tengo que hacer todo esto para CADA endpoint?

<Aclaracion pregunta="¿Tengo que hacer todo esto para CADA endpoint?">

  Para **endpoints del MVP (críticos)**: **sí, todos los puntos**.
  Para **endpoints deseables / internos / admin**: puedes relajar puntos 5
  (rendimiento) y 8 (prueba frontend completa), pero **nunca** saltes 2
  (validación), 3 (permisos), 4 (integridad BD) ni 7 (commits limpios).
  La calidad mínima es innegociable; la excelencia es para el core.

</Aclaracion>

## 🧠 Mini-chequeo

**Pregunta 1.** Acabas de hacer `POST /api/pedidos`. ¿Cuál de estos NO es
obligatorio antes de commit?
A) Validar que `productoId` existe y tiene stock · B) Probar desde el frontend
   real que el pedido aparece en "Mis pedidos" · C) Añadir un índice en
   `pedidos.usuarioId` para acelerar "mis pedidos".

**Pregunta 2.** Un commit dice `fix: cosas varias`. ¿Qué haces?
A) Lo dejas, total funciona · B) Haces `git reset HEAD~1`, separas en commits
   atómicos con mensajes claros · C) Añades otro commit `fix: más cosas`.

<details>
<summary>...Respuestas...</summary>

1. **C**. El índice es rendimiento (punto 5): importante, pero no bloqueante
   para el commit *si* ya has verificado que la query responde en tiempo
   razonable. A y B son obligatorios (validación + prueba real).
2. **B**. Commits "basura" ocultan historial y dificultan revertir. Separa y
   renombra.

</details>

## ✅ Resumen en 3 frases

1. **La checklist es tu red de seguridad, no burocracia.** Pásala *antes* de
   cerrar cada tarea. Lo que saltas hoy, te muerde en la defensa.
2. Mínimo innegociable: **validación (400), permisos (401/403/404),
   integridad BD, commits atómicos, prueba manual happy+error**.
3. El caso Miguel: **haz lo difícil (core) primero, lo vistoso (deseable) al
   final**. Un MVP completo y limpio vale más que un "proyecto soñado" a medias.

> 🐛 **Vocabulario rápido**

| Término | Idea general |
|---|---|
| **Camino feliz / Happy path** | Caso de uso ideal: datos correctos, usuario autorizado, recurso existe |
| **Validación de entrada** | Rechazar datos malos en la frontera (400) antes de que entren al sistema |
| **Integridad referencial** | BD garantiza que no hay huérfanos (FK, cascada, restrict) |
| **Problema N+1** | Hacer 1 query + N queries en bucle en vez de 1 query con join/populate |
| **Commit atómico** | Un commit = un cambio lógico único, reversible y entendible |
