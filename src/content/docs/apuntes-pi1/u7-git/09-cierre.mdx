A lo largo de esta unidad has aprendido a establecer reglas antes de codificar,
elegir herramientas y reuniones que sirvan, repartir tareas con matriz RACI,
aplicar un flujo Git main/dev/feature, configurar ESLint+Prettier, escribir
commits que se entienden, hacer code review constructivo y resolver conflictos
de código y de personas. Ahora toca demostrar que no solo lo has leído: toca
**usarlo**.

## ⭐ Sé el Proyecto

Ponte en la piel del repositorio de tu proyecto. El equipo tiene que decidir
la estrategia de ramas para el próximo mes. ¿Qué eliges?

- **Opción A — "Todos a main"**: "Somos tres, nos conocemos, vamos rápido.
  Commit directo a main, sin ramas, sin PR. Si algo falla, hacemos revert.
  Menos burocracia, más velocidad."
- **Opción B — "Flujo main/dev/feature"**: "Main solo para versiones estables.
  Dev integra todo. Cada funcionalidad (login, productos, pedidos) en su
  rama feature desde dev. PR obligatorio con code review de otro miembro.
  Merge a dev → test → merge a main."
- **Opción C — "GitFlow completo"**: "Feature, develop, release, hotfix,
  master. Cada rama con su propósito estricto. Tags versionados. Es lo que
  usan las empresas, así que lo hacemos nosotros también."

<details>
<summary>...Respuestas...</summary>

**La opción B.** Es el equilibrio para un equipo DAW de 2-4 personas: protege
main, obliga a code review, permite integración continua en dev, y no añade
la complejidad de GitFlow (release/hotfix) que aquí no se necesita. La A es
receta para el desastre del merge final; la C es overengineering para un
proyecto de clase.

</details>

## ⚡ Laboratorio de Tortura

**Duración estimada: 30-40 minutos.** Objetivo: diagnosticar un flujo Git
roto que *parece* funcionar... hasta que no.

**Contexto.** El equipo usó este flujo durante 3 semanas:

```
main (protegida)
  └─ dev
       ├─ feature/login (Marta)
       ├─ feature/productos (Javi)
       └─ feature/pedidos (Lucas)
```

Todo iba bien hasta que intentaron mergear `feature/pedidos` a `dev`:

```
<<<<<<< HEAD (dev)
const API_URL = "https://api.miproyecto.com";
=======
const API_URL = "http://localhost:3000";
>>>>>>> feature/pedidos
```

Lucas resolvió el conflicto dejando `localhost:3000` porque "es lo que
usaba yo". Mergeó a dev. Al día siguiente, la demo en staging falló:
el frontend llamaba a localhost en lugar de a la API real.

**Instrucciones.** Detecta el fallo de proceso (no solo el conflicto) y
propón la corrección. Después, descubre el **fallo intencionado** del
flujo completo.

<details>
<summary>Pista 1</summary>

Revisa el punto 04 (flujo Git): ¿qué rama debe tener la configuración de
producción? ¿Y desarrollo?

</details>

<details>
<summary>Pista 2</summary>

Revisa el punto 07 (code review): ¿quién debía revisar la resolución del
conflicto de Lucas? ¿Se hizo?

</details>

<details>
<summary>Pista 3 (casi la respuesta)</summary>

El fallo intencionado es que **el flujo no usa variables de entorno para
configuración sensible (API_URL, claves, puertos). El código duro
`localhost:3000` vs `https://api...` en el repositorio es el error de
diseño: la configuración debe estar en variables de entorno, no en ramas
Git**. Además, Lucas resolvió el conflicto sin code review y mergeó a dev
sin que nadie probara en staging.

</details>

<details>
<summary>...Solución completa...</summary>

**Corrección de proceso.**
1. **Variables de entorno**: `API_URL` en `.env.development` y
   `.env.production`. El código usa `process.env.API_URL` (punto 05 de U7
   y U6).
2. **Code review obligatorio en PR**: incluido resolución de conflictos.
   Lucas no mergea directo a dev; abre PR → revisa Marta o Javi → test en
   staging → merge.
3. **Staging automático**: cada PR a dev despliega a staging (GitHub
   Actions). Nadie mergea sin pasar staging.
4. **Comunicación**: antes de mergear cambios de config, avisa al equipo.

**Fallo intencionado**: configuración hardcodeada en el repo + ausencia de
review en resolución de conflictos = despliegue roto silencioso. Si no lo
cazas, el tribunal lo hace en la demo. 😉

</details>

## 🧠 Atrévete a Pensar

Preguntas abiertas. Piensa primero, mira la solución después.

1. "Comunicación constante" suena bien, pero ¿cuándo se convierte en
   ruido que impide trabajar? ¿Dónde está el equilibrio?
2. El punto 08 dice "hablad en persona, no por chat". ¿Qué haces si tu
   compañero está en otra ciudad y solo tenéis Discord?
3. ¿Una matriz RACI no es burocracia excesiva para 3 personas? ¿Cuándo
   SÍ merece la pena?
4. Si tuvieras que explicar esta unidad entera en un tuit (280 caracteres),
   ¿qué dirías?

<details>
<summary>...Sugerencias de respuesta...</summary>

1. Equilibrio: **asíncrono por defecto** (issues, PR, tablero), **síncrono
   solo cuando bloquea** (15 min daily, 30 min planning semanal). Si el chat
   suena cada 5 min, silencia notificaciones y fija franjas de foco.
2. Videollamada con cámara. "En persona" = *cara a cara*, no necesariamente
   *físicamente en la misma sala*. Lo clave: tono, matices, reacción
   inmediata.
3. Para 3 personas: RACI informal en el tablero (columna "Responsable" en
   cada tarjeta). Para 4+: RACI escrito. Merece la pena cuando hay solapamiento
   de tareas o tareas "huérfanas" (nadie las hace).
4. Respuesta libre. Ejemplo: "Reglas antes de código → main/dev/feature →
   lint+commits convencionales → code review siempre → conflictos: persona +
   review → config en .env. Equipo coordinado = proyecto entregado."

</details>

## 💬 Entrevista de trabajo

Te acaban de contratar como "desarrollador fullstack junior". Estas son
las preguntas sobre trabajo en equipo que te harán:

1. **"Explícame tu flujo Git ideal para un equipo de 3 personas como si
   yo fuera tu abuela."**
2. **"¿Por qué un commit que dice 'fix' es malo y uno que dice 'Corregir
   validación de email en registro (issue #42)' es bueno?"**
3. **"Tu compañero mergea a main sin PR y rompe la build. ¿Qué haces?"**
4. **"¿Cómo detectas que un miembro del equipo no está aportando?"**
5. **"¿Para qué sirve una daily de 15 minutos si ya nos hablamos por
   Discord todo el día?"**

<details>
<summary>...Modelos de respuesta...</summary>

1. "Abuela, main es la cocina limpia donde sirves la comida. Dev es la
   mesa de preparación donde pruebas los platos. Feature es cada
   receta que preparas en tu bol aparte. Cuando el plato está probado,
   lo pasas a la mesa (dev), y cuando el menú completo está listo,
   a la cocina (main)."
2. "El primero obliga a leer el diff para saber qué pasó. El segundo
   dice *qué*, *por qué* y *referencia al issue*. En 6 meses, el segundo
   te ahorra horas de arqueología git."
3. "(1) Revert inmediato en main. (2) Reunión de 10 min: ¿por qué pasó?
   ¿Faltó review? ¿Faltó test? (3) Acción correctiva: regla dura 'PR
   obligatorio + CI verde' + recordatorio en canal del equipo."
4. "Tarjetas sin mover en 1 semana, commits &lt; 1/semana, no responde en
   daily, no revisa PRs. Acción: habla en privado → acuerda plan → si
   no cambia, escala al profesor. No es 'chivatazo': es salvar el proyecto."
5. "La daily no es para chatear: es **sincronización forzosa**. 15 min,
   de pie, tres preguntas: ¿qué hice? ¿qué haré? ¿qué me bloquea? Obliga
   a verbalizar bloqueos que en chat se quedan en 'ya lo miro'."

</details>

## 🤷 Preguntas Tontas

> ❓ **Pregunta** — "¿Y si mi equipo es de 2 personas? ¿Nos saltamos el
> code review?"
> **Respuesta** — **No**. Code review a 2 es *más* importante: no hay
   tercer ojo. Haced PR cruzados: tú revisas el mío, yo reviso el tuyo.
   5 minutos por PR evitan horas de debugging compartido.

> ❓ **Pregunta** — "¿Puedo usar `git commit --amend` para arreglar mi
> último commit antes de push?"
> **Respuesta** — Sí, *mientras no hayas hecho push*. Si ya pusheaste,
   `amend` reescribe historia compartida: rompe el repo de los demás.
   Usa `git commit --fixup` + `rebase -i --autosquash` antes de mergear.

> ❓ **Pregunta** — "¿Qué hago si mi compañero hace `git push --force`
> a main?"
> **Respuesta** — Protege main: `Settings → Branches → Branch protection
   rules → Require PR + Require status checks`. El force push a main
   debe ser **imposible** por configuración, no por "buenas intenciones".

llegamos. ¿Tenéis un tablero actualizado?"
