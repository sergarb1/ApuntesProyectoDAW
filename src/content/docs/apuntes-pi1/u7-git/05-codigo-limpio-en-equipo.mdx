## 📬 La idea en una frase

> El estilo de código no es gusto personal: es **contrato de equipo**.
> Se acuerda una vez, se automatiza (ESLint + Prettier + Husky) y se
> olvida. El código de todos parece escrito por la misma persona.

## 🤝 Acordar el estilo (15 min, una vez)

Reuníos 15 minutos al empezar el proyecto y decidid esto. No hay "mejor"
opción universal: lo importante es **consistencia**.

| Decisión | Opciones | Recomendación si no tenéis preferencia |
|---|---|---|
| Indentación | Tabs / Espacios (2 o 4) | **Espacios · 2** (estándar JS/TS moderno) |
| Punto y coma | Sí / No | **Sí** (evita errores sutiles en ASI) |
| Comillas | Simples `'` / Dobles `"` | **Simples** (menos escapes en JSX/HTML) |
| Coma final (trailing) | Sí / No | **Sí** (diffs más limpios al añadir líneas) |
| Nombres variables/funciones | camelCase / snake_case | **camelCase** (estándar JS/TS) |
| Nombres componentes React/Vue | PascalCase | **PascalCase** (obligatorio en JSX/Vue) |
| Nombres constantes | UPPER_SNAKE_CASE | **UPPER_SNAKE_CASE** |
| Archivos | kebab-case / PascalCase | **kebab-case** para utils, **PascalCase** para componentes |

> 💡 Escribid lo acordado en `docs/estilo-codigo.md` (3 líneas) y
> vinculadlo en el README. Así el que llega nuevo no tiene que adivinar.

## 🤖 Automatizar: ESLint + Prettier + Husky

**No confiéis en "me acordaré de formatear". No funciona.** Automatizad:

### 1. ESLint (reglas de código: errores, warnings, buenas prácticas)
```bash
npm init @eslint/config@latest
# Elegir: TypeScript, React/Vue, Browser/Node, JSON config
```

### 2. Prettier (formato: espacios, comillas, comas, ancho de línea)
```bash
npm install -D prettier eslint-config-prettier eslint-plugin-prettier
```
- `eslint-config-prettier`: apaga reglas de ESLint que chocan con Prettier.
- `eslint-plugin-prettier`: hace que Prettier corra como regla de ESLint.

### 3. Configuración compartida (`.eslintrc.json` o `eslint.config.js`)

```json
{
  "extends": [
    "eslint:recommended",
    "plugin:@typescript-eslint/recommended",
    "plugin:prettier/recommended",
    "prettier"
  ],
  "plugins": ["prettier"],
  "rules": {
    "prettier/prettier": "error",
    "@typescript-eslint/no-unused-vars": ["warn", { "argsIgnorePattern": "^_" }]
  }
}
```

### 4. `.prettierrc` (opciones de formato)
```json
{
  "semi": true,
  "singleQuote": true,
  "tabWidth": 2,
  "trailingComma": "es5",
  "printWidth": 100,
  "bracketSpacing": true,
  "arrowParens": "avoid"
}
```

### 5. Husky (git hooks: formatea y lintea ANTES de commit)
```bash
npm install -D husky lint-staged
npx husky install
npx husky add .husky/pre-commit "npx lint-staged"
```

`package.json`:
```json
{
  "lint-staged": {
    "*.{js,ts,jsx,tsx,json,css,md}": ["prettier --write", "eslint --fix"]
  }
}
```

**Resultado**: al hacer `git commit`, `lint-staged` pasa Prettier y ESLint
--fix solo a los archivos staged. Si hay errores que no se auto-arreglan,
el commit se cancela. **Cero excusas.**

## 📦 Configuración compartida en el repo

Para que **todo el equipo use lo mismo** sin configurar en local:

1. Commit `eslint.config.js` (o `.eslintrc.json`), `.prettierrc`,
   `.husky/`, `package.json` (con scripts y lint-staged).
2. En README: "Clona, `npm install`, listo. Los hooks se activan solos".
3. Opcional: `editorconfig` (`.editorconfig`) para que el IDE
   indente bien aunque no tengas Prettier instalado.

```ini
# .editorconfig
root = true
[*]
indent_style = space
indent_size = 2
end_of_line = lf
charset = utf-8
trim_trailing_whitespace = true
insert_final_newline = true
```

<Aclaracion pregunta="¿Y si el proyecto ya tiene código sin formatear?">
  Una sola vez: `npx prettier --write . && npx eslint --fix .`. Revisad
  el diff, commit masivo "chore: formatear todo el proyecto con
  Prettier/ESLint". A partir de ahí, los hooks evitan la deriva. No
  formateéis archivo a archivo en PRs normales: ensucia el historial y
  oculta cambios reales.
</Aclaracion>

## 🧠 Mini-chequeo

**Pregunta 1.** ¿Para qué sirve `eslint-config-prettier`?
A) Añade reglas de Prettier a ESLint · B) **Apaga reglas de ESLint que
   chocan con Prettier** · C) Instala Prettier automáticamente.

**Pregunta 2.** ¿Qué hace `lint-staged` en el hook `pre-commit`?
A) Lintea todo el proyecto · B) **Lintea y formatea solo los archivos
   staged** · C) Sube el commit a GitHub.

<details>
<summary>...Respuestas...</summary>

1. **B**. Evita el error "Delete `␍` (prettier/prettier)" por reglas
   duplicadas/contradictorias.
2. **B**. Rápido (solo lo que vas a committear) y seguro (no toca
   archivos de otros).

</details>

## ✅ Resumen en 3 frases

1. Estilo = contrato de equipo. Se acuerda 15 min, se escribe en docs,
   se automatiza.
2. ESLint (calidad) + Prettier (formato) + Husky + lint-staged =
   commits limpios automáticos, reviews centrados en lógica.
3. Configuración en el repo (commitida) = cualquier clon funciona igual
   sin tocar nada.

> 🐛 **Vocabulario rápido**

| Término | Idea general |
|---|---|
| **ESLint** | Linter: analiza código y avisa de errores, bugs potenciales, malas prácticas |
| **Prettier** | Formateador: aplica estilo consistente (espacios, comillas, comas) sin opinión |
| **Husky** | Gestor de git hooks: ejecuta scripts en eventos git (pre-commit, pre-push...) |
| **lint-staged** | Ejecuta linters/formatters solo sobre archivos staged (rápido y seguro) |
| **Conventional Commits** | Estándar de mensajes: `tipo: descripción` (feat, fix, docs, style, refactor...) |
