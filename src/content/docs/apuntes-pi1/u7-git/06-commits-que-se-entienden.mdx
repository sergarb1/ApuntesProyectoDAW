## 📬 La idea en una frase

> Un buen commit explica **qué cambia y por qué** en una línea. Sigue
> Conventional Commits (`tipo: descripción`), es atómico (una cosa por
> commit), y su mensaje sirve de changelog automático.

## ❌ Mal vs ✅ Bien

```bash
# ❌ Mal: ruido, no informa
git commit -m "cambios"
git commit -m "fix"
git commit -m "arreglo login"
git commit -m "wip"
git commit -m "update"

# ✅ Bien: tipo + descripción imperativa + contexto si hace falta
git commit -m "feat: añadir validación de email en formulario de registro"
git commit -m "fix: corregir cálculo de total en carrito (redondeo)"
git commit -m "refactor: extraer hook useAuth para reutilizar en login y registro"
git commit -m "docs: actualizar README con instrucciones de despliegue Docker"
git commit -m "test: añadir tests unitarios para AuthService"
```

## 🏷️ Conventional Commits: tipos estándar

| Tipo | Cuándo usarlo | Ejemplo |
|---|---|---|
| `feat` | Nueva funcionalidad para el usuario | `feat: añadir filtro por categoría en listado` |
| `fix` | Corrección de bug | `fix: evitar error 500 si BD no disponible` |
| `refactor` | Cambio interno sin alterar comportamiento | `refactor: simplificar lógica de paginación` |
| `docs` | Solo documentación | `docs: añadir diagrama ER en README` |
| `style` | Formato, comillas, espacios (sin lógica) | `style: formatear con Prettier` |
| `test` | Añadir o corregir tests | `test: cubrir AuthService.login con Jest` |
| `chore` | Mantenimiento: deps, configs, scripts, CI | `chore: actualizar dependencias de desarrollo` |
| `perf` | Mejora de rendimiento | `perf: cachear consultas frecuentes a productos` |
| `build` | Sistema de build, bundler, Docker | `build: configurar multi-stage Dockerfile` |
| `ci` | Configuración de CI/CD | `ci: añadir job de lint en GitHub Actions` |

> 💡 **Scope opcional**: `feat(auth): añadir login con Google`. Útil en
> proyectos grandes; en proyecto de clase, `feat:` suele bastar.

## 📐 Estructura del mensaje

```
<tipo>[scope opcional]: <descripción en imperativo>

[cuerpo opcional: qué y por qué, no cómo]

[footer opcional: issues relacionados, breaking changes]
```

**Ejemplo completo:**
```
feat(carrito): añadir cupón de descuento por primera compra

Permite aplicar un código promocional que descuenta un 10% en el
primer pedido. El cupón se valida contra la BD y caduca a 30 días.

Closes #42
```

**Reglas de la descripción:**
- **Imperativo**: "añadir", no "añadido" ni "añade".
- **Minúscula inicial**, sin punto final.
- **Máx. 50-72 chars** (GitHub lo muestra en una línea).
- **Qué y por qué** en el cuerpo; el **cómo** está en el diff.

## ⚛️ Atomicidad: un commit = un cambio lógico

```
# ❌ No atómico: mezcla funcionalidad, fix y formato
git commit -m "feat: añadir login + fix validación + formatear"

# ✅ Atómico: tres commits, tres propósitos
git commit -m "feat: añadir formulario de login con email y password"
git commit -m "fix: validar email con regex RFC5322 en login"
git commit -m "style: formatear auth con Prettier"
```

**Por qué importa:**
- `git bisect` encuentra el commit que rompió algo.
- `git revert` deshace una cosa sin arrastrar otras.
- Code review: cada commit se entiende solo.
- Changelog automático: `feat` y `fix` generan release notes.

<CasoPractico titulo="El commit que salvó la entrega">
  A 2 días de la entrega, la app fallaba al deployar en producción.
  `git log --oneline` mostraba:
  ```
  a1b2c3d fix: cosas
  e4f5g6h arreglos varios
  i7j8k9l merge
  ```
  Inútil. Nadie sabía qué commit introdujo el fallo.

  El equipo hizo `git bisect` manual: checkout a commits antiguos,
  probar deploy. Tardaron 3 horas en dar con el commit que cambió la
  variable de entorno de BD.

  Desde ese día, **todos los commits siguen Conventional Commits**.
  En la siguiente entrega, un fallo similar se localizó en 5 minutos
  con `git bisect` automático gracias a commits atómicos y mensajes
  claros.
</CasoPractico>

## 🧠 Mini-chequeo

**Pregunta 1.** ¿Cuál de estos mensajes sigue Conventional Commits?
A) "Arreglado el login" · B) "fix: corregir validación de password en login" · C) "FIX LOGIN".

**Pregunta 2.** ¿Por qué es mejor un commit atómico (una cosa) que uno
grande (mezcla feat + fix + style)?
A) Ocupa menos espacio en disco · B) Permite `git bisect`, `revert`,
   review limpio y changelog automático · C) Hace que el push sea más rápido.

<details>
<summary>...Respuestas...</summary>

1. **B**. Tipo `fix:`, imperativo, descriptivo.
2. **B**. La atomicidad es para la herramienta (bisect, revert) y para
   las personas (review, historial).

</details>

## ✅ Resumen en 3 frases

1. Conventional Commits (`tipo: descripción`) hace el historial legible
   y permite changelogs automáticos.
2. Descripción en imperativo, minúscula, ≤72 chars. Cuerpo opcional con
   qué/por qué. Footer para issues (`Closes #12`).
3. Un commit = un cambio lógico (atómico). Mezclar feat+fix+style en
   uno rompe `bisect`, `revert` y el review.

> 🐛 **Vocabulario rápido**

| Término | Idea general |
|---|---|
| **Conventional Commits** | Especificación de mensajes: `tipo(scope): descripción` |
| **Atómico** | Un commit hace una sola cosa lógica (feat O fix O refactor...) |
| **Imperativo** | Modo verbal de orden: "añadir", "corregir", no "añadido" |
| **git bisect** | Búsqueda binaria automática del commit que introdujo un bug |
| **Changelog** | Registro de cambios por versión; generable auto desde commits `feat`/`fix` |
