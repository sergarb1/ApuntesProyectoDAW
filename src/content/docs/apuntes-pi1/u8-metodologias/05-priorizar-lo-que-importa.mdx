## 📬 La idea en una frase

> No puedes hacer todo. **Priorizar es decidir qué entra y qué se queda
> fuera**, con criterio, no con corazonadas. El MVP es lo imprescindible;
> lo demás es deseable o futuro.

## 🎯 MVP: lo que tiene que funcionar

El **MVP** (Mínimo Producto Viable) es el conjunto de funcionalidades
**sin las cuales el proyecto no tiene sentido**. Si quitas una de estas
funcionalidades, el proyecto deja de funcionar como proyecto.

**Ejemplo**: para un sistema de gestión de biblioteca:

| Categoría | Funcionalidad | ¿MVP? |
|---|---|---|
| Esencial | Buscar libros | ✅ Sí |
| Esencial | Registrar préstamo | ✅ Sí |
| Esencial | Devolver libro | ✅ Sí |
| Esencial | Listar libros disponibles | ✅ Sí |
| Deseable | Reservar libro | ❌ Deseable |
| Deseable | Sistema de multas | ❌ Deseable |
| Deseable | Recomendaciones | ❌ Futuro |
| Futuro | Chat con bibliotecario | ❌ Futuro |

**Pregunta clave**: ¿si quito esta funcionalidad, el proyecto sigue
teniendo sentido? Si la respuesta es sí, no es MVP.

## 📊 Matriz impacto/esfuerzo

Una herramienta visual para decidir qué priorizar:

```
         ALTO IMPACTO
              │
    ┌─────────┼─────────┐
    │  ★ HACER │  ⚡ PLANIFICAR  │
    │ (fácil   │ (difícil pero   │
    │  y útil) │  muy útil)      │
BAJO├─────────┼─────────┤ ALTO
ESFUERZO│  ✅ DELEGAR │  ❌ ELIMINAR  │    ESFUERZO
    │ (rápido  │ (difícil y de   │
    │  pero poco│  poco impacto) │
    │  impacto)│                 │
    └─────────┼─────────┘
              │
         BAJO IMPACTO
```

### Cómo usarla

1. **Listar** todas las funcionalidades
2. **Clasificar** cada una por impacto (alto/bajo) y esfuerzo (alto/bajo)
3. **Resultado**:

| Cuadrante | Acción |
|---|---|
| **Alto impacto + bajo esfuerzo** | Hacer primero (golpe rápido) |
| **Alto impacto + alto esfuerzo** | Planificar bien y meter en sprint temprano |
| **Bajo impacto + bajo esfuerzo** | Hacer si sobra tiempo |
| **Bajo impacto + alto esfuerzo** | Eliminar o dejar para "futuro" |

## 🏷️ MoSCoW: el método de las 4 letras

**MoSCoW** es un acrónimo para clasificar funcionalidades por prioridad:

| Letra | Significado | Ejemplo |
|---|---|---|
| **M** — Must have | Sin esto el proyecto no funciona | Login, registro, CRUD principal |
| **S** — Should have | Importante, pero el proyecto funciona sin ello | Búsqueda avanzada, filtros |
| **C** — Could have | Deseable, pero no crítico | Modo oscuro, notificaciones |
| **W** — Won't have (this time) | No entra en esta entrega | Chat en tiempo real, IA |

### Regla de oro MoSCoW

**Los "Must have" no deben superar el 60% del tiempo disponible.**
Si el 60% del tiempo está en "Must", el 40% restante cubre "Should" y
"Could". Si los "Must" se comen el 100% del tiempo, tu proyecto es
demasiado grande o tu alcance es demasiado ambicioso.

## 🔧 Cómo aplicarlo a tu proyecto

### Paso 1: Lista todas las funcionalidades

Escribe todo lo que "debería" tener el proyecto. Sin filtro. Después
priorizarás.

### Paso 2: Clasifica con MoSCoW

| Funcionalidad | MoSCoW | Impacto | Esfuerzo |
|---|---|---|---|
| Login/registro | M | Alto | Medio |
| CRUD productos | M | Alto | Medio |
| Carrito de compra | M | Alto | Alto |
| Búsqueda | S | Medio | Bajo |
| Filtros avanzados | C | Medio | Medio |
| Panel admin | S | Alto | Alto |
| Notificaciones | C | Bajo | Alto |
| Exportar PDF | W | Bajo | Medio |

### Paso 3: Estima el tiempo total

Si los "M" ya se comen el 70% del tiempo, **recorta antes de empezar**.
Es mejor entregar 3 funcionalidades bien hechas que 7 a medias.

<Aclaracion pregunta="¿Y si el profesor pide algo que no es MVP?">
  Habla con el profesor. Explica qué es lo imprescindible (MVP) y qué
  es deseable. Un profesor razonable preferirá un proyecto con 4
  funcionalidades sólidas que uno con 10 rotas.

  Si el profesor insiste en algo que no es MVP, pregúntate: "¿puedo
  hacerlo de forma simplificada?" Muchas veces la respuesta es sí.
</Aclaracion>

## 🧩 Ejemplo práctico: priorizar un sprint

Equipo de 2 personas, sprint de 1 semana (30h de trabajo real entre los dos).

| Tarea | MoSCoW | Estimación (×2) | ¿Entra? |
|---|---|---|---|
| Login funcional | M | 10h | ✅ Sí |
| Registro con validación | M | 8h | ✅ Sí |
| Pantalla de inicio | M | 6h | ✅ Sí |
| CRUD productos | M | 16h | ⚠️ No cabe |
| Búsqueda de productos | S | 6h | ❌ No es MVP |
| **Total Must** | — | **40h** | — |

**Problema**: los Must ya superan las 30h. Solución: recortar. La pantalla
de inicio puede ser una página estática simple (2h en lugar de 6h).
Así: 10 + 8 + 2 = 20h para Must, quedan 10h para Should.

## 🧠 Mini-chequeo

**Pregunta 1.** Una funcionalidad es "Must have" cuando:
A) El profesor la pide específicamente
B) Sin ella el proyecto no tiene sentido
C) Es fácil de hacer
D) Es lo primero que se te ocurre

**Pregunta 2.** ¿Qué porcentaje del tiempo debería dedicarse a los
"Must have" como máximo?
A) 100% · B) 80% · C) 60% ·D) 40%

<details>
<summary>...Respuestas...</summary>

1. **B**. Must = lo imprescindible para que el proyecto funcione. No
   es por gusto del profesor ni por facilidad.
2. **C**. Si los Must se comen más del 60%, el proyecto es demasiado
   grande o hay que recortar alcance.

</details>

## ✅ Resumen en 3 frases

1. El **MVP** es lo imprescindible: si lo quitas, el proyecto no tiene
   sentido. Todo lo demás es deseable o futuro.
2. La **matriz impacto/esfuerzo** te ayuda a decidir el orden: primero
   lo fácil y útil, después lo importante y difícil, y eliminar lo
   difícil y poco útil.
3. **MoSCoW** clasifica en Must/Should/Could/Won't: los Must no deben
   superar el 60% del tiempo disponible.

> 🐛 **Vocabulario rápido**

| Término | Idea general |
|---|---|
| **MVP** | Mínimo Producto Viable: lo imprescindible para que el proyecto funcione |
| **MoSCoW** | Método de priorización: Must, Should, Could, Won't |
| **Impacto** | Cuánto valor aporta al usuario final |
| **Esfuerzo** | Cuánto tiempo y trabajo requiere implementarlo |
| **Backlog** | Lista de todas las funcionalidades pendientes, por priorizar |
