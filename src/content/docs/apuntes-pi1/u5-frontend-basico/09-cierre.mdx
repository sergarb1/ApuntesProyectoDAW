## ðŸ§  Atrévete a Pensar

Preguntas abiertas. Piensa primero, mira la solución después.

1. Â¿Por qué "mobile-first" no es lo mismo que "responsive"? Â¿Qué se gana
   diseñando primero para lo pequeño?
2. El punto 07 dice "feedback visible". Â¿Qué haces si la operación tarda
   3 segundos? Â¿Spinner? Â¿Barra? Â¿Skeleton? Â¿Cuándo cada uno?
3. "Consistencia visual" suena a "todo igual", pero Â¿qué pasa si una
   pantalla *necesita* ser distinta (ej. landing page vs dashboard)?
4. Si tuvieras que explicar esta unidad entera en un tuit (280 caracteres),
   Â¿qué dirías?

<details>
<summary>...Sugerencias de respuesta...</summary>

1. Mobile-first = **empezar** por lo pequeño (contenido prioritario, tap
   targets, rendimiento). Responsive = **adaptar** a cualquier tamaño.
   Empezar por móvil obliga a priorizar; empezar por escritorio invita a
   meter "todo" y luego no cabe.
2. &lt;2s: spinner sutil. 2-5s: barra de progreso o skeleton. &gt;5s: notificación
   "esto tarda, te avisamos" + opción de cancelar. Nunca dejes al usuario
   sin saber qué pasa.
3. La consistencia es en **patrones** (botones, inputs, espaciado, tipografía),
   no en "todo idéntico". La landing puede tener hero grande, pero sus
   botones usan el mismo sistema que el dashboard.
4. Respuesta libre. Ejemplo: "Proto papel â†’ Figma â†’ mobile-first HTML/CSS/JS
   â†’ consistencia + feedback + test usuarios = UI que el tribunal entiende."

</details>
