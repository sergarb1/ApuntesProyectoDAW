  Suena bien, ¿verdad? Es lo que pensaron Marta, Javi y Lucas cuando
  empezaron su proyecto. Marta haría el frontend, Javi el backend, Lucas
  la base de datos. Cada uno en su rama de git, sin pisarse.

  Dos semanas antes de la entrega, intentaron mergear.

  — "Marta, has cambiado el nombre de una columna que yo usaba"
  — "Javi, tu API devuelve JSON distinto al que esperaba"
  — "Lucas, has borrado un archivo que los dos necesitábamos"

  El merge fue un infierno. Pasaron un fin de semana entero arreglando
  conflictos. Aprendieron que **trabajar en equipo no es repartirse tareas
  y no hablar**. Es comunicarse constantemente, acordar reglas antes de
  empezar y usar Git como herramienta de coordinación, no como trámite
  final.

Este es el séptimo capítulo de un libro de **diecisiete capítulos**. Hasta
aquí has definido tu proyecto, diseñado la solución, modelado los datos,
planificado la interfaz, elegido la arquitectura y preparado el entorno.
Ahora toca la parte que decide si el proyecto llega a puerto o se hunde en
el último mes: **cómo trabajar en equipo sin que el proceso se convierta en
el mayor obstáculo**.

## 🎯 Objetivo de la unidad

Al terminar esta unidad sabrás:

- 🤝 Establecer reglas de juego claras **antes** de escribir la primera línea.
- 🛠️ Elegir y usar herramientas de comunicación y reuniones que sirvan, no que molesten.
- ⚖️ Repartir tareas de forma equilibrada y visible para todo el equipo.
- 🌿 Aplicar un flujo Git sencillo y robusto: `main`, `dev`, ramas `feature`.
- ✨ Configurar y usar ESLint + Prettier para que el código de todos parezca de uno.
- 📝 Escribir commits que cuenten qué ha pasado y por qué, no solo "cambios".
- 👀 Hacer code review para aprender y detectar malentendidos a tiempo.
- ⚔️ Resolver conflictos de código (Git) y de personas sin que el equipo explote.
