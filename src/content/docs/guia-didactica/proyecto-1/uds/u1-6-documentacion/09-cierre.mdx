## 🎯 Mini-chequeo final

Responde estas preguntas antes de seguir:

### Preguntas de comprensión

<details>
<summary>¿Qué es Docs as Code?</summary>

**Respuesta**: Filosofía que trata la documentación igual que el código: se escribe en Markdown, se versiona con Git, se revisa con PRs y se publica automáticamente.

**Para qué sirve**: Para tener documentación siempre actualizada y sincronizada con el código.
</details>

<details>
<summary>¿Cuáles son las secciones mínimas de un README?</summary>

**Respuesta**: Nombre + descripción, características, tecnologías, instalación, uso, estructura del proyecto, equipo y licencia.

**Para qué sirve**: Para que el tribunal entienda tu proyecto en menos de 1 minuto.
</details>

<details>
<summary>¿Cuál es la diferencia entre doc técnica y manual de usuario?</summary>

**Respuesta**: La doc técnica explica CÓMO está hecho (arquitectura, APIs, decisiones). El manual de usuario explica CÓMO SE USA (pasos, capturas, FAQ).

**Para qué sirve**: Para no mezclar audiencias.
</details>

<details>
<summary>¿Qué es el error #1 de documentación?</summary>

**Respuesta**: "Lo documento luego". Dejar la documentación para el final cuando ya no hay tiempo ni ganas.

**Para qué sirve**: Para empezar a documentar desde el primer día.
</details>

<details>
<summary>¿Qué herramientas se recomiendan para documentar?</summary>

**Respuesta**: Markdown para texto, draw.io para diagramas, Notion para wikis colaborativas, GitHub para versionado.

**Para qué sirve**: Para elegir la herramienta correcta para cada tipo de documentación.
</details>

<details>
<summary>¿Cómo se escribe Markdown?</summary>

**Respuesta**: Texto plano con reglas: `#` para títulos, `**negrita**`, `-` para listas, `>` para citas, `[texto](url)` para enlaces.

**Para qué sirve**: Para dominar el formato estándar de documentación técnica.
</details>

### Ejercicio práctico

**En 60 minutos, documenta tu proyecto completo:**

1. **Crea el README** (15 min): Usa la plantilla del punto 08
2. **Escribe la doc técnica** (15 min): Arquitectura, setup, decisiones
3. **Crea el manual de usuario** (15 min): 3 funcionalidades con pasos y capturas
4. **Revisa errores** (15 min): ¿Tienes los 7 errores? Corrígelos

**Si consigues documentar todo esto → tu proyecto está listo para el tribunal.**

## 📖 Vocabulario rápido

| Término | Definición |
|---------|-----------|
| **Docs as Code** | Filosofía de tratar la documentación como código: versionada y revisada |
| **README** | Archivo de entrada de un repositorio que explica el proyecto |
| **Markdown** | Formato de texto plano con sintaxis de formato |
| **Jerga técnica** | Palabras que solo entienden programadores (endpoint, build, etc.) |
| **Diagrama de arquitectura** | Representación visual de cómo se organizan las partes del sistema |
| **Plantilla** | Documento base con secciones predefinidas para rellenar |
| **Docs obsoletas** | Documentación que no refleja el estado actual del código |
| **Setup** | Proceso de instalación y configuración de un proyecto |
| **Captura de pantalla** | Imagen de la interfaz para documentar visualmente |
| **Wiki** | Sitio web colaborativo para documentación |

## 💡 Consejo para el siguiente punto

Si todavía no tienes claro cómo documentar tu proyecto:

1. **Empieza por el README** — es lo que el tribunal verá primero
2. **Usa la plantilla** — no reinventes la rueda
3. **Documenta una funcionalidad** — practica antes de documentar todo
4. **Pide feedback** — que un compañero lea tu doc y te diga si la entiende

**No necesitas documentación perfecta. Necesitas documentación útil.**

---

## ✅ Resumen en 3 frases

1. La documentación se compone de **3 tipos**: README (entrada), doc técnica (cómo está hecho) y manual de usuario (cómo se usa).
2. **Docs as Code** es la filosofía: escribe en Markdown, versiona con Git, publica automáticamente.
3. **Documenta mientras desarrollas**, no al final — y usa la plantilla para no olvidar nada.
