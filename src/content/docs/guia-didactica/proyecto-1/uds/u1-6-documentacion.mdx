## 📬 La idea en una frase

> **Documentar es explicar a tu yo del futuro (y a otros) cómo funciona tu proyecto y por qué.**

No es rellenar páginas. Es **ahorrar tiempo** a quien mantenga el código.

## 🃏 El algoritmo

El proceso de documentación tiene 3 pasos:

1. **Escribe el README** — Lo primero que ve quien clona tu repo
2. **Documenta lo técnico** — Arquitectura, decisiones, estructura
3. **Documenta cómo se usa** — Manual de usuario con ejemplos

## 👣 Paso a paso

### Paso 1: El README (obligatorio)

El README es la **puerta de entrada** a tu proyecto. Debe responder:
- ¿Qué es esto?
- ¿Cómo lo ejecuto?
- ¿Cómo está organizado?

```markdown
# Gestor de Libros

Aplicación de consola para gestionar una colección de libros
con persistencia en SQLite.

## Cómo ejecutar

1. Clonar el repositorio
   ```bash
   git clone https://github.com/usuario/gestor-libros.git
   ```

2. Compilar
   ```bash
   javac -d bin src/**/*.java
   ```

3. Ejecutar
   ```bash
   java -cp bin Main
   ```

## Estructura del proyecto

- `src/model/` — Entidades de dominio
- `src/repository/` — Acceso a datos
- `src/service/` — Lógica de negocio
- `data/` — Base de datos SQLite

## Tecnologías

- Java 17
- SQLite
- Git

## Autor

Nombre Apellido — Curso 2026-2027
```

### Paso 2: Documentación técnica (recomendada)

| Documento | Qué incluye | Ejemplo |
|-----------|-------------|---------|
| **Análisis** | Requisitos, actores, casos de uso | RF-01: Añadir libro... |
| **Diseño** | Arquitectura, modelo de datos, decisiones | "Usé SQLite porque..." |
| **Estructura** | Árbol de carpetas explicado | `src/model/` contiene... |

### Paso 3: Manual de usuario (recomendado)

Explica **cómo usar** la aplicación con ejemplos:

```markdown
## Uso

### Añadir un libro
1. Ejecutar la aplicación
2. Seleccionar "1. Añadir libro"
3. Introducir título, autor y género
4. El libro se guarda en la base de datos

### Buscar libros
1. Seleccionar "3. Buscar"
2. Introducir término de búsqueda
3. Se muestran los resultados que coinciden
```

## 📊 El análisis: ¿cuándo es buena la documentación?

| Característica | ❌ Mala documentación | ✅ Buena documentación |
|----------------|----------------------|------------------------|
| **Atualización** | Desactualizada (meses vieja) | Actualizada con el código |
| **Claridad** | Técnica sin explicar | Explica el porqué |
| **Ejemplos** | Sin ejemplos | Tiene ejemplos concretos |
| **Estructura** | Texto continuo | Encabezados, listas, tablas |
| **Localización** | En un PDF perdido | En el repositorio con el código |

## ⭐ Sé el Código, my friend…

### Docs as Code

El enfoque **Docs as Code** significa tratar la documentación como código:

| Aspecto | Código | Documentación |
|---------|--------|---------------|
| **Formato** | .java, .py | Markdown (.md) |
| **Versionado** | Git | Git |
| **Revisión** | Pull Request | Pull Request |
| **Publicación** | Build automático | Build automático |

**Ventajas**:
- La documentación vive **junto al código**
- Se versiona **automáticamente**
- Se puede generar en **HTML, PDF, etc.**

### Herramientas

| Herramienta | Tipo | Cuándo usarla |
|-------------|------|---------------|
| **Markdown** | Formato básico | Siempre (es el estándar) |
| **Obsidian** | Editor local | Para notas personales |
| **VitePress** | Generador web | Para documentación online |
| **Astro + Starlight** | Generador web | Para sitios de documentación |

<Aclaracion pregunta="¿Cuánta documentación es demasiada?">
  Si tu documentación es más larga que tu código, probablemente estás
  documentando de más. La documentación debe **añadir valor**:
  explicar lo que el código no explica por sí solo.
</Aclaracion>

## ✅ Resumen en 3 frases

1. El README es la **puerta de entrada**: explica qué es, cómo ejecutar y cómo está organizado.
2. Usa **Docs as Code**: la documentación vive en el repositorio, se versiona con Git y se revisa con Pull Requests.
3. Documenta para **tu yo del futuro**: dentro de 6 meses, ¿entenderías lo que escribiste?
