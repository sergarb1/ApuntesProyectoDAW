## 📬 La idea en una frase

> **Git avanzado es trabajar en equipo sin pisarse, automatizar la calidad y mantener el código principal siempre funcional.**

No es solo `git add . && git commit`. Es una **estrategia** para que el código nunca se rompa.

## 🃏 El algoritmo

El proceso tiene 4 partes:

1. **Elige una estrategia de branching** — GitFlow o Trunk-based
2. **Resuelve conflictos** — Cuando dos ramas chocan
3. **Configura hooks** — Automatiza calidad antes del commit
4. **Activa CI/CD** — Pruebas automáticas en cada push

## 👣 Paso a paso

### Paso 1: Estrategias de branching

#### GitFlow (para proyectos con versiones)

```
main (producción)
  │
  └── develop (integración)
        │
        ├── feature/login
        ├── feature/busqueda
        └── feature/dashboard
              │
              └── release/v1.0
                    │
                    └── main (merge + tag)
```

| Rama | Cuándo crear | Cuándo merge |
|------|--------------|--------------|
| **main** | Nunca directamente | Solo desde release/hotfix |
| **develop** | Nunca directamente | Solo desde features/release |
| **feature/** | Nueva funcionalidad | A develop después de review |
| **release/** | Preparar versión | A main Y develop |
| **hotfix/** | Bug en producción | A main Y develop |

#### Trunk-based (más simple, para CI/CD continuo)

```
main (trunk)
  │
  ├── feature/login (corta vida)
  ├── feature/busqueda (corta vida)
  └── feature/dashboard (corta vida)
```

- Las ramas de feature viven **pocos días**
- Se hace merge a main **frecuentemente**

#### ¿Cuál elegir?

| Estrategia | Cuándo usarla |
|------------|---------------|
| **GitFlow** | Proyectos con versiones, releases planificadas |
| **Trunk-based** | CI/CD continuo, despliegues frecuentes |

### Paso 2: Resolución de conflictos

#### Cuándo ocurren
Cuando dos ramas modifican la **misma línea** del mismo archivo.

#### Cómo resolverlos

1. **Obtener la rama destino**: `git merge develop`
2. **VS Code muestra el conflicto** con marcadores:
   ```
   <<<<<<< HEAD
   Tu código
   =======
   Código del otro
   >>>>>>> develop
   ```
3. **Elige qué mantener** (o combina ambas)
4. **Elimina los marcadores** y guarda
5. **Commit**: `git commit -m "resolve: merge conflict in file.java"`

#### Prevención

- **Commits pequeños**: menos probabilidad de conflictos
- **Merge frecuente**: no dejes que las ramas se alejen
- **Comunicación**: si ambos tocan lo mismo, que uno espere

### Paso 3: Hooks de Git

Los hooks son scripts que se ejecutan automáticamente en eventos de Git:

#### Hook pre-commit (el más útil)

```bash
#!/bin/sh
# .git/hooks/pre-commit

# Ejecutar linter antes de commit
npm run lint

# Si falla, no deja commitear
if [ $? -ne 0 ]; then
  echo "❌ Linting failed. Fix errors before committing."
  exit 1
fi
```

#### Otros hooks útiles

| Hook | Cuándo se ejecuta | Para qué |
|------|-------------------|----------|
| **pre-commit** | Antes del commit | Linting, formateo |
| **commit-msg** | Después del mensaje | Validar formato del mensaje |
| **pre-push** | Antes de push | Ejecutar tests rápidos |

### Paso 4: CI/CD básico con GitHub Actions

#### Archivo `.github/workflows/ci.yml`

```yaml
name: CI

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Set up JDK
        uses: actions/setup-java@v4
        with:
          java-version: '17'
      - name: Build
        run: mvn compile
      - name: Test
        run: mvn test
```

#### Convenciones de mensajes de commit

| Tipo | Uso | Ejemplo |
|------|-----|---------|
| **feat** | Nueva funcionalidad | `feat(auth): add JWT login` |
| **fix** | Corregir bug | `fix(search): handle empty results` |
| **refactor** | Refactorizar | `refactor(db): extract connection pool` |
| **docs** | Documentación | `docs: update README setup` |
| **test** | Tests | `test(auth): add login unit tests` |
| **chore** | Mantenimiento | `chore: update dependencies` |

  y ya tienes pipeline básico. Lo difícil no es la herramienta, es
  acostumbrarse a que el código se pruebe automáticamente.

## 📊 El análisis: ¿cuándo es buena tu estrategia Git?

| Característica | ❌ Mala práctica | ✅ Buena práctica |
|----------------|-----------------|-------------------|
| **Commits** | "update", "fix", "cambio" | `feat(auth): add login validation` |
| **Ramas** | Trabajar directamente en main | Crear feature branch por funcionalidad |
| **Merge** | Merge de 500 líneas una vez al mes | Merge frecuente de cambios pequeños |
| **CI** | Probar manualmente antes de entregar | Tests automáticos en cada push |

## ✅ Resumen en 3 frases

1. Elige **GitFlow** (para versiones) o **trunk-based** (para CI/CD continuo) y sé consistente.
2. Los **hooks de Git** automatizan calidad: ejecutan linting y tests antes de cada commit.
3. **CI/CD** significa que tu código se prueba solo en cada push — si falla, no se puede mergear.
