| Aspecto | Detalle |

---

### 2. Logs

| Aspecto | Detalle |
|---------|---------|
| **Librería** | [Ej: Winston] |
| **Niveles habilitados** | [Ej: error, warn, info] |
| **Formato** | [Ej: JSON estructurado] |
| **Archivos** | [Ej: logs/error.log, logs/combined.log] |
| **Rotación** | [Ej: 5MB, 5 archivos máximo] |
| **Transportes** | [Ej: Archivo + Consola (dev)] |

**Ejemplo de log:**
```json
{
  "timestamp": "2025-01-15T10:30:45.123Z",
  "level": "error",
  "message": "Error al conectar con la base de datos",
  "service": "api-users",
  "error": { "name": "ConnectionError", "message": "ECONNREFUSED" }
}
```

---

### 3. Métricas

| Métrica | Tipo | Descripción |
|---------|------|-------------|
| `app_http_requests_total` | Counter | Total de peticiones HTTP |
| `app_http_request_duration_seconds` | Histogram | Duración de peticiones |
| `app_http_requests_active` | Gauge | Peticiones activas |
| `app_errors_total` | Counter | Errores por tipo |

**Endpoint de métricas:** `GET /metrics`

---

### 4. Dashboard de Grafana

| Panel | Tipo | Métrica principal |
|-------|------|-------------------|
| Estado de la app | Stat | `up{job="mi-app"}` |
| Peticiones/segundo | Timeseries | `sum(rate(app_http_requests_total[1m]))` |
| Tasa de errores | Gauge | `rate(errores) / rate(total) * 100` |
| Latencia P95 | Timeseries | `histogram_quantile(0.95, ...)` |
| Errores por endpoint | Table | `topk(10, sum by (path))` |
| CPU y Memoria | Timeseries | `node_cpu`, `node_memory` |

---

### 5. Alertas

| Alerta | Condición | Canal | Urgencia |
|--------|-----------|-------|----------|
| AppDown | `up == 0` durante 1m | Email + Slack | Crítica |
| HighErrorRate | >5% errores durante 2m | Slack | Alta |
| HighLatency | P95 >2s durante 3m | Slack | Media |
| HighCPU | >80% durante 5m | Email | Media |

---

### 6. Comandos útiles

```bash
# Ver logs en tiempo real
tail -f logs/combined.log

# Buscar errores en logs
grep '"level":"error"' logs/combined.log

# Ver métricas actuales
curl http://localhost:3000/metrics

# Levantar stack de monitorización
docker-compose -f docker-compose.monitoring.yml up -d

# Verificar que Prometheus está recogiendo métricas
curl http://localhost:9090/api/v1/targets
```

---

### 7. Troubleshooting

| Problema | Causa | Solución |
|----------|-------|----------|
| No hay logs | Winston no está configurado | Verificar `logger.js` y ruta de archivos |
| No hay métricas | Endpoint /metrics no existe | Verificar ruta y middleware |
| Grafana no conecta | Prometheus apunta mal | Verificar `prometheus.yml` target |
| Alertas no llegan | SMTP no configurado | Verificar `alertmanager.yml` |

## ✅ Resumen en 3 frases

1. Documenta **logs** (librería, formato, rotación), **métricas** (nombres, tipos, descripción) y **dashboard** (paneles, consultas).
2. Incluye las **alertas** configuradas con sus condiciones y canales, y un apartado de **troubleshooting** para problemas comunes.
3. La documentación debe permitir que **cualquier persona reproduzca tu monitorización** sin preguntarte.

## 🔗 Conexión con los agentes de IA

Un agente de IA como **opencode** puede ayudarte a montar y documentar la
monitorización:

- 📝 Generar la **configuración de logs** (Winston, formato, rotación)
- 📊 Crear **consultas PromQL** para métricas y dashboards
- 🚨 Sugerir **alertas** razonables a partir de tus métricas
- 📋 Completar esta plantilla a partir de tu configuración real

Pero **qué métricas importan** (las que responden a tu checklist de
despliegue) lo decides tú: la IA sugiere, tú seleccionas lo relevante.

> 📚 Ver [UD 2.7 — opencode](../../u2-7-ia-copiloto/06-opencode) y [UD 2.7 — Prompts efectivos](../../u2-7-ia-copiloto/02-prompts-efectivos).
