## ⭐ Sé el Proyecto

Ponte en la piel del proyecto de PI1 de tu equipo. El equipo tiene que
decidir cómo afrontar la seguridad en PI2. ¿Qué enfoque eliges?

- **Opción A — "El programador directo"**: "Nuestra app es pequeña,
  no necesita seguridad. El login funciona y ya está."
- **Opción B — "El metódico"**: "Implemento las 4 protecciones básicas:
  parámetros, hash, validación y HTTPS. Luego veo qué más necesito."
- **Opción C — "El exagerado"**: "Necesito firewall, WAF, SOC 2,
  penetration testing y un certificado de seguridad para mi app de
  tareas."

<details>
<summary>...Respuestas...</summary>

**La opción B.** Es la única que equilibra seguridad y eficiencia. La A
es un riesgo inaceptable: ignorar la seguridad por completo lleva a
vulnerabilidades que el tribunal detectará. La C es burocracia excesiva
para un proyecto de clase: no necesitas un SOC 2 para una app de tareas.
La B implementa las protecciones esenciales y luego itera según necesidad.

</details>

## ⚡ Laboratorio de Tortura

**Duración estimada: 30-40 minutos.** Objetivo: detectar el fallo de una
implementación que *parece* correcta... y no lo es.

**Contexto.** Un equipo tiene esta API de autenticación:

```javascript
const express = require('express');
const bcrypt = require('bcrypt');
const jwt = require('jsonwebtoken');
const app = express();

app.use(express.json());

app.post('/api/login', async (req, res) => {
  const { email, password } = req.body;
  const user = await db.query(
    `SELECT * FROM users WHERE email = '${email}'`
  );

  if (!user) {
    return res.status(401).json({ error: 'Credenciales incorrectas' });
  }

  const valid = await bcrypt.compare(password, user.password_hash);
  if (!valid) {
    return res.status(401).json({ error: 'Credenciales incorrectas' });
  }

  const token = jwt.sign(
    { id: user.id, role: user.role },
    'mi-clave-secreta'
  );

  res.json({ token, user: { id: user.id, email: user.email,
    password_hash: user.password_hash } });
});

app.delete('/api/users/:id', async (req, res) => {
  await db.query(`DELETE FROM users WHERE id = ${req.params.id}`);
  res.json({ ok: true });
});

app.listen(3000);
```

**Instrucciones.** Detecta **mínimo 5 problemas** de seguridad. Después,
descubre el **fallo intencionado**.

<details>
<summary>Pista 1</summary>

Revisa el punto 02 (inyección SQL): ¿cómo se construye la consulta
de login? ¿Qué pasa si el email contiene comillas?

</details>

<details>
<summary>Pista 2</summary>

Revisa el punto 03 (contraseñas): ¿qué devuelve la respuesta del
login? ¿Está devolviendo algo que no debería?

</details>

<details>
<summary>Pista 3 (casi la respuesta)</summary>

El fallo intencionado es que **el secreto JWT está hardcodeado** como
'mi-clave-secreta'. Cualquiera que vea el código puede firmar tokens
falsos. Además, la consulta de login es vulnerable a inyección SQL,
y el endpoint DELETE no tiene autenticación.

</details>

<details>
<summary>...Solución completa...</summary>

**Problemas detectados:** (1) Inyección SQL en la consulta de login —
concatenación directa de `email`. (2) Secreto JWT hardcodeado — 'mi-clave-secreta'
debería estar en `.env`. (3) El endpoint DELETE no tiene autenticación —
cualquiera puede borrar usuarios. (4) El DELETE no tiene autorización —
un usuario normal podría borrar otros. (5) La respuesta del login
devuelve `password_hash` — dato sensible expuesto. (6) No hay validación
de entrada — el email podría ser vacío o tener caracteres peligrosos.
(7) No hay CORS configurado — cualquier sitio puede hacer peticiones.

**Correcciones clave:**

```javascript
// 1. Consulta parametrizada
const user = await db.query(
  'SELECT * FROM users WHERE email = ?', [email]
);

// 2. Secreto en variable de entorno
const token = jwt.sign(
  { id: user.id, role: user.role },
  process.env.JWT_SECRET,
  { expiresIn: '24h' }
);

// 3. Endpoint DELETE con autenticación y autorización
app.delete('/api/users/:id', verificarToken, requireRole(['admin']),
  async (req, res) => {
    await db.query('DELETE FROM users WHERE id = ?', [req.params.id]);
    res.json({ ok: true });
  }
);

// 4. Respuesta filtrada
res.json({
  token,
  user: { id: user.id, email: user.email }
});
```

El fallo intencionado era el secreto JWT hardcodeado: visible para
cualquiera que abra el código, permite firmar tokens falsos.

</details>

## 🧠 Atrévete a Pensar

Preguntas abiertas. Piensa primero, mira la solución después.

1. Si solo tienes 2 horas para mejorar la seguridad de tu app, ¿qué
   haces primero?
2. ¿Cómo convences a un compañero de que la seguridad no es opcional?
3. ¿Cuándo un nivel de seguridad es "suficiente" para un proyecto
   de clase?

<details>
<summary>...Sugerencias de respuesta...</summary>

1. Prioriza: (1) parámetros SQL, (2) hash de contraseñas, (3) HTTPS,
   (4) variables de entorno. Estas 4 cosas se implementan en menos de
   2 horas y cubren el 80% de los riesgos.
2. Con datos: el 15% de los ataques web son inyecciones SQL (OWASP).
   Si el profesor ve que la app no valida datos o guarda contraseñas
   en texto plano, pierde puntos directamente.
3. Cuando cubres las 4 protecciones básicas (parámetros, hash,
   validación, HTTPS) y la checklist no tiene puntos críticos pendientes.

</details>

Te acaban de contratar como "full stack junior". Estas son las preguntas
que te harán en la entrevista:

1. **"¿Qué es la inyección SQL y cómo la evitas?"**
2. **"¿Por qué no guardar contraseñas en texto plano?"**
3. **"¿Qué necesitas para que una API sea segura?"**

<details>
<summary>...Modelos de respuesta...</summary>

1. "Es cuando un atacante inserta código SQL en un campo de entrada.
   Se evita con consultas parametrizadas, nunca concatenando strings."
2. "Porque si alguien accede a la base de datos, tiene todas las
   contraseñas. Con bcrypt, solo tiene hashes irreversibles."
3. "HTTPS para cifrar la comunicación, validación en el servidor,
   autenticación con JWT, autorización con roles, y secretos en
   variables de entorno."

</details>

## 🤷 Preguntas Tontas

> ❓ **Pregunta** — "¿Y si mi proyecto es tan pequeño que no necesita
> seguridad?"
> **Respuesta** — Si tiene login o recoge datos de usuarios, necesita
> seguridad. No es cuestión de tamaño, es cuestión de responsabilidad.

> ❓ **Pregunta** — "¿Qué pasa si el tribunal no se fija en la
> seguridad?"
> **Respuesta** — Puede que no, pero puede que sí. Y lo más importante:
> proteger datos de otros es lo correcto, independientemente de la nota.

## 🎬 Post-Créditos

El proyecto de Sergio ya no tiene contraseñas en texto plano. Las
consultas SQL usan parámetros. La API filtra datos sensibles. HTTPS
está activo. Los secretos están en variables de entorno. Los usuarios
tienen roles definidos.

Suena el teléfono. Es un mensaje de su compañero de backend:

"He configurado CORS para que solo acepte peticiones de nuestro
dominio. Pero el profesor ha preguntado si también necesitamos
protección contra ataques DDoS para el proyecto. ¿Qué le digo?"

Sergio sonríe. Los ataques DDoS están fuera del alcance de un
proyecto de clase. Pero saber que existen demuestra que su equipo
piensa en seguridad en serio.
