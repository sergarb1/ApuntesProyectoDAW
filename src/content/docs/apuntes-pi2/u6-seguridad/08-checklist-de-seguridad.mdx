## La idea en una frase

> Una checklist no es burocracia: es la diferencia entre "funciona" y
> "funciona bien, de forma segura".

## Checklist de seguridad completa

Revisa cada punto antes de entregar tu proyecto. Si alguno falla,
corrígelo antes de la presentación.

### Base de datos

- [ ] Todas las consultas SQL usan parámetros (`?` o `$1`), nunca
      concatenación de strings
- [ ] Las contraseñas se guardan con hash (bcrypt, argon2), nunca
      en texto plano
- [ ] Las contraseñas tienen al menos 8 caracteres, con mayúsculas,
      minúsculas y números
- [ ] No se devuelven hashes de contraseñas ni tokens en las respuestas
      de la API
- [ ] Los datos sensibles (tarjetas, datos médicos) se cifran en
      la base de datos

### Validación y entrada

- [ ] Todos los datos de entrada se validan en el servidor (tipo,
      longitud, formato, rango)
- [ ] Se usa sanitización para eliminar caracteres peligrosos en
      textos que se muestran en la web
- [ ] Los campos obligatorios están marcados como requeridos
- [ ] Los formularios tienen límites de tamaño (upload de archivos,
      campos de texto)

### Autenticación y autorización

- [ ] Las contraseñas se verifican con `bcrypt.compare`, nunca
      con comparación directa
- [ ] Los tokens JWT tienen fecha de expiración (máximo 24 horas)
- [ ] El secreto JWT está en una variable de entorno, nunca en el código
- [ ] Cada ruta protegida verifica el token Y el rol del usuario
- [ ] El principio de mínimo privilegio está implementado (cada usuario
      solo tiene los permisos que necesita)

### Variables de entorno y secretos

- [ ] No hay API keys, contraseñas ni tokens hardcodeados en el código
- [ ] El archivo `.env` está en `.gitignore`
- [ ] Existe un `.env.example` con valores de ejemplo (sin secretos reales)
- [ ] Los secretos son largos (mínimo 32 caracteres) y aleatorios
- [ ] No se muestran variables de entorno en mensajes de error

### Comunicación

- [ ] La aplicación usa HTTPS (no HTTP)
- [ ] CORS está configurado para aceptar solo orígenes conocidos
- [ ] Los cookies (si se usan) tienen `httpOnly` y `secure`
- [ ] No se transmiten datos sensibles en la URL (parámetros GET)

### Errores y logs

- [ ] Los mensajes de error no revelan información interna (stack
      traces, rutas de archivos, versiones de librerías)
- [ ] Los logs no contienen contraseñas, tokens ni datos sensibles
- [ ] Los errores de base de datos se muestran como "Error interno"
      al usuario, nunca los detalles técnicos

### Dependencias

- [ ] Se ejecuta `npm audit` o equivalente periódicamente
- [ ] No hay dependencias con vulnerabilidades conocidas críticas
- [ ] Las dependencias están actualizadas (o al menos las críticas)

## Cómo usar esta checklist

### Antes de cada sprint

Revisa los puntos críticos:
- ¿Las consultas SQL siguen parametrizadas?
- ¿Los secretos siguen fuera del código?
- ¿HTTPS sigue activo?

### Antes de la presentación

Revisa **todos** los puntos. Dedica una hora completa. Si encuentras
un problema, corrígelo antes de la defensa. Es mejor entregar con
menos funcionalidades que entregar con vulnerabilidades.

### En equipo

Divide la checklist entre los miembros. Cada uno revisa una sección
y reporta al equipo. Así cubres más terreno en menos tiempo.

## Caso práctico

<CasoPractico titulo="El día que la checklist evitó un desastre">

  Un equipo tenía su proyecto listo para la presentación. Una hora
  antes, el líder sacó la checklist de seguridad y empezó a revisar.

  Punto 1: "¿Las consultas SQL usan parámetros?" — Sí, todos.
  Punto 2: "¿Las contraseñas van con hash?" — Sí, bcrypt con 10 rondas.
  Punto 3: "¿La API devuelve datos sensibles?" — ...

  Se detuvo. La API de perfil de usuario devolvía el objeto completo,
  incluyendo `password_hash` y `token_recuperacion`.

  En 10 minutos corrigieron el endpoint para que solo devolviera
  `id`, `nombre` y `email`. El profesor, en la presentación, abrió
  el inspector y revisó la respuesta de la API.

  Todo limpio. Sin datos sensibles. La checklist les había salvado
  de una pérdida de puntos segura.

  **Lección**: una checklist te avisa de problemas que ya sabes
  detectar pero que puedes olvidar bajo presión.

</CasoPractico>

## Errores que la checklist detecta

| Error | Punto de la checklist | Consecuencia |
|-------|----------------------|--------------|
| Contraseña en texto plano | Base de datos | Acceso completo si hay brecha |
| API key en el código | Variables de entorno | Cualquiera con el repo la ve |
| Sin CORS | Comunicación | Cualquier sitio puede llamar a tu API |
| Sin HTTPS | Comunicación | Datos en texto plano en la red |
| Sin validación | Validación y entrada | Datos basura en la BD |
| Token sin expiración | Autenticación | Token válido para siempre |
| Error con stack trace | Errores y logs | Información interna expuesta |

## Mini-chequeo

**Pregunta 1.** ¿Cuándo se debe usar la checklist?
A) Solo al final del proyecto · B) En cada sprint y antes de cada
entrega · C) Solo si el profesor la pide

**Pregunta 2.** ¿Qué hago si un punto de la checklist falla?
A) Lo ignoro porque funciona igual · B) Lo corrijo antes de la
entrega · C) Lo documento y lo corrijo después

<details>
<summary>...Respuestas...</summary>

1. **B**. La checklist se usa periódicamente (cada sprint) y siempre
   antes de una entrega. No es algo que solo se hace al final.
2. **B**. Si un punto falla, se corrige antes de entregar. La checklist
   existe para detectar problemas a tiempo, no para documentar fallos.

</details>

## Resumen en 3 frases

1. La checklist de seguridad cubre base de datos, validación,
   autenticación, secretos, comunicación, errores y dependencias.
2. Úsala en cada sprint y siempre antes de una entrega: te detecta
   problemas que puedes olvidar bajo presión.
3. Si un punto falla, corrígelo antes de la presentación. Es mejor
  entregar con menos funcionalidades que con vulnerabilidades.
