## La idea en una frase

> Si tu aplicación concatena lo que el usuario escribe directamente
> en una consulta SQL, estás regalando el control de tu base de datos
> a cualquiera.

## Qué es la inyección SQL

La inyección SQL es un ataque donde el usuario inserta código SQL
malicioso en un campo de entrada de la aplicación. Si la aplicación
construye la consulta concatenando ese código directamente, la base
de datos ejecuta lo que el usuario quiera.

### Ejemplo visual

Imagina un formulario de login:

```sql
-- Tu consulta en el código:
SELECT * FROM usuarios WHERE email = '[email]' AND password = '[pass]'

-- Lo que el usuario escribe en el campo email:
' OR '1'='1

-- La consulta se convierte en:
SELECT * FROM usuarios WHERE email = '' OR '1'='1' AND password = 'cualquiera'
```

`'1'='1'` siempre es verdadero. La consulta devuelve **todos los
usuarios**. El atacante accede sin conocer ninguna contraseña.

### Tipos de inyección SQL

| Tipo | Qué hace | Ejemplo |
|------|----------|---------|
| **Básica** | Manipula la lógica de la consulta | `' OR '1'='1` |
| **Unión** | Añade tablas con UNION SELECT | `' UNION SELECT * FROM passwords --` |
| **Blind** | No ve resultados directamente | `' AND (SELECT LENGTH(password) FROM users LIMIT 1) > 5 --` |
| **Time-based** | Mide tiempos para inferir datos | `' AND SLEEP(5) --` |

No necesitas memorizar los tipos. Solo necesitas entender que **cualquier**
campo de entrada puede ser un punto de ataque si no lo manejas bien.

## Por qué es tan peligroso

La inyección SQL lleva años en el top 10 de OWASP (Open Web Application
Security Project). Es el ataque más documentado y sigue funcionando
porque muchos desarrolladores no lo evitan.

Las consecuencias pueden ser catastróficas:

- **Lectura de datos**: el atacante puede ver todos los registros
- **Borrado de tablas**: puede borrar tu base de datos entera
- **Inserción de datos**: puede crear usuarios administradores
- **Ejecución de comandos**: en algunos casos, controlar el servidor

## La solución: consultas parametrizadas

La forma de evitar la inyección SQL es **nunca concatenar** lo que
el usuario escribe directamente en una consulta. Usa parámetros.

### Ejemplo en Node.js con SQLite

```javascript
// ❌ MAL — Concatenación directa
const query = "SELECT * FROM usuarios WHERE email = '" + email + "'";
db.run(query);

// ✅ BIEN — Consulta parametrizada
const query = "SELECT * FROM usuarios WHERE email = ?";
db.run(query, [email]);
```

El signo `?` es un **marcador de posición**. La librería de base de
datos se encarga de escapar el valor correctamente. Da igual lo que
el usuario escriba: nunca se interpretará como código SQL.

### Ejemplo en Java con JDBC

```java
// ❌ MAL
String query = "SELECT * FROM usuarios WHERE email = '" + email + "'";
stmt.executeQuery(query);

// ✅ BIEN
String query = "SELECT * FROM usuarios WHERE email = ?";
PreparedStatement pstmt = conn.prepareStatement(query);
pstmt.setString(1, email);
pstmt.executeQuery();
```

### Ejemplo en Python con sqlite3

```python
# ❌ MAL
query = f"SELECT * FROM usuarios WHERE email = '{email}'"
cursor.execute(query)

# ✅ BIEN
query = "SELECT * FROM usuarios WHERE email = ?"
cursor.execute(query, (email,))
```

## Errores comunes que parecen seguros pero no lo son

### Usar template literals

```javascript
// ❌ MAL — Parece más limpio pero sigue siendo vulnerable
const query = `SELECT * FROM usuarios WHERE email = '${email}'`;
```

Los template literals de JavaScript (`backticks`) no escapan nada.
Sigues concatenando el valor directamente en la consulta.

### "Filtrar" caracteres peligrosos

```javascript
// ❌ MAL — Intento de sanitización manual
const sanitized = email.replace(/'/g, "''");
const query = `SELECT * FROM usuarios WHERE email = '${sanitized}'`;
```

Esta aproximación es frágil. Puedes olvidar un caso, y los atacantes
siempre encuentran formas de eludir filtros manuales. Las consultas
parametrizadas existen para que no tengas que preocuparte por esto.

### Usar ORM sin pensar

```javascript
// ❌ MAL — El ORM puede generar SQL inseguro si lo usas mal
const users = await User.findAll({
  where: `email = '${email}'`  // ¡Sigue siendo vulnerable!
});

// ✅ BIEN — El ORM gestiona los parámetros
const users = await User.findAll({
  where: { email: email }
});
```

Los ORM (Object-Relational Mapping) como Sequelize o SQLAlchemy protegen
automáticamente... pero solo si los usas correctamente. Si pasas strings
en vez de objetos, pierdes la protección.

## Caso práctico

<CasoPractico titulo="El buscador que devolvía más de lo esperado">

  Un equipo tenía un formulario de búsqueda de productos. El endpoint
 接受ía un parámetro `q` y ejecutaba:

  ```sql
  SELECT * FROM productos WHERE nombre LIKE '%[q]%';
  ```

  Un compañero, curioso, escribió en el buscador:

  ```
  a' UNION SELECT email, password FROM usuarios --
  ```

  La aplicación devolvió una lista donde, entre los productos,
  aparecían emails y contraseñas hasheadas de todos los usuarios.

  No borró nada. No destruyó la base de datos. Pero expuso datos
  que no debería haber visto.

  **Lección**: la inyección SQL no siempre borra datos. A veces solo
  lee. Y leer datos sensibles es igual de grave.

</CasoPractico>

<Aclaracion pregunta="¿Y si uso MongoDB en vez de SQL?">
  MongoDB y otras bases de datos NoSQL también son vulnerables a
  inyecciones, aunque de forma diferente. Un atacante puede manipular
  los parámetros de consulta para que devuelva más datos de los
  previstos.

  La regla es la misma: **nunca confíes en la entrada del usuario**.
  Usa las herramientas de validación y sanitización que proporcione
  tu base de datos, sea SQL o NoSQL.
</Aclaracion>

## Cómo detectar inyección SQL en tu código

Busca estos patrones en tu proyecto:

1. **Concatenación de strings** en consultas SQL (`+`, template literals
   con interpolación directa)
2. **Variables de entrada** (req.body, req.query, req.params) que aparezcan
   directamente en una consulta
3. **Funciones de ejecución** que reciban un string completo en vez de
   query + parámetros

Si encuentras alguno, reemplázalo por consultas parametrizadas. No es
un cambio grande, pero es crítico.

A) `db.query("SELECT * FROM users WHERE id = ?", [id])`
B) `db.query("SELECT * FROM users WHERE id = " + id)`
C) `User.findByPk(id)`

**Pregunta 2.** ¿Por qué las template literals de JavaScript no protegen?
A) Porque son más rápidas · B) Porque interpolan el valor directamente
en el string sin escapar · C) Porque solo funcionan con strings

<details>
<summary>...Respuestas...</summary>

1. **B**. La concatenación directa (`+`) inserta el valor del usuario
   en la consulta sin escapar. Las opciones A y C usan parámetros
   implícitos o explícitos.
2. **B**. Las template literals (`backticks`) interpolan el valor
   tal cual, sin escpear ni parametrizar. Sigue siendo concatenación.

## Resumen en 3 frases

1. La inyección SQL ocurre cuando el código concatena la entrada del
   usuario directamente en una consulta de base de datos.
2. La solución siempre es la misma: usa consultas parametrizadas con
   `?` o `$1` en vez de concatenar strings.
3. Esto no es solo para SQL: cualquier base de datos (MongoDB, etc.)
   requiere que no confíes en la entrada del usuario.
