## ⭐ Sé el Proyecto

Ponte en la piel del proyecto de PI1 de tu equipo. El frontend tiene
12 pantallas, formularios con validación, datos dinámicos, y el código
JavaScript ya no se mantiene. El equipo debe decidir cómo afrontar PI2.

- **Opción A — "Quédate con HTML plano"**: "Ya funciona. No compliques."
- **Opción B — "Migra a un framework de golpe"**: "Borramos todo y
  empezamos con React desde cero."
- **Opción C — "Migra incrementalmente"**: "Empieza con Vue en las 3
  pantallas más complejas. Si funciona, migra el resto."

<details>
<summary>...Respuestas...</summary>

**La opción C.** Equilibra riesgo y progreso. La A ignora el problema:
con 12 pantallas y datos dinámicos, HTML plano no escala. La B es un
riesgo enorme: borrar desde cero implica perder lo que funciona. La C
migra donde más se necesita, aprende en el camino, y escala sin romper.

</details>

## ⚡ Laboratorio de Tortura

**Duración estimada: 30-40 minutos.** Objetivo: detectar el fallo de una
implementación que *parece* correcta... y no lo es.

**Contexto.** Un proyecto de e-commerce con React. La interfaz tiene
un catálogo de productos y un carrito de compra:

```jsx
function ProductList() {
  const [productos, setProductos] = useState([]);
  useEffect(() => {
    fetch('/api/productos')
      .then(res => res.json())
      .then(data => setProductos(data));
  }, []);
  return (
    <div>
      {productos.map(p => (
        <div key={p.id}>
          <h3>{p.nombre}</h3>
          <p>{p.precio} €</p>
          <button onClick={() => agregarAlCarrito(p)}>Añadir</button>
        </div>
      ))}
    </div>
  );
}

function CartSidebar() {
  const [carrito, setCarrito] = useState([]);
  function agregarAlCarrito(producto) {
    setCarrito([...carrito, producto]);
  }
  return (
    <div>
      <h3>Carrito ({carrito.length})</h3>
      {carrito.map((item, i) => (
        <div key={i}>{item.nombre} - {item.precio} €</div>
      ))}
    </div>
  );
}
```

**Instrucciones.** Detecta **mínimo 5 problemas** de frontend y
propón la corrección. Después, descubre el **fallo intencionado**.

<details>
<summary>Pista 1</summary>

Revisa el punto 04 (gestión del estado): ¿dónde vive el carrito?
¿`ProductList` y `CartSidebar` comparten el mismo estado?

</details>

<details>
<summary>Pista 2</summary>

Revisa el punto 03 (componentes): ¿`ProductList` renderiza la lista
Y tiene la lógica de fetch? ¿Debería separarse?

</details>

<details>
<summary>Pista 3 (casi la respuesta)</summary>

El fallo intencionado es que **el carrito está duplicado**. `ProductList`
tiene su propio estado `carrito` y `CartSidebar` tiene el suyo. Cuando
uno agrega un producto, el otro no se entera. Son dos estados diferentes
que deberían ser uno.

</details>

<details>
<summary>...Solución completa...</summary>

**Problemas detectados:** (1) Estado del carrito duplicado. (2)
`ProductList` hace fetch y renderiza: debería separarse. (3)
`agregarAlCarrito` no está definida (se usa pero no se importa). (4)
No hay manejo de errores en el fetch. (5) `key={i}` es un anti-patrón.

**Corrección del estado:**

```jsx
function App() {
  const [carrito, setCarrito] = useState([]);
  function agregarAlCarrito(producto) {
    setCarrito([...carrito, producto]);
  }
  return (
    <div>
      <ProductList onAgregar={agregarAlCarrito} />
      <CartSidebar items={carrito} />
    </div>
  );
}
```
El fallo era el estado duplicado: cada componente tenía su copia y las
actualizaciones no se sincronizaban.

</details>

## 🧠 Atrévete a Pensar

1. ¿Cuándo rechazar un framework "porque sí"?
2. ¿Qué haces si tu interfaz funciona pero es inaccesible?
3. ¿Cuándo una optimización se convierte en over-engineering?

<details>
<summary>...Sugerencias de respuesta...</summary>

## 🤷 Preguntas Tontas

> ❓ **Pregunta** — "¿Y si mi proyecto es tan pequeño que no necesita
> componentes reutilizables?"
> **Respuesta** — Incluso un proyecto pequeño se beneficia de separar
> la interfaz en partes lógicas. Un botón separado del formulario
> ya es un componente.

> ❓ **Pregunta** — "¿Qué pasa si optimizo todo y el tribunal no
> valora el rendimiento?"
> **Respuesta** — El tribunal no mide milisegundos, pero sí nota un
> sitio lento. Optimizar no es por el tribunal: es por los usuarios.

## 🎬 Post-Créditos

El proyecto de Sergio ya no tiene HTML plano con JavaScript suelto.
Ahora tiene componentes reutilizables, estado bien gestionado, imágenes
comprimidas, formularios con labels, y navegación por teclado. La
interfaz carga en 1.8 segundos.

Suena el teléfono. Es un mensaje de su compañero de backend:

"Necesito que el endpoint `GET /api/productos` devuelva los productos
con paginación `?page=1&limit=20`. Y que el de `POST /api/carrito`
acepte JSON con `{ productoId, cantidad }`. ¿Puedes hacer el frontend
que lo consuma?"

Sergio mira sus componentes: `ProductList` hace fetch, `CartSidebar`
muestra el carrito. Solo tiene que añadir parámetros de paginación y
un servicio para las peticiones. Con los componentes que ya tiene,
es cuestión de una tarde.
