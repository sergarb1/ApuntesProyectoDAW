## La idea en una frase

> GitHub Actions es el CI/CD de GitHub: un archivo YAML en tu
> repositorio que ejecuta pasos automáticamente cada vez que haces push.

## ¿Qué es GitHub Actions?

GitHub Actions es la plataforma de automatización de GitHub. Te
permite definir **workflows** (flujos de trabajo) que se ejecutan
automáticamente cuando ocurre un evento en tu repositorio.

El evento más común es un **push**: cada vez que subes código a
una rama (normalmente `main`), GitHub Actions ejecuta los pasos
que definas.

```
git push → GitHub Actions detecta el push → Ejecuta los pasos del workflow
                                                    ↓
                                         Tests → Build → Deploy
```

## La estructura de un workflow

Un workflow de GitHub Actions es un archivo YAML en la carpeta
`.github/workflows/`. Cada workflow tiene esta estructura:

```yaml
name: Nombre del workflow

on:
  push:
    branches: [main]

jobs:
  nombre-del-job:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm install
      - run: npm test
```

Vamos a desglosarlo:

### `name`

El nombre que aparece en la pestaña "Actions" de GitHub. Puedes
poner lo que quieras.

### `on`

El evento que dispara el workflow. El más común es `push` en la
rama `main`. También puedes usar `pull_request`, `schedule` o
`workflow_dispatch` (para ejecutarlo manualmente).

### `jobs`

Los trabajos que se ejecutan. Cada job es una máquina virtual
que ejecuta los pasos. Puedes tener varios jobs que se ejecuten
en paralelo.

### `runs-on`

El sistema operativo de la máquina virtual. `ubuntu-latest` es
el más rápido y barato. También puedes usar `windows-latest` o
`macos-latest`.

### `steps`

Los pasos que se ejecutan en orden. Cada paso es una acción
(`uses`) o un comando (`run`).

## Workflow mínimo para un proyecto Node.js

```yaml
# .github/workflows/deploy.yml
name: CI

on:
  push:
    branches: [main]

jobs:
  test-and-build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: npm install
      - run: npm test
      - run: npm run build
```

Este workflow:
1. Se ejecuta cada push a `main`
2. Clona el repositorio (`checkout`)
3. Instala Node.js 20
4. Instala dependencias (`npm install`)
5. Ejecuta tests (`npm test`)
6. Construye el proyecto (`npm run build`)

Si algo falla en cualquier paso, el workflow se detiene. La app
no se despliega si los tests fallan.

## Workflow con despliegue a Vercel

Si usas Vercel, puedes desplegar automáticamente:

```yaml
name: Deploy

on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: npm install
      - run: npm test
      - run: npm run build
      - uses: amondnet/vercel-action@v25
        with:
          vercel-token: ${{ secrets.VERCEL_TOKEN }}
          vercel-org-id: ${{ secrets.VERCEL_ORG_ID }}
          vercel-project-id: ${{ secrets.VERCEL_PROJECT_ID }}
          vercel-args: '--prod'
```

Necesitas crear un **token de Vercel** y guardarlo como secreto
en GitHub (Settings → Secrets → Actions).

## Workflow con despliegue a Render

```yaml
name: Deploy

on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: npm install
      - run: npm test
      - run: npm run build
```

Render detecta automáticamente los pushes y despliega. No necesitas
un paso extra de despliegue en el workflow si tu repo está conectado
a Render.

## Los secrets: variables que no se suben al repositorio

Nunca subas tokens, contraseñas o claves de API al código fuente.
GitHub Actions usa **secrets** para esto:

1. Ve a tu repositorio → Settings → Secrets and variables → Actions
2. Haz clic en "New repository secret"
3. Pon el nombre (por ejemplo, `VERCEL_TOKEN`) y el valor
4. Usa `${{ secrets.VERCEL_TOKEN }}` en tu workflow

Los secrets están encriptados y no se muestran en los logs.

<Aclaracion pregunta="¿Y si no entiendo el YAML?">
  No necesitas entender todo el YAML desde el principio. Copia un
  workflow mínimo, adáptalo a tu proyecto y ve aprendiendo sobre
  la marcha. Lo importante es que entiendas:

  1. **on**: cuándo se ejecuta (cada push a main)
  2. **steps**: qué se ejecuta (install, test, build)
  3. **run**: comandos que se ejecutan en orden

  El resto (actions, secrets, matrix) lo aprendes cuando lo
  necesites. No necesitas ser un experto en YAML para tener
  CI/CD funcionando.
</Aclaracion>

## Cómo comprobar que funciona

1. Haz push a `main`
2. Ve a la pestaña "Actions" de tu repositorio
3. Verás el workflow ejecutándose
4. Si todo va bien, verás un check verde ✅
5. Si algo falla, verás un check rojo ❌ y los logs del error

Si el workflow falla, haz clic en el job para ver qué paso falló.
Los logs muestran exactamente qué comando produjo el error.

## El error más común: no tener tests

Si tu workflow ejecuta `npm test` pero no tienes tests, el workflow
fallará. Tienes dos opciones:

1. **Escribe tests** (lo ideal)
2. **Cambia la línea** a `npm test || true` (ejecuta tests si existen,
   pero no falla si no hay ninguno)

La segunda opción es temporal. Lo correcto es tener tests.

<CasoPractico titulo="El workflow que falló y enseñó más que un tutorial">

  Un equipo configuró su primer workflow. Hicieron push y el workflow
  falló. El error: `npm test` fallaba porque un test tenía un
  `expect` mal escrito.

  Corrigieron el test, volvieron a hacer push, y el workflow pasó.
  La app se desplegó automáticamente.

  Al día siguiente, otro test falló. Esta vez era un bug real en el
  código. Lo detectaron en 2 minutos, antes de que llegara a
  producción.

  **Lección**: CI/CD no solo despliega. Detecta errores que de otra
  forma llegarían al tribunal.
</CasoPractico>

## Mini-chequeo

**Pregunta 1.** ¿Dónde se define un workflow de GitHub Actions?
A) En el package.json · B) En `.github/workflows/` como archivo YAML ·
C) En la configuración de GitHub

**Pregunta 2.** ¿Qué pasa si un step del workflow falla?
A) Se saltan los pasos siguientes y no se despliega · B) Se ejecutan
todos los pasos igualmente · C) Se reinicia el servidor

<details>
<summary>...Respuestas...</summary>

1. **B**. Los workflows se definen en archivos YAML dentro de
   `.github/workflows/`. Cada archivo es un workflow independiente.
2. **A**. Si un step falla, el workflow se detiene. Los pasos
   siguientes no se ejecutan y la app no se despliega.

</details>

## Resumen en 3 frases

1. GitHub Actions es el CI/CD de GitHub: un archivo YAML que ejecuta
   pasos automáticamente cada push.
2. Un workflow mínimo son 10 líneas: on (cuándo), jobs (qué), steps
   (cómo).
3. Los secrets guardan tokens y contraseñas fuera del código fuente.

> 🐛 **Vocabulario rápido**

| Término | Idea general |
|---|---|
| **Workflow** | Flujo de trabajo automatizado definido en YAML |
| **Step** | Un paso individual dentro de un job |
| **Job** | Conjunto de pasos que se ejecutan en la misma máquina |
| **Secret** | Variable encriptada que no se sube al repositorio |
| **Checkout** | Acción que clona el repositorio en la máquina virtual |
