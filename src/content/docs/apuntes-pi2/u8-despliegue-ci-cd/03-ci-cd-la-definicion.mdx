## La idea en una frase

> CI/CD significa que cada vez que subes código, los tests se ejecutan
> y la aplicación se despliega sola. Sin intervención manual.

## ¿Qué es CI/CD?

CI/CD son las siglas de **Integración Continua** y **Despliegue
Continuo** (o **Entrega Continua**). Son dos prácticas que van
juntas y que automatizan todo el proceso de pasar código del
desarrollador al usuario final.

### Integración Continua (CI)

Cada vez que un desarrollador sube código al repositorio, se ejecutan
automáticamente:

1. **Tests unitarios**: ¿el código nuevo rompe algo existente?
2. **Linting**: ¿el código sigue las normas de estilo?
3. **Build**: ¿el proyecto se compila sin errores?

Si algo falla, el desarrollador lo sabe en segundos, no en días.

### Despliegue Continuo (CD)

Si los tests pasan, la aplicación se despliega automáticamente a
producción. Sin que nadie tenga que hacer clic en un botón. Sin
que nadie tenga que ejecutar un script.

```
Código → Push a Git → Tests → Build → Deploy → Producción
          ↓
       (automático)
```

## CI vs CD: la diferencia

| Concepto | Qué hace | Cuándo se ejecuta |
|----------|---------|-------------------|
| **CI** (Integración Continua) | Ejecuta tests y verifica el código | Cada push a Git |
| **CD** (Despliegue Continuo) | Despliega la aplicación a producción | Solo si CI pasa |
| **CE** (Entrega Continua) | Prepara la aplicación para despliegue | Solo si CI pasa |

La diferencia entre CD y CE es sutil: en **Despliegue Continuo**,
la app se despliega automáticamente. En **Entrega Continua**, se
prepara pero alguien debe aprobar el despliegue.

Para un proyecto DAW, la diferencia no importa. Lo importante es
que los tests se ejecuten siempre y que el despliegue sea automático.

## Por qué CI/CD elimina el deploy manual

Sin CI/CD, el despliegue es un proceso manual con muchos puntos
de fallo:

```
Sin CI/CD:
1. Pull el código最新imo
2. Ejecutar tests manualmente (si te acuerdas)
3. Build el proyecto
4. Subir archivos al servidor
5. Reiniciar el servidor
6. Comprobar que funciona
7. Rezar

Con CI/CD:
1. git push
2. (todo lo demás ocurre solo)
```

Los problemas del deploy manual:

- **Olvidas un paso**: ¿ejecutaste los tests? ¿Subiste todos los archivos?
- **Errores humanos**: ejecutas el script en el servidor equivocado
- **Inconsistencia**: cada miembro del equipo despliega de forma diferente
- **No hay rollback**: si algo falla, ¿cómo vuelves a la versión anterior?

## Las ventajas concretas

### Sin deploy manual

Cada push a Git es un despliegue. No necesitas recordar pasos,
ejecutar scripts ni pedir permiso a nadie. Si el código pasa los
tests, se despliega.

### Tests siempre ejecutados

Si introduce un error, lo sabes en segundos. No en días. No en
la presentación ante el tribunal. Los tests son tu red de seguridad.

### El tribunal ve la última versión

Siempre que haces un push, la app se actualiza. No necesitas
desplegar manualmente antes de la presentación. La URL siempre
muestra la versión más reciente.

### Menos errores humanos

No olvidas un paso del despliegue. No ejecutas el script en el
servidor equivocado. No subes archivos incompletos. La
automatización elimina los errores de ejecución manual.

### Historial de cambios

Cada despliegue queda registrado en el historial de GitHub Actions.
Puedes ver cuándo se desplegó, qué versión, quién lo hizo y si
hubo errores.

## CI/CD no es complicado

Muchos estudiantes piensan que CI/CD es algo "de empresas grandes".
No es así. Un workflow básico son 10 líneas de YAML:

```yaml
name: Deploy
on:
  push:
    branches: [main]
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm install
      - run: npm test
      - run: npm run build
```

Esto es CI/CD. Cada push a `main` ejecuta tests y construye el
proyecto. Desplegar es solo una línea más.

<Aclaracion pregunta="¿Necesito ser experto para configurar CI/CD?">
  No. Necesitas saber qué es un workflow de GitHub Actions (lo
  veremos en el punto siguiente) y tener tests escritos. Si tu
  proyecto tiene tests, configurar CI/CD lleva 5 minutos.

  Si no tienes tests, CI/CD aún te sirve para automatizar el
  build y el despliegue. Los tests los puedes añadir después.
</Aclaracion>

## CI/CD en la vida real

En las empresas, CI/CD es estándar. Ningún equipo profesional
despliega manualmente. Los beneficios son tan claros que no tener
CI/CD se considera un riesgo:

- **Sin CI**: los bugs se detectan tarde, cuando ya están en producción
- **Sin CD**: el despliegue es lento, caro y propenso a errores
- **Con CI/CD**: el código se prueba y despliega en minutos, con
  cero intervención humana

En un proyecto DAW, CI/CD demuestra que entiendes las prácticas
actuales del desarrollo de software. No es solo comodidad es
profesionalidad.

  **Lección**: CI/CD no es solo para empresas. Es una práctica que

## Resumen en 3 frases

1. CI/CD significa Integración Continua (tests automáticos) y
   Despliegue Continuo (deploy automático).
2. Elimina el deploy manual, ejecuta tests siempre y reduce errores
   humanos.
3. Un workflow básico son 10 líneas de YAML que cualquier estudiante
   puede configurar.
