## La idea en una frase

> Una checklist no es burocracia. Es la diferencia entre "se nos olvidó
> algo" y "todo está comprobado".

## Checklist completa

### Plataforma de despliegue

- [ ] He elegido una plataforma de despliegue (Vercel, Render, Netlify, etc.)
- [ ] La plataforma tiene plan gratuito suficiente para mi proyecto
- [ ] El repositorio de GitHub está conectado a la plataforma
- [ ] La app se despliega automáticamente con cada push a `main`

### HTTPS y seguridad

- [ ] HTTPS está habilitado (la URL empieza por `https://`)
- [ ] El certificado SSL es válido (no hay advertencias en el navegador)
- [ ] No hay contenido mixto (recursos HTTP en página HTTPS)

### Variables de entorno

- [ ] Todas las variables de entorno están definidas en la plataforma
- [ ] Ninguna variable tiene valores hardcodeados en el código
- [ ] Las credenciales (API keys, contraseñas) no están en el repositorio
- [ ] Existe un `.env.example` que documenta las variables necesarias

### Build y dependencias

- [ ] El `package.json` tiene un script `build` correcto
- [ ] El script `test` ejecuta tests sin errores
- [ ] Las dependencias de producción están en `dependencies`
- [ ] El `package-lock.json` está en el repositorio
- [ ] `.gitignore` excluye `node_modules`, `.env`, `dist`

### CI/CD (GitHub Actions)

- [ ] Existe un workflow en `.github/workflows/`
- [ ] El workflow ejecuta `npm install`, `npm test` y `npm run build`
- [ ] El workflow se ejecuta cada push a `main`
- [ ] Si los tests fallan, la app no se despliega
- [ ] Los secrets están configurados (si se usan)

### App funcionando

- [ ] La URL de la app está en la memoria del proyecto
- [ ] He probado la app desplegada (no solo en local)
- [ ] He probado la app desde otro dispositivo (móvil, tablet)
- [ ] Los formularios funcionan correctamente
- [ ] La API responde (si hay backend)
- [ ] No hay errores en la consola del navegador

### Monitoreo

- [ ] UptimeRobot (o similar) está configurado y monitorizando la URL
- [ ] He recibido al menos una alerta de "app disponible"
- [ ] He revisado los logs recientes (no hay errores)

<details>
<summary>Checklist adicional para proyectos con backend</summary>

### Backend

- [ ] El backend arranca sin errores en producción
- [ ] Los endpoints de la API responden correctamente
- [ ] La base de datos se conecta con las variables de entorno
- [ ] Los errores devuelven mensajes claros (no 500 genéricos)
- [ ] La autenticación funciona (login, registro, sesiones)
- [ ] No hay datos sensibles en las respuestas de la API

### Base de datos

- [ ] La BD se crea automáticamente al arrancar (o hay script de migración)
- [ ] Los datos de prueba se cargan al iniciar
- [ ] He probado a reiniciar el servicio y los datos persisten
- [ ] Las conexiones a la BD están configuradas con variables de entorno

</details>

## Cómo usar esta checklist

### Durante el desarrollo

Cada vez que termines una funcionalidad, comprueba si afecta a algún
punto de la checklist. Si es así, marcalo ahora. Es más fácil corregir
sobre la marcha que al final.

### Una semana antes de la presentación

Recorre la checklist completa. Si algo falla, tienes tiempo de corregir.
Si todo está marcado, tu proyecto está listo.

### El día antes de la presentación

Repasa los puntos críticos:
- ¿La app está desplegada y accesible?
- ¿Funciona en otro dispositivo?
- ¿Las variables de entorno están configuradas?
- ¿UptimeRobot está monitorizando?
- ¿El README está actualizado?

<Aclaracion pregunta="¿Cuántos puntos debo cumplir para sacar buena nota?">
  Todos. La checklist no es opcional. Cada punto que no cumplas es algo
  que el tribunal puede detectar y preguntar. No necesitas ser perfecto,
  pero sí necesitas haber **pensado en cada aspecto**.

  Si algún punto te resulta difícil, no lo saltes. Pregunta al profesor
  o busca alternativas. La mayoría de los puntos son sencillos de
  implementar si piensas en ellos desde el principio.
</Aclaracion>

## Caso práctico

<CasoPractico titulo="La checklist que cambió la nota final">

  Un equipo de 4 personas desarrolló una aplicación de gestión de
  reservas con backend Node.js y MySQL. Una semana antes de la
  presentación, recorrieron esta checklist.

  **Resultado del checklist:**

  - 2 puntos de plataforma: **fallaban** (no habían conectado el
    repositorio a la plataforma)
  - 3 puntos de variables de entorno: **faltaban** (API key hardcodeada,
    sin `.env.example`)
  - 2 puntos de CI/CD: **faltaban** (sin workflow configurado)
  - 2 puntos de app funcionando: **fallaban** (error en Firefox que
    no habían visto)
  - 1 punto de monitoreo: **faltaba** (sin UptimeRobot)

  **Acciones correctivas (5 días):**

  1. Conectaron el repositorio a Render y configuraron el despliegue
  2. Movieron API key a variable de entorno, crearon `.env.example`
  3. Crearon un workflow básico de GitHub Actions
  4. Corrigieron el bug de Firefox
  5. Configuraron UptimeRobot en 2 minutos

  **Resultado en la presentación:** el tribunal comprobó que la app
  funcionaba en su navegador (Chrome y Firefox), vio la URL desplegada,
  preguntó por CI/CD y vio el workflow funcionando. Todo estaba
  preparado. La nota subió un punto entero.

  **Lección**: una checklist de 30 minutos puede ser la diferencia
  entre un 7 y un 9. No la dejes para el último día.
</CasoPractico>

## Mini-chequeo

**Pregunta 1.** ¿Cuándo debes usar la checklist?
A) Solo el día antes de la presentación · B) Durante todo el desarrollo,
repasándola periódicamente · C) Solo si el tribunal la pide

**Pregunta 2.** ¿Qué haces si un punto de la checklist te parece
difícil de implementar?
A) Lo saltas, no es importante · B) Preguntas al profesor o buscas
alternativas, pero no lo ignoras · C) Eliminas ese punto de la checklist

<details>
<summary>...Respuestas...</summary>

1. **B**. La checklist se usa durante todo el desarrollo. Si piensas
   en ella desde el principio, los puntos son fáciles de cumplir.
   Si la dejas para el final, todo es más difícil.
2. **B**. Cada punto existe por una razón. Si uno es difícil, no lo
   ignores: busca cómo resolverlo. Normalmente hay alternativas más
   sencillas de lo que parece.

</details>

## Resumen en 3 frases

1. La checklist cubre: plataforma, HTTPS, variables de entorno, build,
   CI/CD, app funcionando y monitoreo.
2. Recórrela durante el desarrollo, no solo al final. Es más fácil
   corregir sobre la marcha que rehacer todo.
3. Cada punto que falta es algo que el tribunal puede detectar.
   Una checklist completa te da confianza el día de la presentación.
