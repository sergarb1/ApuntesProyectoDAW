## La idea en una frase

> Un contenedor es como una caja que contiene tu aplicación y todo lo
> que necesita para funcionar. La caja funciona igual en cualquier sitio.

## Qué es un contenedor

Un contenedor es una forma de **empaquetar** tu aplicación con todo
lo que necesita: código, dependencias, configuración, runtime. Todo
envuelto en una unidad que se ejecuta igual en cualquier máquina.

Piensa en un contenedor como una **caja de mudanza**. Cuando te mudas,
no llevas las paredes de tu casa, ni el suelo, ni el techo. Llevas
tus muebles, tus cosas, tu configuración. El contenedor es igual:
lleva tu aplicación y sus dependencias, pero no el sistema operativo
completo (eso lo comparte con el anfitrión).

## Contenedor vs Máquina Virtual

| Característica | Contenedor | Máquina Virtual |
|---|---|---|
| **Peso** | Ligero (MB) | Pesado (GB) |
| **Arranque** | Segundos | Minutos |
| **Sistema operativo** | Comparte con el anfitrión | Tiene el suyo propio |
| **Rendimiento** | Casi nativo | Menor (capa extra) |
| **Aislamiento** | Procesos aislados | Máquina completa aislada |
| **Uso típico** | Desplegar aplicaciones | Ejecutar sistemas completos |

Para un proyecto DAW, los contenedores son la opción correcta. Las
máquinas virtuales son overkill.

## Imágenes y contenedores

Estos dos términos se usan mucho y es importante no confundirlos:

- **Imagen**: el **plano** de tu aplicación. Un archivo que describe
  qué sistema operativo usa, qué dependencias instala, qué comandos
  ejecuta. Es como un molde.

- **Contenedor**: una **instancia** de esa imagen. Es el molde con
  contenido real. Puedes crear mil contenedores de la misma imagen,
  cada uno con sus datos.

```
Imagen (plano)          Contenedores (instancias)
┌─────────────┐         ┌─────────────┐
│  Mi App     │   →     │  App copia 1│ (puerto 3000)
│  Node 20    │   →     │  App copia 2│ (puerto 3001)
│  npm install│   →     │  App copia 3│ (puerto 3002)
└─────────────┘         └─────────────┘
```

## Por qué Docker resuelve el problema

### Reproducibilidad

Si tu Dockerfile dice `FROM node:20`, siempre usará Node 20. Da igual
que tu máquina tenga Node 18 o 22. El contenedor usa exactamente lo
que le dices.

### Aislamiento

Tu aplicación no conflictúa con otras. Si otra app necesita Node 18,
no hay problema: cada contenedor tiene la suya.

### Portabilidad

El mismo contenedor funciona en Windows, macOS y Linux. En tu máquina,
en el servidor del profesor, en la nube. Sin cambios.

### Arranque rápido

Un contenedor arranca en segundos. No necesitas instalar nada en la
máquina destino. Solo Docker.

## ¿Necesitas Docker?

### Sí, si:

- Tu proyecto tiene **más de un servicio** (frontend + backend + BD)
- Quieres que funcione **igual en cualquier máquina**
- Quieres **desplegarlo en la nube** con facilidad
- El equipo tiene **diferentes sistemas operativos**
- El tribunal **probará la aplicación** en su máquina

### No, si:

- Es un proyecto pequeño que solo usas tú en tu máquina
- No tienes tiempo para aprender Docker (aunque merece la pena)
- Tu aplicación es un archivo HTML estático sin servidor

<Aclaracion pregunta="¿Docker es obligatorio para el proyecto DAW?">
  No es obligatorio, pero es muy recomendable. Si tu proyecto tiene
  backend con base de datos, Docker te ahorra problemas serios.

  Si no puedes usar Docker, al menos documenta todo el proceso de
  instalación en un README claro. Pero si tienes tiempo, aprende
  lo mínimo de Docker: te salvará el día de la presentación.
</Aclaracion>

## Los tres conceptos clave

### 1. Dockerfile

Un archivo de texto con instrucciones para construir tu imagen.
Define qué sistema operativo usar, qué instalar, qué copiar, qué
ejecutar. Es como una receta de cocina.

```dockerfile
FROM node:20
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
EXPOSE 3000
CMD ["node", "app.js"]
```

### 2. Imagen

El resultado de ejecutar el Dockerfile. Un paquete completo y
versionado de tu aplicación. Se almacena en un registro (Docker Hub,
GitHub Container Registry, etc.).

### 3. Contenedor

Una instancia de la imagen que se está ejecutando. Puedes crear,
detener, eliminar y gestionar contenedores con comandos de Docker.

## Comandos básicos de Docker

```bash
# Construir una imagen desde un Dockerfile
docker build -t mi-app .

# Ejecutar un contenedor
docker run -p 3000:3000 mi-app

# Listar contenedores en ejecución
docker ps

# Detener un contenedor
docker stop <id-o-nombre>

# Eliminar un contenedor
docker rm <id-o-nombre>
```

No necesitas memorizar todos. Lo importante es entender el concepto:
construyes una imagen, ejecutas un contenedor, y ese contenedor es
tu aplicación funcionando.

## Mini-chequeo

**Pregunta 1.** ¿Cuál es la diferencia entre una imagen y un contenedor?
A) No hay diferencia · B) La imagen es el plano, el contenedor es la
instancia ejecutándose · C) El contenedor es más grande que la imagen

**Pregunta 2.** ¿Por qué Docker es mejor que una máquina virtual para
un proyecto DAW?
A) Porque es más pesado · B) Porque es más ligero, arranca en segundos
y comparte el sistema operativo del anfitrión · C) Porque no necesita
Dockerfile

<details>
<summary>...Respuestas...</summary>

1. **B**. La imagen es el molde (un archivo con instrucciones). El
   contenedor es una instancia de ese molde ejecutándose. Puedes crear
   muchos contenedores de la misma imagen.
2. **B**. Los contenedores son más ligeros que las VMs, arrancan en
   segundos y comparten el kernel del sistema operativo anfitrión.
   Para un proyecto DAW son la opción correcta.

</details>

## Resumen en 3 frases

1. Un contenedor es una caja que contiene tu aplicación y todo lo que
   necesita, y funciona igual en cualquier máquina.
2. La imagen es el plano, el contenedor es la instancia ejecutándose.
   Docker resuelve el problema de "en mi máquina funciona".
3. Para un proyecto DAW, Docker es la herramienta ideal: ligero, rápido
   y portátil.
