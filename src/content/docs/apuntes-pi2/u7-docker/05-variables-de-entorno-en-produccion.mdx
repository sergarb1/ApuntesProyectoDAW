## La idea en una frase

> Todo lo que cambia entre entornos debe ser una variable de entorno.
> Nunca hardcodees credenciales, URLs ni configuración sensible.

## Qué son las variables de entorno

Son valores que se definen **fuera del código** y se leen en tiempo
de ejecución. El mismo código funciona en desarrollo, staging y
producción sin modificarse. Solo cambian las variables.

```javascript
// ❌ MAL: hardcodeado
const DB_URL = "mongodb://localhost:27017/mi_app";
const API_KEY = "sk-1234567890abcdef";
const PORT = 3000;

// ✅ BIEN: variables de entorno
const DB_URL = process.env.DB_URL || "mongodb://localhost:27017/mi_app";
const API_KEY = process.env.API_KEY;
const PORT = process.env.PORT || 3000;
```

## Las variables que necesitas

| Variable | Descripción | Ejemplo |
|----------|-------------|---------|
| `DB_HOST` | Host de la base de datos | `localhost` / `database` |
| `DB_PORT` | Puerto de la base de datos | `3306` / `5432` |
| `DB_NAME` | Nombre de la base de datos | `mi_app` |
| `DB_USER` | Usuario de la base de datos | `admin` |
| `DB_PASSWORD` | Contraseña de la base de datos | *(nunca en el código)* |
| `API_KEY` | Clave de servicios externos | *(nunca en el código)* |
| `NODE_ENV` | Entorno actual | `development` / `production` |
| `PORT` | Puerto del servidor | `3000` / `8080` |
| `JWT_SECRET` | Secreto para tokens JWT | *(nunca en el código)* |

## El archivo .env

La forma más común de gestionar variables de entorno en desarrollo es
el archivo `.env`:

```bash
# .env (desarrollo local)
DB_HOST=localhost
DB_PORT=3306
DB_NAME=mi_app_desarrollo
DB_USER=root
DB_PASSWORD=mipassword
API_KEY=sk-dev-1234567890
NODE_ENV=development
PORT=3000
```

### Reglas de oro con .env

1. **Nunca subas `.env` al repositorio**. Añádelo a `.gitignore`.
2. **Crea `.env.example`** con las variables sin valores reales.
3. **Documenta cada variable** en el README.
4. **Usa valores diferentes** para desarrollo y producción.

```gitignore
# .gitignore
.env
.env.*
!.env.example
```

```bash
# .env.example (subido al repositorio)
DB_HOST=          # Host de la base de datos
DB_PORT=          # Puerto de la base de datos
DB_NAME=          # Nombre de la base de datos
DB_USER=          # Usuario de la base de datos
DB_PASSWORD=      # Contraseña (nunca valores reales)
API_KEY=          # Clave de la API externa
NODE_ENV=         # development o production
PORT=             # Puerto del servidor
```

## Configuración por entorno

Diferentes entornos necesitan diferentes configuraciones. La forma
clásica de organizarlo:

```
config/
├── default.js        # Configuración común a todos los entornos
├── development.js    # Desarrollo: BD local, logs detallados
├── staging.js        # Staging: como producción pero de pruebas
└── production.js     # Producción: BD remota, logs mínimos
```

```javascript
// config/default.js
module.exports = {
  app: {
    name: "Mi Aplicación",
    version: "1.0.0",
  },
  logs: {
    level: "info",
  },
};

// config/development.js
module.exports = {
  db: {
    host: "localhost",
    port: 3306,
    name: "mi_app_dev",
  },
  logs: {
    level: "debug",
  },
};

// config/production.js
module.exports = {
  db: {
    host: process.env.DB_HOST,
    port: process.env.DB_PORT,
    name: process.env.DB_NAME,
  },
  logs: {
    level: "warn",
  },
};
```

## Gestión de secrets en producción

En producción, las credenciales no van en archivos `.env`. Cada
plataforma tiene su propio sistema:

| Plataforma | Cómo configurar secrets |
|-----------|------------------------|
| **Vercel** | Settings → Environment Variables |
| **Netlify** | Site settings → Environment variables |
| **Render** | Environment → Environment Variables |
| **Railway** | Variables tab |
| **GitHub Pages** | No aplica (estático, sin secrets) |
| **VPS** | Archivo `.env` en el servidor o sistema del SO |

## Errores comunes

### 1. Subir .env al repositorio

```bash
# Si ya lo subiste, la clave está comprometida
# Revócala inmediatamente y genera una nueva
```

### 2. Hardcodear valores por defecto peligrosos

```javascript
// ❌ MAL: valor por defecto es una credencial real
const DB_PASSWORD = process.env.DB_PASSWORD || "mi_password_secreto";

// ✅ BIEN: sin valor por defecto para secrets
const DB_PASSWORD = process.env.DB_PASSWORD;
if (!DB_PASSWORD) {
  throw new Error("DB_PASSWORD no está definida");
}
```

### 3. Usar las mismas variables en desarrollo y producción

```javascript
// ❌ MAL: misma variable, diferente entorno
const DB_URL = process.env.DB_URL;

// ✅ BIEN: configuración separada por entorno
const config = require(`./config/${process.env.NODE_ENV || 'development'}`);
```

### 4. Logear variables de entorno

```javascript
// ❌ MAL: el log expone secrets
console.log(process.env);

// ✅ BIEN: logear solo lo necesario
console.log(`App arrancada en puerto ${process.env.PORT}`);
```

<Aclaracion pregunta="¿Qué pasa si una variable de entorno no está definida?">
  Depende de cómo la uses. Si usas `process.env.VARIABLE` directamente,
  será `undefined`. Tu aplicación puede fallar de formas impredecibles.

  La buena práctica es **validar al arrancar**:

  ```javascript
  const required = ['DB_HOST', 'DB_NAME', 'DB_PASSWORD', 'API_KEY'];
  const missing = required.filter(v => !process.env[v]);
  if (missing.length > 0) {
    console.error(`Variables faltantes: ${missing.join(', ')}`);
    process.exit(1);
  }
  ```

  Si falta una variable crítica, la aplicación no arranca. Es mejor
  fallar rápido que funcionar con configuración incompleta.
</Aclaracion>

<CasoPractico titulo="El proyecto que configuró 3 entornos en un día">

  Un equipo tenía desarrollo local, un servidor de pruebas y producción.
  Al principio, copiaban y pegaban configuración entre entornos. Cada
  vez que cambiaban algo, tenían que recordar cambiarlo en los tres sitios.

  Organizaron la configuración así:

  1. `config/default.js` — valores comunes
  2. `config/development.js` — override para local
  3. `config/production.js` — override para producción
  4. `process.env.NODE_ENV` — selecciona qué configuración cargar

  ```javascript
  const env = process.env.NODE_ENV || 'development';
  const config = require(`./config/${env}`);
  ```

  Ahora, para cambiar de entorno, solo necesitan cambiar una variable.
  La configuración se adapta automáticamente.

  **Lección**: invertir una hora en organizar la configuración te ahorra
  días de bugs por entornos mal configurados.
</CasoPractico>

## Mini-chequeo

**Pregunta 1.** ¿Qué debe contener `.env.example`?
A) Los mismos valores que `.env` · B) Las variables sin valores reales,
  para que quien clone el repo sepa qué necesita configurar · C) Solo
  las variables sensibles

**Pregunta 2.** ¿Qué haces si encuentras una clave API hardcodeada en
el código que ya está en el repositorio?
A) La borro del código y hago un commit · B) La revoco inmediatamente,
  la borro del código, añado la nueva como variable de entorno y configuro
  `.gitignore` · C) No pasa nada si el repo es privado

<details>
<summary>...Respuestas...</summary>

1. **B**. `.env.example` documenta las variables necesarias sin exponer
   valores reales. Quien clone el repositorio lo copia a `.env` y rellena
   los valores.
2. **B**. Si una clave está en el historial de Git, está comprometida.
   Revócala, borra del código, usa variable de entorno y protege el
   repositorio.

</details>

## Resumen en 3 frases

1. Todo lo que cambia entre entornos debe ser una variable de entorno:
   credenciales, URLs, puertos, configuración.
2. Nunca subas `.env` al repositorio. Usa `.env.example` para
   documentar y `.gitignore` para proteger.
3. En producción, configura las variables en la plataforma de despliegue,
   no en archivos.

> 🐛 **Vocabulario rápido**

| Término | Idea general |
|---|---|
| **Variable de entorno** | Valor externo al código leído en tiempo de ejecución |
| **Secret** | Variable de entorno sensible (credenciales, claves API) |
| **.env** | Archivo con variables de entorno para desarrollo local |
| **.env.example** | Plantilla de variables sin valores reales |
| **Hardcodear** | Escribir valores fijos directamente en el código |
