## La idea en una frase

> No hay respuesta universal. La respuesta correcta es **la que mejor se
> adapte a tu proyecto concreto**, y puedes explicar por qué la elegiste.

## Las tres grandes decisiones de PI2

### 1. Framework frontend o HTML plano

Si tu interfaz es compleja con varios componentes reutilizables, un
framework (React, Vue, Svelte) te aporta organización, reutilización y
herramientas de desarrollo. Si son 3 pantallas sencillas con poca
interacción, HTML/CSS/JS plano puede ser suficiente y más simple.

| Criterio | HTML plano | Framework |
|----------|-----------|-----------|
| Complejidad de la UI | Baja (pocas pantallas) | Media-alta (muchos componentes) |
| Curva de aprendizaje | Mínima | Moderada |
| Reutilización de componentes | Manual | Nativa |
| Mantenibilidad a largo plazo | Difícil si crece | Escalable |
| Herramientas de desarrollo | Básicas | DevTools, HMR, testing |

**Criterio práctico**: si vas a tener más de 5 componentes distintos
que se repiten en varias pantallas, un framework te ahorra tiempo.
Si son páginas estáticas con poca interacción, no lo compliques.

### 2. API REST propia o servicio externo

Una API propia (Node/Express, Python/Flask, PHP) te da control total:
eliges la estructura, los datos, la lógica. Un servicio externo
(Firebase, Supabase, Airtable) te ahorra horas de backend pero te ata
a ese proveedor.

| Criterio | API propia | Servicio externo |
|----------|-----------|-----------------|
| Control total | Sí | Limitado |
| Tiempo de desarrollo | Largo | Corto |
| Curva de aprendizaje | Moderada | Baja |
| Coste | Solo tu tiempo | Posible coste mensual |
| Vendor lock-in | No | Sí |
| Aprendizaje DAW | Mucho | Poco |

**Criterio práctico**: para el proyecto DAW, una API propia te permite
demostrar competencias de desarrollo servidor. El servicio externo
es válido para prototipos rápidos, pero el tribunal valora que sepas
construir la API.

### 3. Base de datos relacional o NoSQL

Si tus datos tienen relaciones claras (usuarios con pedidos, alumnos
con notas), SQL es natural. Si son documentos flexibles sin estructura
fija (logs, contenido variable), NoSQL encaja mejor.

| Criterio | SQL (MySQL, PostgreSQL) | NoSQL (MongoDB) |
|----------|------------------------|-----------------|
| Relaciones entre datos | Naturales (JOINs) | Manuales o embebidas |
| Esquema | Rígido, definido antes | Flexible, evoluciona |
| Consistencia | ACID (garantizada) | Eventual |
| Escalabilidad | Vertical | Horizontal |
| Complejidad de queries | Media-alta | Baja (documentos) |

**Criterio práctico**: para un proyecto DAW con entidades relacionadas
(usuarios, productos, pedidos, etc.), SQL suele ser la opción correcta.
NoSQL es válido cuando la estructura de datos es verdaderamente flexible.

<Aclaracion pregunta="¿Y si no sé cuál elegir? ¿Puedo cambiar después?">
  Puedes cambiar, pero tiene un coste. Por eso es mejor decidir con
  criterio antes de empezar. Hazte estas preguntas:

  1. **¿Qué necesito realmente?** No lo que sería guay, sino lo mínimo
     que necesito para que funcione.
  2. **¿Cuánto tiempo tengo?** Un framework aprendido a medias es peor
     que HTML plano bien hecho.
  3. **¿Qué puede salir mal?** Evalúa los riesgos de cada opción.
  4. **¿Lo puedo explicar?** Si no sabes por qué elegiste algo, no lo
     elegiste: lo encontraste.

  Documenta tus decisiones (ver punto 06) para que el tribunal sepa
  que pensaste antes de codear.
</Aclaracion>

## Cómo documentar una decisión técnica

No basta con decidir. Hay que **explicar por qué**. Un formato sencillo:

```
DECISIÓN: Usar Vue.js como framework frontend
ALTERNATIVAS: React, HTML plano, Svelte
CRITERIOS: Curva de aprendizaje del equipo, documentación,
           ecosistema de componentes
JUSTIFICACIÓN: Todo el equipo conoce Vue de clase. La documentación
               es clara. Hay componentes UI gratuitos (PrimeVue).
CONSECUENCIAS: Dependencia de Vue. Si cambiamos, toca refactorizar
               toda la interfaz.
```

Esto es un ADR (Architecture Decision Record). En el punto 06 verás
cómo documentarlos formalmente.

<CasoPractico titulo="La decisión que marcó la diferencia">
  Un equipo tuvo que decidir entre React y Vue para PI2. Hicieron una
  prueba rápida:

  1. Crearon una pantalla sencilla en React (2 horas)
  2. Crearon la misma pantalla en Vue (1.5 horas)
  3. Preguntaron al equipo cuál les resultaba más intuitivo

  Eligen Vue porque:
  - Más rápido de implementar con su nivel de experiencia
  - Template syntax les resultaba más legible
  - Documentación oficial en español

  Documentaron la decisión con el formato ADR. El tribunal preguntó
  por qué Vue y no React. La respuesta fue clara, técnica y justificada.

  **Lección**: la mejor decisión es la que puedes explicar, no la que
  usa la tecnología más popular.
</CasoPractico>

## Mini-chequeo

**Pregunta 1.** Tu proyecto tiene 20 pantallas con muchos componentes
reutilizables. ¿Qué elegirías?
A) HTML plano, es más simple · B) Un framework como Vue o React ·
C) Lo que use mi compañero

**Pregunta 2.** ¿Por qué es importante documentar las decisiones técnicas?
A) Para que el tribunal vea que escribes · B) Para que el equipo entienda
las razones y pueda mantener o cambiar la decisión después · C) Porque
lo pide la rúbrica

<details>
<summary>...Respuestas...</summary>

1. **B**. Con 20 pantallas y componentes reutilizables, un framework
   te da organización y reutilización que HTML plano no puede ofrecer
   de forma mantenible.
2. **B**. Documentar no es burocracia: es para que cualquier persona
   del equipo (incluido tu yo del futuro) entienda por qué se tomó
   esa decisión.

</details>

## Resumen en 3 frases

1. Las tres grandes decisiones de PI2 son framework frontend, tipo de
   API y base de datos. No hay respuesta universal.
2. Decide con criterio: qué necesitas, cuánto tiempo tienes, qué puede
   salir mal, y si puedes explicar la decisión.
3. Documenta cada decisión técnica (ADR) para que el equipo y el tribunal
   entiendan el porqué.
