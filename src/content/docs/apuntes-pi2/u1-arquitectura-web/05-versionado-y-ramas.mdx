## La idea en una frase

> Las ramas de Git son como líneas de tiempo paralelas: cada una avanza
> por su lado, y cuando está lista se une a la principal. Así nadie
> bloquea a nadie.

## Por qué necesitas ramas

Sin ramas, todos trabajan en `main` al mismo tiempo. Si Ana modifica
un archivo mientras Marc modifica el mismo, hay un conflicto. Con ramas,
cada persona trabaja en su propia línea hasta que termina, y luego une
su trabajo de forma controlada.

```
SIN RAMAS (caos):
main ──●──●──●──●──●──●──●──●──●──  (conflictos, blocajes)
        Ana Marc Laura Sergio Ana Marc

CON RAMAS (orden):
main   ──●─────────────────────●──────  (solo lo que funciona)
           \                  /
rama Ana    ●──●──●──●──●──●─/
              \            /
rama Marc      ●──●──●──●─/
```

## Git Flow simplificado para DAW

No necesitas el Git Flow completo. Para un proyecto DAW, esta
estructura es suficiente:

### Ramas principales

- **`main`** — solo código que funciona y ha sido probado. Nunca se
  trabaja directamente aquí.
- **`develop`** — rama de integración donde se van juntando las
  funcionalidades. Opcional pero recomendable.

### Ramas de funcionalidad

Cada tarea nueva se crea en una rama con un nombre claro:

```
git checkout -b feature/nombre-descriptivo
```

Ejemplos:
- `feature/login-usuarios`
- `feature/api-productos`
- `feature/listado-pedidos`
- `fix/bug-validacion-email`
- `refactor/separar-servicios`

### Flujo típico

```
1. Crear rama desde main o develop
   git checkout -b feature/nueva-funcionalidad

2. Trabajar y commitear
   git add .
   git commit -m "feat: añadir endpoint GET /api/users"

3. Cuando termine, hacer pull request (o merge manual)
   git checkout develop
   git merge feature/nueva-funcionalidad

4. Borrar la rama ya mergeada
   git branch -d feature/nueva-funcionalidad
```

## Merge vs Rebase

Cuando tu rama está lista, tienes dos opciones para unirla a `main`:

### Merge

```
git checkout main
git merge feature/login
```

Crea un "commit de merge" que une las dos historias. Es seguro porque
no modifica el historial.

**Cuándo usarlo:** siempre que trabajes en equipo. No altera el historial
compartido.

### Rebase

```
git checkout feature/login
git rebase main
```

Reescribe los commits de tu rama sobre la base de `main`. El historial
queda lineal, sin "merges" intermedios.

**Cuándo usarlo:** solo en tu rama personal antes de mergear. **Nunca**
en ramas compartidas, porque reescribe el historial y puede causar
conflictos a los demás.

```
MERGE (historial con ramas):
main    ●─────●─────●─────●
             \           /
feature       ●──●──●──●

REBASE (historial lineal):
main    ●─────●─────●─────●─────●──●──●
feature               ↑ (commits movidos al final)
```

<Aclaracion pregunta="¿Y si surge un conflicto en el merge?">
  Un conflicto de Git no es un error. Es Git diciéndote: "este archivo
  fue modificado en dos sitios y no sé cuál es correcto". La solución:

  1. Abre el archivo conflicto (Git lo marca con `&lt;&lt;&lt;&lt;&lt;&lt;&lt;`, `=======`,
     `&gt;&gt;&gt;&gt;&gt;&gt;&gt;`)
  2. Elige qué versión es correcta (o combina ambas)
  3. Guarda el archivo
  4. `git add .` y `git commit`

  No da miedo una vez lo has hecho 2-3 veces. Y con ramas, los conflictos
  son más pequeños y fáciles de resolver.
</Aclaracion>

## Convenciones de nombres

| Tipo | Prefijo | Ejemplo |
|------|---------|---------|
| Nueva funcionalidad | `feature/` | `feature/listado-usuarios` |
| Corrección de bug | `fix/` | `fix/validacion-email` |
| Refactorización | `refactor/` | `refactor/separar-servicios` |
| Documentación | `docs/` | `docs/readme-actualizado` |
| Pruebas | `test/` | `test/endpoint-users` |

## Commits que se entienden

No es solo ramas: los commits también necesitan convención. Un buen
commit message explica **qué** se hizo y **por qué**:

```
feat: añadir endpoint GET /api/users con paginación
fix: corregir validación de email en registro
refactor: extraer lógica de BD a services/userService.js
docs: actualizar README con instrucciones de instalación
test: añadir tests para endpoint POST /api/users
```

**Regla de oro:** si tu commit message es "arreglo" o "cosas varias",
el commit probablemente demasiado grande o demasiado vago.

<CasoPractico titulo="El equipo que eliminó los conflictos">
  Un equipo de 4 personas tenía conflictos de Git constantes. Cada merge
  era una odisea. Decidieron implementar 3 reglas:

  1. **Nadie trabaja directamente en main** — todo pasa por ramas
  2. **Cada rama = una funcionalidad** — no meter cosas de más
  3. **Merge secuencial** — uno mergea, verifica que funciona, luego el
     siguiente

  En una semana pasaron de 3 conflictos diarios a 0. Y cuando aparecían
  (porque aparecían), eran pequeños y fáciles de resolver porque cada
  rama solo tocaba archivos de su responsabilidad.

  **Lección**: los conflictos de Git no son un problema técnico, son
  un problema de organización. Soluciona la organización y los
  conflictos desaparecen.
</CasoPractico>

## Mini-chequeo

**Pregunta 1.** ¿Cuándo se trabaja directamente en la rama `main`?
A) Siempre, es la rama principal · B) Solo para merge cuando la funcionalidad
está lista · C) Nunca, solo se usan ramas

**Pregunta 2.** ¿Qué es un "feature branch"?
A) Una rama que nunca se borra · B) Una rama temporal para desarrollar
una funcionalidad concreta · C) Una copia de seguridad del proyecto

<details>
<summary>...Respuestas...</summary>

1. **B**. Main es la rama del código que funciona. No se trabaja
   directamente: se crean ramas, se trabaja en ellas, y se mergea
   cuando están listas.
2. **B**. Una feature branch es una rama temporal que se crea para
   desarrollar una funcionalidad y se borra una vez mergeada.

</details>

## Resumen en 3 frases

1. Las ramas permiten que varias personas trabajen en paralelo sin
   pisarse: cada uno en su feature branch hasta que esté lista.
2. **Merge** es seguro para equipos; **rebase** es para ramas personales
   antes de mergear. Nunca rebase en ramas compartidas.
3. Los commits deben ser atómicos (un cambio = un commit) y con mensajes
   claros que expliquen qué se hizo.

> 🐛 **Vocabulario rápido**

| Término | Idea general |
|---|---|
| **Rama (branch)** | Línea de desarrollo paralela que permite experimentar sin afectar a main |
| **Merge** | Unir dos ramas en una, conservando el historial de ambas |
| **Rebase** | Reescribir commits de una rama sobre otra para obtener un historial lineal |
| **Conflicto** | Situación donde Git no sabe qué versión de un archivo es correcta |
| **Commit atómico** | Un commit que contiene un solo cambio lógico, reversible y entendible |
