## Sé el Proyecto

Ponte en la piel del proyecto de PI1 de tu equipo. El tribunal os pide
que conectéis el frontend con un servicio de email para enviar
confirmaciones. ¿Qué enfoque eliges?

- **Opción A — "El directo"**: "Escribo un script de Node que envía
  el email con nodemailer y listo. No necesito documentación para algo
  tan simple."
- **Opción B — "El metódico"**: "Defino el contrato (qué datos recibe
  el endpoint de envío), pruebo con Mailtrap, luego conecto SendGrid,
  documento todo en Swagger y añado variables de entorno."
- **Opción C — "El rápido"**: "Copio el ejemplo de la documentación
  de SendGrid, lo pego en el backend y lo pruebo. Si funciona, adelante."

<details>
<summary>...Respuestas...</summary>

**La opción B.** Es la única que equilibra velocidad y calidad. La A
no documenta nada: cuando el frontend necesite enviar emails, no sabrá
qué datos enviar. La C no maneja errores ni usa variables de entorno:
si SendGrid cambia algo, todo se rompe. La B define el contrato, prueba
con modo test, documenta y protege las claves.

</details>

## Laboratorio de Tortura

**Duración estimada: 30-40 minutos.** Objetivo: detectar el fallo de una
implementación que *parece* correcta... y no lo es.

**Contexto.** Un proyecto tiene esta implementación del endpoint de login:

```javascript
app.post('/api/login', async (req, res) => {
  const { email, password } = req.body;

  const usuario = await db.query(
    'SELECT * FROM usuarios WHERE email = ? AND password = ?',
    [email, password]
  );

  if (usuario) {
    const token = jwt.sign({ id: usuario.id }, 'secreto123');
    res.json({ token, usuario: { id: usuario.id, nombre: usuario.nombre } });
  } else {
    res.status(401).json({ error: 'Credenciales inválidas' });
  }
});
```

**Instrucciones.** Detecta **mínimo 5 problemas** de integración y
seguridad. Después, descubre el **fallo intencionado**.

<details>
<summary>Pista 1</summary>

Revisa el punto 04 (manejo de errores): ¿el formato del error es el
estándar `{ error, mensaje, codigo }`? ¿Qué pasa si la base de datos
se cae?

</details>

<details>
<summary>Pista 2</summary>

Revisa el punto 06 (seguridad): ¿la contraseña se compara en texto
plano? ¿El secreto de JWT está hardcodeado? ¿Qué pasa si no hay token
en el header?

</details>

<details>
<summary>Pista 3 (casi la respuesta)</summary>

El fallo intencionado es que **la contraseña se compara en texto plano**
(la query SQL compara `password = ?` sin hashing). El password del
usuario se guarda en la BD sin cifrar. Además, el secreto de JWT está
hardcodeado como `'secreto123'`, el error no tiene el formato estándar,
no hay try/catch, y no se verifica el header Authorization.

</details>

<details>
<summary>...Solución completa...</summary>

**Problemas detectados:**
1. Contraseña en texto plano (no usa bcrypt para comparar)
2. Secreto JWT hardcodeado (`'secreto123'` en vez de variable de entorno)
3. Error sin formato uniforme (falta `mensaje` y `codigo`)
4. Sin try/catch (si la BD falla, el servidor se cae)
5. No se verifica el header Authorization en la respuesta
6. La query SQL es vulnerable a inyección SQL si `email` no se valida

**Código corregido:**

```javascript
app.post('/api/login', async (req, res, next) => {
  try {
    const { email, password } = req.body;

    if (!email || !password) {
      return res.status(400).json({
        error: 'datos_invalidos',
        mensaje: 'Email y contraseña son obligatorios',
        codigo: 400
      });
    }

    const usuario = await db.query(
      'SELECT * FROM usuarios WHERE email = ?',
      [email]
    );

    if (!usuario || !(await bcrypt.compare(password, usuario.password))) {
      return res.status(401).json({
        error: 'credenciales_invalidas',
        mensaje: 'Email o contraseña incorrectos',
        codigo: 401
      });
    }

    const token = jwt.sign(
      { id: usuario.id, rol: usuario.rol },
      process.env.JWT_SECRET,
      { expiresIn: '24h' }
    );

    res.json({
      token,
      usuario: { id: usuario.id, nombre: usuario.nombre }
    });
  } catch (err) {
    next(err);
  }
});
```

El fallo intencionado era la contraseña en texto plano: la query compara
`password = ?` directamente. Debería buscar solo por email y luego usar
`bcrypt.compare()` para verificar la contraseña.

</details>

## Atrévete a Pensar

Preguntas abiertas. Piensa primero, mira la solución después.

1. ¿Qué haces si un servicio externo (SendGrid, Stripe) falla el día
   de la presentación?
2. ¿Cómo decides si una funcionalidad va en el frontend o en el backend?
3. ¿Cuándo es suficiente con una API y cuándo necesitas GraphQL o WebSockets?

<details>
<summary>...Sugerencias de respuesta...</summary>

1. Plan B: ten un modo offline que muestre un mensaje amigable. Para email,
   guarda el email en cola y envíalo cuando vuelva la conexión. Para pagos,
   muestra "Servicio temporalmente no disponible". Lo importante es que
   el usuario no vea un error técnico.
2. Regla práctica: si los datos necesitan procesamiento o seguridad,
   van en el backend. Si es presentación o interacción del usuario,
   va en el frontend. Ejemplo: validar un email es backend; mostrar un
   formulario es frontend.
3. REST es suficiente para el 95% de proyectos DAW. GraphQL cuando el
   frontend necesita datos de múltiples endpoints en una sola petición.
   WebSockets cuando necesitas comunicación en tiempo real (chat,
   notificaciones en vivo).

</details>

## Entrevista de trabajo

Te acaban de contratar como "full stack junior". Estas son las preguntas
que te harán en la entrevista:

1. **"¿Qué diferencia hay entre PUT y PATCH?"**
2. **"¿Por qué no expones las claves API en el frontend?"**
3. **"¿Cómo manejas los errores de una API en el frontend?"**

<details>
<summary>...Modelos de respuesta...</summary>

1. "PUT reemplaza el recurso completo con todos los campos. PATCH actualiza
   solo los campos que cambian. En la práctica, muchos proyectos usan PUT
   para ambos casos."
2. "Porque el frontend es visible para cualquiera. Si la clave está ahí,
   cualquiera puede copiarla y usarla. La clave debe vivir solo en el
   backend, en variables de entorno."
3. "Con una función genérica que encapsula fetch. Si la respuesta no es
   ok, lee el JSON del error y muestra el mensaje al usuario. Si hay
   error de red, muestra 'No hay conexión'. Todo centralizado, no caso
   por caso."

</details>

## Preguntas Tontas

> **Pregunta** — "¿Y si mi proyecto es tan pequeño que no necesita
> documentación ni OpenAPI?"
> **Respuesta** — Incluso un proyecto pequeño se beneficia de una tabla
> en el README con los endpoints. Si tu API tiene más de 3 endpoints,
> documentarla ahorra tiempo.

> **Pregunta** — "¿Qué pasa si el frontend necesita datos que la API
> no devuelve?"
> **Respuesta** — Añade un endpoint nuevo o modifica el existente.
> Pero documenta el cambio y comunica al equipo. Nunca modifiques la
> respuesta de un endpoint existente sin avisar.

> **Pregunta** — "¿JWT o sesiones para autenticación?"
> **Respuesta** — Para APIs, JWT es el estándar. Las sesiones son
   para aplicaciones tradicionales con servidor que renderiza HTML.
   Si tu frontend es un SPA (Single Page Application), usa JWT.
