## Checklist de integraciones

### Comunicación entre partes

- [ ] Frontend y backend hablan el mismo idioma (formato de datos)
- [ ] Los nombres de campos son consistentes (`nombre` en ambos lados)
- [ ] La estructura de respuestas es coherente (array vs objeto con paginación)
- [ ] El contrato está documentado (al menos los endpoints principales)
- [ ] Ambos equipos conocen el contrato y lo consultan

### Diseño de la API

- [ ] Las URLs usan recursos (sustantivos, no verbos): `/api/usuarios`
- [ ] Los métodos HTTP son correctos: GET, POST, PUT, DELETE
- [ ] Los códigos de estado son apropiados (200, 201, 400, 404, 500)
- [ ] La API sigue convenciones REST coherentes
- [ ] Existe versionado (`/api/v1/...`)

### Documentación y contratos

- [ ] La API está documentada en OpenAPI/Swagger
- [ ] Swagger UI está accesible para el equipo (y el tribunal)
- [ ] El contrato se actualiza cuando cambia la API
- [ ] Existe un `.env.example` con las variables necesarias
- [ ] Los endpoints están probados con Postman o Insomnia

### Manejo de errores

- [ ] Todos los errores devuelven `{ error, mensaje, codigo }`
- [ ] Los códigos HTTP son correctos (no 200 para todo)
- [ ] El frontend tiene una función genérica de manejo de errores
- [ ] Los errores de red están manejados (sin conexión, timeout)
- [ ] Los mensajes de error son claros para el usuario

### Servicios externos

- [ ] Los servicios externos están en modo test/sandbox
- [ ] Las claves API están en variables de entorno
- [ ] El `.env` está en `.gitignore`
- [ ] He probado la integración real (no solo el mock)
- [ ] Tengo un plan B si el servicio falla

### Seguridad

- [ ] CORS está configurado (solo permitir tu dominio en producción)
- [ ] Las rutas protegidas usan autenticación (JWT)
- [ ] Los tokens tienen fecha de expiración
- [ ] Las claves API no están expuestas en el frontend
- [ ] La comunicación usa HTTPS

### Herramientas

- [ ] Postman tiene una colección con las peticiones principales
- [ ] La colección se ha compartido con el equipo
- [ ] curl funciona para las peticiones básicas (backup)
- [ ] Swagger UI muestra la documentación actualizada

## Cuándo usar la checklist

| Momento | Puntos clave a revisar |
|---------|----------------------|
| **Inicio del proyecto** | Diseño de API, contrato, documentación |
| **Cada sprint** | Comunicación, errores, servicios externos |
| **Antes de merge** | CORS, autenticación, pruebas |
| **Antes de la entrega** | Documentación, Swagger UI, plan B |

## Mini-check de rapidez

Si necesitas una revisión rápida (2 minutos), estos son los 5 puntos
más críticos:

1. **¿El contrato está documentado?** — Swagger UI o tabla en README
2. **¿Los errores son uniformes?** — `{ error, mensaje, codigo }` siempre
3. **¿Las claves están en .env?** — nada de claves en el código
4. **¿CORS está configurado?** — solo tu dominio en producción
5. **¿Los servicios externos están en modo test?** — sandbox, no producción

Si respondes sí a las 5, estás en buen punto. Si alguna es no,
¿por qué no?

<Aclaracion pregunta="¿Tengo que cumplir TODOS los puntos antes de cada sprint?">
  No. La checklist es una guía, no una norma estricta. Algunos puntos
  son para el inicio del proyecto (diseño de API, documentación), otros
  son continuos (errores, servicios externos), y otros son para antes
  de la entrega (Swagger UI, plan B).

  La idea es consultarla periódicamente y preguntarte: "¿estoy olvidando
  algo importante?" Si la respuesta es no, estás en buen camino.
</Aclaracion>

## Caso práctico

<CasoPractico titulo="La checklist que salvó la presentación">
  El equipo de Pablo tenía la entrega del proyecto en 3 días. Estaban
  nerviosos y a punto de empezar a codear sin plan. El líder de equipo
  sacó la checklist y la repasaron juntos en 20 minutos.

  Resultados del repaso:
  - **Contrato**: no documentado. Crearon una tabla en el README en
    30 minutos.
  - **CORS**: no configurado. Lo añadieron en 10 minutos.
  - **Swagger UI**: no existía. Lo configuraron en 20 minutos.
  - **Variables de entorno**: una clave estaba hardcodeada. La movieron
    a `.env` en 5 minutos.
  - **Plan B para servicios**: no tenían ninguno. Añadieron un modo
    offline que mostraba un mensaje amigable.

  Con la checklist, perdieron 1 hora al inicio pero ganaron 2 días
  de productividad. La entrega fue tranquila y el tribunal pudo probar
  la API desde Swagger UI.

  **Lección**: 20 minutos de checklist ahorran días de caos.
</CasoPractico>

## Resumen en 3 frases

1. La checklist es tu **memoria externa**: un recurso para consultarte
   antes de cada sprint y no olvidar nada importante.
2. Revisa los puntos clave en los **momentos clave**: inicio de proyecto,
   cada sprint, antes de merge, antes de la entrega.
3. No necesitas cumplir todo a la vez: usa la checklist como **brújula**,
   no como camisa de fuerza.

> 🐛 **Vocabulario rápido**

| Término | Idea general |
|---|---|
| **Checklist** | Lista de puntos que deben verificarse antes de una acción |
| **Sprint** | Periodo de tiempo (1-2 semanas) en el que se trabaja en tareas concretas |
| **Merge** | Unir una rama de funcionalidad en la rama principal |
| **Sandbox** | Modo de prueba de un servicio externo sin efectos reales |
| **Plan B** | Alternativa para cuando un servicio externo falla |
