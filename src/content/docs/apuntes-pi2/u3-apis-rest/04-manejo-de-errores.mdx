## La idea en una frase

> Un error bien informado es casi una característica. Un error mal informado
> es un usuario perdido y un desarrollador envejecido.

## Por qué los errores importan tanto

Los errores van a ocurrir. La base de datos se caerá, el usuario enviará
datos inválidos, un servicio externo fallará. La pregunta no es "si"
ocurrirán, sino **qué haces cuando ocurran**.

### El error que nadie entiende

```javascript
// Esto es lo que ve el usuario:
Error: Cannot read property 'map' of undefined

// Esto es lo que ve el desarrollador en consola:
TypeError: Cannot read property 'map' of undefined
    at UsuariosList (Usuarios.jsx:23)
    at renderWithHooks (react-dom.development.js:14985)
    // ... 20 líneas más
```

El usuario no sabe qué hacer. El desarrollador tarda 10 minutos en
encontrar la causa. Todo porque no había un manejo de errores decente.

## Formato uniforme de errores en el backend

Tus errores deben tener **siempre** la misma estructura:

```javascript
// Formato estándar de error
{
  "error": "usuario_no_encontrado",
  "mensaje": "No existe un usuario con el ID 42",
  "codigo": 404
}
```

### Reglas del formato

| Campo | Tipo | Ejemplo | Propósito |
|-------|------|---------|-----------|
| `error` | string | `"datos_invalidos"` | Identificador del error (para programadores) |
| `mensaje` | string | `"El email es obligatorio"` | Mensaje legible (para usuarios) |
| `codigo` | number | `400` | Código HTTP (para el frontend) |

### Implementación en Express

```javascript
// Middleware de errores
function errorHandler(err, req, res, next) {
  const codigo = err.codigo || 500;
  const error = err.error || 'error_interno';
  const mensaje = err.mensaje || 'Ha ocurrido un error inesperado';

  res.status(codigo).json({ error, mensaje, codigo });
}

// Uso en rutas
app.get('/api/usuarios/:id', async (req, res, next) => {
  try {
    const usuario = await db.usuarios.findById(req.params.id);
    if (!usuario) {
      return next({
        error: 'usuario_no_encontrado',
        mensaje: `No existe un usuario con el ID ${req.params.id}`,
        codigo: 404
      });
    }
    res.json(usuario);
  } catch (err) {
    next(err);
  }
});
```

## Códigos HTTP: usar el correcto

| Situación | Código | Nombre |
|-----------|--------|--------|
| Datos del cliente incorrectos | 400 | Bad Request |
| No autenticado | 401 | Unauthorized |
| Autenticado pero sin permisos | 403 | Forbidden |
| Recurso no encontrado | 404 | Not Found |
| Email duplicado | 409 | Conflict |
| Datos correctos pero imposibles | 422 | Unprocessable |
| Error del servidor | 500 | Internal Error |

### Errores comunes en proyectos DAW

```javascript
// 400 — Datos inválidos
{
  "error": "datos_invalidos",
  "mensaje": "El email no tiene un formato válido",
  "codigo": 400
}

// 404 — No encontrado
{
  "error": "usuario_no_encontrado",
  "mensaje": "No existe un usuario con el ID 42",
  "codigo": 404
}

// 409 — Conflicto
{
  "error": "email_duplicado",
  "mensaje": "Ya existe un usuario con ese email",
  "codigo": 409
}

// 500 — Error del servidor
{
  "error": "error_base_datos",
  "mensaje": "No se pudo conectar con la base de datos",
  "codigo": 500
}
```

## Manejo de errores en el frontend

### fetchAPI genérico reutilizable

No manejes errores caso por caso. Crea una función que haga el trabajo
sucio por ti:

```javascript
async function fetchAPI(url, options = {}) {
  try {
    const res = await fetch(url, {
      ...options,
      headers: {
        'Content-Type': 'application/json',
        ...options.headers
      }
    });

    if (!res.ok) {
      const error = await res.json().catch(() => ({
        error: 'error_red',
        mensaje: 'No se pudo conectar con el servidor',
        codigo: res.status
      }));
      mostrarError(error.mensaje);
      return null;
    }

    if (res.status === 204) return null;
    return await res.json();
  } catch (err) {
    mostrarError('Error de conexión. Inténtalo de nuevo.');
    return null;
  }
}

// Uso
const usuarios = await fetchAPI('/api/usuarios');
if (usuarios) {
  renderizarUsuarios(usuarios);
}
```

### Mostrar errores al usuario

```javascript
function mostrarError(mensaje) {
  // Opción 1: toast/flotante
  const toast = document.createElement('div');
  toast.className = 'toast-error';
  toast.textContent = mensaje;
  document.body.appendChild(toast);
  setTimeout(() => toast.remove(), 5000);

  // Opción 2: mensaje en la interfaz
  // document.getElementById('error-container').textContent = mensaje;
}
```

<Aclaracion pregunta="¿Y si el backend no devuelve mi formato de error?">
  Si el backend es de otro equipo o de un servicio externo, puede que no
  cumpla tu formato. En ese caso, la función `fetchAPI` debe detectar
  ambos formatos:

  ```javascript
  const error = await res.json();
  const mensaje = error.mensaje || error.message || 'Error desconocido';
  mostrarError(mensaje);
  ```

  Adaptar es mejor que exigir cuando no controlas el backend.
</Aclaracion>

## Errores que debes manejar siempre

| Error | Cómo detectarlo | Qué mostrar al usuario |
|-------|-----------------|----------------------|
| Sin conexión | `fetch` lanza excepción | "No hay conexión a internet" |
| Timeout | `AbortController` | "La petición tardó demasiado" |
| Datos inválidos | 400 del backend | El mensaje del backend |
| No encontrado | 404 del backend | "El recurso no existe" |
| Sin permisos | 401/403 del backend | "No tienes acceso" |
| Error del servidor | 500 del backend | "Error interno. Inténtalo más tarde" |

## Caso práctico

<CasoPractico titulo="El error que el tribunal no vio">
  El equipo de Pablo tenía una aplicación de gestión de tareas. Un día
  antes de la presentación, el servidor de desarrollo se cayó. En vez
  de entrar en pánico, el frontend mostró: "El servicio no está disponible.
  Inténtalo de nuevo en unos minutos."

  El tribunal preguntó: "¿Y si esto pasa en producción?" Pablo respondió:
  "Tenemos monitoreo que nos avisa y el usuario ve un mensaje claro. Además,
  los datos se guardan localmente y se sincronizan cuando vuelve la conexión."

  El tribunal no vio ningún error en pantalla. Todo porque el equipo había
  implementado el manejo de errores desde el primer día.

  **Lección**: los errores van a pasar. Lo que marca la diferencia es
  cómo los manejas.
</CasoPractico>

## Resumen en 3 frases

1. Los errores deben tener un **formato uniforme**: `{ error, mensaje, codigo }`
   siempre, en todos los endpoints.
2. El frontend debe usar una **función genérica** (`fetchAPI`) que maneje
   errores de forma centralizada, no caso por caso.
3. Los **códigos HTTP** (400, 404, 500) le dicen al frontend qué tipo de
   error es y cómo mostrarlo al usuario.

> 🐛 **Vocabulario rápido**

| Término | Idea general |
|---|---|
| **Formato de error** | Estructura JSON que describe qué falló y por qué |
| **Código HTTP** | Número que indica el resultado de una petición |
| **fetchAPI** | Función reutilizable que encapsula fetch con manejo de errores |
| **Middleware** | Función que se ejecuta entre la petición y la respuesta |
| **Error predecible** | Error que sabes que puede ocurrir y has planificado |
