> 🗺️ **Estás en:** 🔁 **U9 · Gestionar el proyecto** → 08 · Checklist de gestión

Antes de entregar tu proyecto, usa esta checklist para asegurarte
de que no se te escapa nada. Marca cada punto cuando esté
comprobado.

## Retrospectiva y aprendizaje

- [ ] He hecho una retrospectiva con el equipo
- [ ] Identifiqué las 3 cosas que salieron bien
- [ ] Identifiqué las 3 cosas que salieron mal
- [ ] Definí 2-3 mejoras concretas para el próximo proyecto
- [ ] Las mejoras tienen responsable y plazo

## Organización del equipo

- [ ] Todos los miembros tuvieron un rol claro
- [ ] El trabajo se repartió según las fortalezas de cada uno
- [ ] Hubo reuniones regulares (al menos 1 por semana)
- [ ] Se usó un tablero Kanban o similar para gestionar tareas
- [ ] Los bloqueos se resolvieron rápido

## Estimación y planificación

- [ ] Se usaron story points o una escala de estimación
- [ ] La velocidad del equipo fue razonable (no todo acabado a última hora)
- [ ] Se priorizaron funcionalidades con MoSCoW o similar
- [ ] No se empezaron cosas nuevas en la última semana

## Toma de decisiones

- [ ] Las decisiones técnicas se documentaron
- [ ] Se usó el framework valor/esfuerzo para priorizar
- [ ] No se discutieron horas sobre decisiones triviales
- [ ] Las decisiones difíciles se tomaron a tiempo

## Comunicación

- [ ] El equipo se comunicó regularmente
- [ ] Los conflictos se resolvieron a tiempo
- [ ] Se dio y recibió retroalimentación constructiva
- [ ] Las decisiones se documentaron por escrito

## Proyecto completo

- [ ] La aplicación funciona de principio a fin
- [ ] No hay errores conocidos en funcionalidades core
- [ ] Los tests pasan
- [ ] El código es comprensible (no solo para los autores)
- [ ] No hay archivos sensibles en el repositorio

## Pruebas

- [ ] Probé la app en otro navegador
- [ ] Probé la app en otro ordenador (o en incógnito)
- [ ] Probé desde cero (clonar, instalar, ejecutar)
- [ ] Probé todas las funcionalidades, no solo las principales
- [ ] Los edge cases están cubiertos (inputs vacíos, límites, etc.)

## Documentación

- [ ] El README es completo y claro
- [ ] Las dependencias están documentadas
- [ ] Las variables de entorno están documentadas
- [ ] El proceso de despliegue está documentado
- [ ] La memoria (si la piden) está terminada

## Presentación

- [ ] La presentación tiene una estructura clara
- [ ] La demo está ensayada al menos 2 veces
- [ ] Hay datos de prueba en la app
- [ ] Hay un plan B si la demo falla
- [ ] Sé cuánto dura la presentación
- [ ] Tenéis respuestas a preguntas probables del tribunal

## Despliegue

- [ ] La app está desplegada en una plataforma accesible
- [ ] El despliegue funciona desde cero
- [ ] Las variables de entorno están configuradas
- [ ] No hay errores en consola del navegador
- [ ] El HTTPS funciona correctamente

## Entrega

- [ ] Todos los archivos están en el repositorio
- [ ] El repositorio está limpio (no hay ramas sueltas, no hay
  archivos innecesarios)
- [ ] La URL de despliegue está en el README
- [ ] He verificado que todo funciona el día antes de entregar

## El más importante

- [ ] Estoy orgulloso del trabajo hecho (aunque no sea perfecto)

<CasoPractico titulo="La checklist que salvó un punto">

  Un equipo tenía el proyecto perfecto: funcional, bonito, bien
  documentado. El día de la entrega, el profesor les pidió que
  clonaran el repositorio y lo ejecutaran en el portátil del
  instituto.

  Falló. El README decía `npm run dev` pero olvidaba que
  necesitaban Node.js 18+, no 16. El archivo `.env` no existía
  (estaba en `.gitignore`). No tenían un `.env.example`.

  **Resultado**: perdieron 1 punto por "entrega incompleta".

  Si hubieran seguido la checklist de cierre, lo habrían detectado.
  La checklist no es burocracia: es tu seguro de vida.
</CasoPractico>

<Aclaracion pregunta="¿Y si me doy cuenta de que falta algo el día de la entrega?">
  **No entres en pánico.** Evalúa: ¿es algo que puedes arreglar
  en 10 minutos? Hazlo. ¿Es algo que necesita más tiempo? Anótalo
  como "mejora pendiente" y entrega lo que tengas.

  El tribunal prefiere ver un proyecto funcional con una nota
  pendiente que un proyecto incompleto porque intentabas arreglar
  todo a última hora.
</Aclaracion>

## Resumen de lo que evalúa el tribunal

| Criterio | Peso aproximado | Cómo prepararlo |
|----------|----------------|-----------------|
| Funcionalidad | 30% | Que todo funcione, no que sea perfecto |
| Código | 20% | Limpio, documentado, con tests |
| Despliegue | 15% | App accesible desde internet |
| Presentación | 15% | Clara, ensayada, dentro del tiempo |
| Memoria | 10% | Completa y bien estructurada |
| Gestión | 10% | Retrospectiva, organización, comunicación |
