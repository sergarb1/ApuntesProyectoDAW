## Objetivos de la unidad

Al final de esta unidad serás capaz de:

1. **Diseñar una API REST** con endpoints claros, métodos correctos y códigos de estado apropiados.
2. **Definir contratos** entre frontend y backend antes de escribir código, usando OpenAPI/Swagger.
3. **Manejar errores** de forma uniforme en backend y frontend, con formatos predecibles.
4. **Integrar servicios externos** (email, pagos, mapas) de forma segura usando variables de entorno.
5. **Proteger la comunicación** con CORS, autenticación por tokens y HTTPS.
6. **Usar herramientas** como Postman, Insomnia y Swagger UI para probar y documentar APIs.

## ¿Por qué importa esta unidad?

En PI1, el frontend y el backend eran uno solo: JavaScript en el navegador
hablando con una base de datos directamente. En PI2, las cosas cambian:

- El frontend vive en el navegador (o en un framework como React/Vue).
- El backend vive en un servidor (Node, Python, Java).
- Entre ambos hay una **API**: un contrato que define qué se envía y qué se recibe.

Si el contrato está mal definido, el proyecto se convierte en un campo de
batalla. Esta unidad te enseña a evitarlo.

<Aclaracion pregunta="¿Esto es solo para proyectos con backend propio?">
  No. Aunque tu proyecto sea frontend-only (sin servidor propio), necesitas
  conectar con servicios externos: una API de clima, un servicio de email,
  un pasarela de pagos. Los mismos principios se aplican: define el contrato,
  maneja los errores, protege las claves.
</Aclaracion>

## Caso práctico de la unidad

<CasoPractico titulo="La app de reservas que salvó la presentación">
  Un equipo desarrolló una aplicación de reservas para restaurantes.
  Una de las funcionalidades que más peso tenía era el envío de emails
  de confirmación al hacer una reserva.

  Durante el desarrollo, probaban con Mailtrap (que intercepta los emails
  y no los envía de verdad). Todo funcionaba. Pero el día de la
  presentación decidieron conectar SendGrid en modo test. El tribunal
  recibió un email de confirmación en tiempo real.

  Ese detalle marcó la diferencia: demostraba que la integración era real,
  no simulada. La clave estuvo en que siguieron todos los pasos de esta
  unidad: definieron el contrato, probaron con herramientas, manejaron
  errores y usaron variables de entorno.
</CasoPractico>
