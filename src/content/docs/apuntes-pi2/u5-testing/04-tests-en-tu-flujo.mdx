## La idea en una frase

> Los tests no sirven si no se ejecutan. Integrarlos en tu flujo de
> trabajo es lo que los convierte en un seguro real.

## El flujo básico: test antes de commit

La regla es simple: **no hagas commit si los tests fallan**.

```
Escribir código → Ejecutar tests → ¿Pasan? → Commit
                      ↓
                   No → Arreglar → Ejecutar tests → Commit
```

### Cómo hacerlo en la práctica

1. Antes de `git add`, ejecuta la batería de tests
2. Si todos pasan, haz commit
3. Si alguno falla, arregla el error primero
4. No hagas commit con tests fallidos "porque ya lo arreglo después"

### Comandos útiles

```bash
# JavaScript (con npm)
npm test

# Java (con Maven)
mvn test

# Ver solo los tests que fallan
npm test -- --verbose
```

## El flujo del equipo: evitar roturas

Cuando trabajáis varios en el mismo repositorio, los tests evitan
que el código de uno rompa el de otro.

### Antes de mergear una rama

```
1. Hacer pull de la rama principal
2. Ejecutar todos los tests
3. Si pasan, mergear tu rama
4. Si no pasas, arreglar antes de mergear
```

### En GitHub Actions (CI)

La integración continua ejecuta los tests automáticamente cuando
alguien hace push. Si fallan, el merge se bloquea.

```yaml
# .github/workflows/test.yml
name: Tests
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm install
      - run: npm test
```

## Test-first: el enfoque TDD

TDD (Test-Driven Development) significa escribir el test **antes**
del código. El ciclo es:

1. **Rojo**: escribe un test que falle (el código aún no existe)
2. **Verde**: escribe el código mínimo para que pase el test
3. **Refactoriza**: mejora el código sin romper el test

### Ejemplo

```javascript
// 1. Rojo: el test falla porque la función no existe
test("sumar dos números", () => {
  expect(sumar(2, 3)).toBe(5);  // ERROR: sumar no está definida
});

// 2. Verde: implementas la función mínima
function sumar(a, b) {
  return a + b;
}

// 3. Refactorizas si es necesario (aquí no hace falta)
```

### Ventajas del TDD

- Cada función tiene al menos un test desde el primer momento
- El código crece respaldado por verificación continua
- Refactorizar es seguro: los tests te avisan si algo se rompe

### Desventajas del TDD

- Curva de aprendizaje pronunciada
- Requiere disciplina
- No siempre es práctico (interfaces visuales, prototipos rápidos)

## Ejecutar tests automáticamente

### Con husky (pre-commit hook)

Husky ejecuta un script automáticamente antes de cada commit:

```bash
# Instalar husky
npm install --save-dev husky

# Inicializar
npx husky init

# Configurar pre-commit
echo "npm test" > .husky/pre-commit
```

Ahora, cada vez que hagas `git commit`, Husky ejecutará `npm test`
automátamente. Si falla, el commit se bloquea.

### Con lint-staged

Si solo quieres testear los archivos que cambiaste:

```bash
npm install --save-dev lint-staged
```

```json
{
  "lint-staged": {
    "*.js": ["eslint --fix", "jest --bail"]
  }
}
```

<Aclaracion pregunta="¿Y si no sé configurar Husky o CI?">
  No es obligatorio. Lo mínimo que puedes hacer es ejecutar `npm test`
  manualmente antes de cada commit. No necesitas automatización para
  empezar.

  Si quieres ir más allá, busca "cómo configurar pre-commit hooks con
  Husky" en tu buscador favorito. Es un tutorial de 5 minutos.
</Aclaracion>

## Qué ejecutar y cuándo

| Acción | Comando | Cuándo |
|--------|---------|--------|
| Tests unitarios | `npm test` | Cada commit |
| Tests de integración | `npm run test:integration` | Antes de mergear |
| Tests E2E | `npm run test:e2e` | Antes de una entrega |
| Linting | `npm run lint` | Cada commit |
| Todo junto | `npm run test:all` | Antes de entregar |

## Caso práctico

<CasoPractico titulo="El equipo que dejó de pelearse">

  Un equipo de 3 personas tenía constantes conflictos por código roto.
  Cada vez que alguien hacía merge, algo dejaba de funcionar. Se
  dedicaban más tiempo a arreglar errores de otros que a avanzar.

  Decidieron implementar una regla: **ningún merge sin tests verdes**.
  Configuraron GitHub Actions para ejecutar los tests automáticamente
  en cada pull request.

  La primera semana, 4 pull requests fueron bloqueados por tests
  fallidos. Los autores los arreglaron antes de mergear. La segunda
  semana, solo 1. La tercera semana, ninguno.

  El equipo dejó de pelearse. Los tests habían eliminado la fuente
  de conflictos: código que rompe sin aviso.

  **Lección**: los tests automatizados no solo detectan errores.
  Eliminan la desconfianza entre compañeros.
</CasoPractico>

## Los 4 pasos para integrar tests en tu flujo

### Paso 1: Ejecutar tests manualmente

Empieza por aquí. Ejecuta `npm test` antes de cada commit. Es
incómodo al principio, pero crea el hábito.

### Paso 2: Añadir pre-commit hook

Con Husky o similar, automatiza la ejecución antes de cada commit.
Así no depende de tu memoria.

### Paso 3: Configurar CI

GitHub Actions ejecuta los tests en cada push. Si fallan, el equipo
lo sabe inmediatamente.

### Paso 4: Bloquear merges con tests fallidos

Configura el repositorio para que no permita mergear si los tests
no pasan. Es la última barrera de seguridad.

## Resumen en 3 frases

1. La regla básica es: ejecuta tests antes de commit, no subas código
   con tests fallidos.
2. Automatiza con pre-commit hooks (Husky) y CI (GitHub Actions)
   para que la ejecución no dependa de tu memoria.
3. Los tests no solo detectan errores: eliminan la desconfianza entre
   compañeros de equipo.
