## La idea en una frase

> La calidad no es responsabilidad de uno. Es responsabilidad de todos.
> Y los tests son el lenguaje compartido para mantenerla.

## Responsabilidad compartida

En un equipo, la calidad no puede recaer en una sola persona. Si
solo Ana ejecuta los tests, Ana es un cuello de botella. Si solo
Pedro escribe tests, Pedro es un punto único de fallo.

### Regla del equipo

**Todo el mundo escribe tests. Todo el mundo ejecuta tests. Todo
el mundo entiende los tests.**

Esto significa:
- Los tests forman parte de la Definition of Done
- Nadie merga sin tests verdes
- Si rompes un test de otro, lo arreglas tú
- Los tests se revisan como se revisa el código

## Code review con foco en testing

La revisión de código (code review) no es solo comprobar que el
código funciona. Es verificar que:

1. **Tiene tests** — ¿la funcionalidad nueva tiene tests asociados?
2. **Los tests son útiles** — ¿prueban algo real o solo cubren código?
3. **Los tests son claros** — ¿otro miembro del equipo entiende qué
   verifica cada test?
4. **No rompen existentes** — ¿al añadir nuevos tests, los anteriores
   siguen pasando?

### Qué buscar en una review de tests

| Aspecto | Qué comprobar |
|---------|---------------|
| **Cobertura** | ¿Están testeadas las partes críticas? |
| **Claridad** | ¿Los nombres de los tests explican qué prueban? |
| **Aislamiento** | ¿Un test puede fallar sin afectar a otros? |
| **Casos borde** | ¿Se prueban situaciones extremas? |
| **Mantenimiento** | ¿Los tests son fáciles de modificar? |

## Cultura de calidad en equipo

### Acuerdos del equipo

Establece reglas claras desde el principio:

- **No se merga sin tests verdes**: si los tests fallan, no hay merge
- **Cada PR tiene tests nuevos**: si añades funcionalidad, añade tests
- **Los tests fallidos se arreglan antes**: no se "arreglan después"
- **Los tests se revisan**: como el código, los tests pasan review

### Testing como documentación compartida

Los tests son documentación que el equipo puede leer. Si un nuevo
miembro quiere entender cómo funciona una funcionalidad, puede leer
los tests en vez de preguntar al autor.

```javascript
// Este test documenta el comportamiento esperado
test("al crear una reserva con fecha pasada, muestra error", async () => {
  const fechaPasada = new Date();
  fechaPasada.setDate(fechaPasada.getDate() - 1);

  const response = await crearReserva({
    sala: "Sala A",
    fecha: fechaPasada
  });

  expect(response.status).toBe(400);
  expect(response.body.error).toContain("fecha no puede ser pasada");
});
```

Un compañero nuevo que lea este test entenderá inmediatamente que
la validación de fecha existe y qué hace. No necesita buscar en el
código ni preguntar.

## Pair testing

El pair testing es cuando dos personas prueban la aplicación juntas.
No es lo mismo que pair programming (programar juntos), sino
**probar juntos**.

### Cómo funciona

1. **Conductor**: usa la aplicación (hace clic, escribe)
2. **Observador**: toma notas, busca problemas, sugiere cosas
3. Se intercambian roles cada 15 minutos

### Ventajas

- Dos personas ven más problemas que una
- El observador detecta cosas que el conductor no ve
- Crea conversación sobre calidad en el equipo
- Es más ligero que una review formal

<Aclaracion pregunta="¿Cuándo hacer pair testing?">
  - Antes de una entrega importante (presentación, examen)
  - Cuando una funcionalidad es crítica y compleja
  - Para capacitar a un nuevo miembro del equipo
  - Cuando un test falla y no sabes por qué

  No es necesario hacerlo siempre. Pero cuando lo haces, detecta
  problemas que Individual testing no ve.
</Aclaracion>

## Gestión de tests en el repositorio

### Estructura recomendada

```
src/
  components/
    Boton.tsx
  services/
    ReservaService.ts
  utils/
    validarEmail.ts
tests/
  unit/
    validarEmail.test.ts
    calcularTotal.test.ts
  integration/
    crearReserva.test.ts
  e2e/
    flujoReserva.cy.ts
```

### Nombres descriptivos

```javascript
// Mal: el test no explica qué verifica
test("test1", () => { ... });
test("funcionCorrecta", () => { ... });

// Bien: el test explica el comportamiento esperado
test("validarEmail acepta emails con formato correcto", () => { ... });
test("crear reserva con fecha pasada devuelve error 400", () => { ... });
```

## Caso práctico

<CasoPractico titulo="El equipo que compartió la responsabilidad">

  Un equipo de 4 personas tenía un acuerdo: **cada PR debía incluir
  tests**. No había excepciones. Si no había tests, el PR no se
  aprobaba.

  Al principio costó: los desarrolladores más rápidos se quejaban de
  que escribir tests les ralentizaba. Pero después de dos semanas,
  algo cambió.

  Cuando Ana hizo un cambio que rompió un test de Pedro, lo arregló
  antes de mergear. Cuando Pedro refactorizó el componente de Luis,
  los tests existentes le dijeron exactamente qué había roto. Cuando
  Laura se incorporó al equipo, leyó los tests para entender el
  proyecto en vez de preguntar a cada uno.

  La inversión inicial en testing se convirtió en un ahorro enorme
  en tiempo de debugging y discusiones.

  **Lección**: el testing en equipo no es un gasto de tiempo. Es
  una inversión en comunicación y estabilidad.
</CasoPractico>

## Mini-chequeo

**Pregunta 1.** ¿Quién debería escribir tests en un equipo?

A) Solo la persona más experimentada
B) Todo el que escriba código
C) Nadie, los tests son opcionales

**Pregunta 2.** ¿Qué es el pair testing?

A) Programar juntos en el mismo ordenador
B) Dos personas probando la aplicación juntas, una de conductor y otra de observador
C) Ejecutar todos los tests del equipo a la vez

<details>
<summary>...Respuestas...</summary>

1. **B**. La responsabilidad de testing es compartida. Todo el que
   escribe código también escribe tests para ese código.
2. **B**. El pair testing es cuando dos personas prueban juntas:
   una usa la aplicación y la otra observa y toma notas.

</details>

## Resumen en 3 frases

1. La calidad es responsabilidad de todo el equipo, no de una sola
   persona.
2. Los tests son documentación compartida: un nuevo miembro puede
   entender el proyecto leyendo los tests.
3. Establece acuerdos claros: no hay merge sin tests verdes, cada PR
   incluye tests, los tests se revisan como el código.
