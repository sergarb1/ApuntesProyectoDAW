## La idea en una frase

> No hace falta probarlo todo. Hace falta probar **lo que importa**.
> Y lo que importa es lo que más usa el usuario, lo que más rompe
> y lo que más cambia.

## Las tres reglas de priorización

### 1. Lo que más usa el usuario

Si el 80% de los usuarios hace el 20% de las funcionalidades, ese
20% merece el 80% de tus tests.

Pregúntate: **¿Cuáles son las 3 pantallas que todo usuario abre?**

En una app de reservas, probablemente sean:
- Buscar una sala disponible
- Crear una reserva
- Ver mis reservas

En una app de tareas:
- Crear una tarea
- Marcar tarea como hecha
- Ver lista de tareas pendientes

### 2. Lo que puede romperse más fácilmente

Algunas partes del código son más frágiles que otras:

- **Validaciones**: email inválido, fecha pasada, campos vacíos
- **Cálculos**: precios, descuentos, fechas
- **Condiciones borde**: lista vacía, usuario sin datos, conexión lenta
- **Integraciones**: llamadas a APIs externas, base de datos

Estas partes merecen tests específicos porque son las que más fallos
producen en producción.

### 3. Lo que más ha cambiado

Si acabas de refactorizar un módulo, esos cambios necesitan tests.
Si escribiste código nuevo, necesita tests. Si arreglaste un bug,
necesita un test que verifique que no vuelve a aparecer.

## Ejemplo práctico: qué testear en una app de reservas

| Funcionalidad | Uso | Fragilidad | Prioridad |
|---------------|-----|------------|-----------|
| Login | Alto | Baja | Media |
| Buscar sala | Alto | Media | **Alta** |
| Crear reserva | Alto | **Alta** | **Muy alta** |
| Cancelar reserva | Medio | **Alta** | **Alta** |
| Ver perfil | Bajo | Baja | Baja |
| Cambiar contraseña | Bajo | Media | Media |
| Ver historial | Bajo | Baja | Baja |

Los tests deberían enfocarse en **crear reserva** y **cancelar reserva**:
alto uso y alta fragilidad.

## El nivel mínimo para aprobar

Como mínimo, tu proyecto debería tener:

### Tests unitarios del core

Las funciones de lógica de negocio que son la esencia de tu aplicación:

- Validaciones de datos de entrada
- Cálculos (precios, fechas, puntuaciones)
- Transformaciones de datos
- Lógica de negocio principal

### Un test de integración del flujo principal

El camino que sigue el usuario para completar la tarea principal:

- Registro → login → acción principal
- Búsqueda → selección → confirmación
- Formulario → envío → respuesta

### Prueba manual completa antes de cada entrega

No sustituye a los tests automatizados, pero es la red de seguridad
final. Si no tienes tiempo para más, al menos haz esto.

<Aclaracion pregunta="¿Qué pasa si solo puedo testear una parte?">
  Testea **la parte más crítica**. Es mejor tener 5 tests en la
  funcionalidad principal que 50 tests en funcionalidades secundarias.

  Pregunta: "Si esta funcionalidad falla el día de la presentación,
  ¿el proyecto es un fracaso?". Si la respuesta es sí, testea esa
  funcionalidad primero.
</Aclaracion>

## Cómo decidir: el mapa de riesgo

Imagina una matriz con dos ejes: **probabilidad de fallo** y
**impacto si falla**.

```
Alto impacto  │  Monitorear   │  ¡TESTEAR AHORA!
              │  (baja prob.) │  (alta probabilidad)
──────────────┼───────────────┼──────────────────
Bajo impacto  │  Ignorar      │  Testear si hay
              │               │  tiempo
              └───────────────┴──────────────────
              Baja probabilidad  Alta probabilidad
```

Las funcionalidades en **"¡TESTEAR AHORA!"** son las que más riesgo
tienen: fallan a menudo y si fallan, el proyecto sufre.

## Caso práctico

<CasoPractico titulo="El test que no priorizó">

  Un equipo de 4 personas escribió tests para todo: login, perfil,
  configuración de idioma, cambio de contraseña, historial de
  actividad... 35 tests en total.

  Pero la funcionalidad核心 —crear un evento y compartirlo con
  invitados— no tenía ni un solo test. "Ya lo probaremos a mano",
  dijeron.

  En la entrega, el profesor intentó crear un evento. La app falló
  al calcular la fecha del evento cuando se cruzaba la frontera de
  medianoche. Un bug que un test unitario habría detectado en
  milisegundos.

  El equipo aprobó, pero perdió 2 puntos por la funcionalidad rota.
  Si hubieran priorizado, esos 35 tests menos críticos habrían sido
  10 tests críticos perfectos.

  **Lección**: testearlo todo sin priorizar es como proteger todas
  las puertas con candado menos la principal.
</CasoPractico>

## Estrategia de testing por fases

### Fase 1: Core (semanas 1-2)

Tests unitarios de las funciones de lógica de negocio.
Un test de integración del flujo principal.

### Fase 2: Estabilidad (semanas 3-4)

Tests de integración de las funcionalidades secundarias.
Tests de validación y casos borde.

### Fase 3: Robustez (semana 5)

Tests E2E de los flujos críticos.
Pruebas manuales en múltiples dispositivos.

### Fase 4: Entrega (semana 6)

Batería completa. Prueba manual exhaustiva.

## Mini-chequeo

**Pregunta 1.** ¿Cuáles son las tres reglas de priorización?

A) Lo que es más bonito, lo que es más grande, lo que tiene más código
B) Lo que más usa, lo que más rompe, lo que más cambia
C) Lo que menos cuesta, lo que es más rápido, lo que es más fácil

**Pregunta 2.** ¿Cuál es el nivel mínimo para aprobar?

A) Tests E2E de todas las funcionalidades
B) Cobertura del 100% del código
C) Tests unitarios del core, integración del flujo principal, manual

<details>
<summary>...Respuestas...</summary>

1. **B**. Las tres reglas de priorización son: lo que más usa el usuario,
   lo que puede romperse más fácilmente y lo que más ha cambiado.
2. **C**. El nivel mínimo incluye tests unitarios de la lógica core,
   un test de integración del flujo principal y una prueba manual
   completa antes de cada entrega.

</details>

## Resumen en 3 frases

1. No testees todo: prioriza por uso, fragilidad y cambio reciente.
2. El nivel mínimo son tests unitarios del core, integración del
   flujo principal y manual antes de entregar.
3. Usa el mapa de riesgo para decidir qué función merece más tests.
