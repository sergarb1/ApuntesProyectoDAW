## La idea en una frase

> Los tests son como las capas de una cebolla: cada una protege una
> parte distinta. Quita una y algo queda expuesto.

## La pirámide de tests

La pirámide de tests es una guía visual de cómo distribuir tus esfuerzos:

```
         /\
        / E2E \          ← pocos (costosos, lentos, frágiles)
       /--------\
      / Integración\     ← algunos (verifican la unión de partes)
     /--------------\
    /   Unitarios     \  ← muchos (rápidos, baratos, precisos)
   /____________________\
```

En la base, **muchos tests unitarios**. En el medio, **algunos de
integración**. En la cima, **pocos E2E**. Si inviertes la pirámide
(muchos E2E y pocos unitarios), tus tests serán lentos y frágiles.

## Test unitario

Un test unitario verifica **una función o método aislado**, sin
dependencias externas. Es la pieza más pequeña del testing.

### Qué prueba

- Una función de cálculo
- Una validación
- Una transformación de datos
- Una lógica condicional

### Ejemplo

```javascript
function esMayorDeEdad(edad) {
  return edad >= 18;
}

test("devuelve true para 18 o más", () => {
  expect(esMayorDeEdad(18)).toBe(true);
  expect(esMayorDeEdad(25)).toBe(true);
});

test("devuelve false para menos de 18", () => {
  expect(esMayorDeEdad(17)).toBe(false);
  expect(esMayorDeEdad(0)).toBe(false);
});
```

### Características

- **Velocidad**: milisegundos
- **Coste**: bajo
- **Fragilidad**: muy baja
- **Alcance**: una sola unidad de código

## Test de integración

Un test de integración verifica que **varias partes trabajan juntas**
correctamente. No prueba una función aislada, sino la unión de dos o
más componentes.

### Qué prueba

- Comunicación entre frontend y backend
- Integración con una base de datos
- Llamadas a una API externa
- Flujo de datos entre capas

### Ejemplo

```javascript
// Test de integración: crear un usuario en la API real
test("crear usuario devuelve 201 y guarda en BD", async () => {
  const response = await request(app)
    .post("/api/usuarios")
    .send({ nombre: "Ana", email: "ana@test.com" });

  expect(response.status).toBe(201);
  expect(response.body.nombre).toBe("Ana");

  // Verificar que se guardó en la base de datos
  const usuario = await db.obtenerPorEmail("ana@test.com");
  expect(usuario).not.toBeNull();
  expect(usuario.nombre).toBe("Ana");
});
```

### Características

- **Velocidad**: segundos
- **Coste**: medio
- **Fragilidad**: media
- **Alcance**: interacción entre componentes

## Test funcional (E2E)

Un test funcional o E2E (End-to-End) simula **un flujo completo del
usuario**, desde la interfaz hasta la base de datos. Es como un usuario
real usando la aplicación.

### Qué prueba

- Flujo completo: registro → login → acción principal
- Formularios completos con validación
- Navegación entre páginas
- Comportamiento en el navegador

### Ejemplo (con Cypress)

```javascript
// Test E2E: el usuario se registra y accede a su perfil
describe("Registro de usuario", () => {
  it("permite registrarse y ver el perfil", () => {
    cy.visit("/registro");
    cy.get('input[name="nombre"]').type("Ana García");
    cy.get('input[name="email"]').type("ana@test.com");
    cy.get('input[name="password"]').type("123456");
    cy.get('button[type="submit"]').click();

    // Verificar que redirige al perfil
    cy.url().should("include", "/perfil");
    cy.contains("Ana García").should("be.visible");
  });
});
```

### Características

- **Velocidad**: segundos a minutos
- **Coste**: alto
- **Fragilidad**: alta (cambios en la UI los rompen fácilmente)
- **Alcance**: flujo completo del usuario

## Test manual

El test manual es cuando **una persona prueba la aplicación** haciendo
clic, escribiendo y navegando. No es automatizado, pero es insustituible.

### Qué prueba

- Aspecto visual (¿se ve bien?)
- Experiencia de usuario (¿es fácil?)
- Casos borde que un test automatizado no contempla
- Compatibilidad con distintos dispositivos

### Cuándo usarlo

- **Siempre** antes de una entrega
- Cuando el aspecto visual importa
- Para descubrir problemas que los tests automatizados no ven
- Para validar la experiencia de usuario

### Limitaciones

- No es repetible (cada persona prueba diferente)
- Es lento (no puedes probar 100 escenarios manualmente)
- Dependiente de quién prueba (si no prueba algo, no se detecta)

<Aclaracion pregunta="¿El test manual es inferior al automatizado?">
  No. Son **complementarios**. Los tests automatizados cubren la
  funcionalidad correcta de manera consistente y repetible. Los tests
  manuales detectan problemas de experiencia, aspecto y casos que nadie
  programó para detectar.

  Un proyecto sin tests automatizados es arriesgado. Un proyecto sin
  pruebas manuales es ciego.
</Aclaracion>

## Tabla comparativa

| Tipo | Qué prueba | Velocidad | Coste | Fiabilidad | Cuándo usar |
|------|-----------|-----------|-------|------------|-------------|
| **Unitario** | Una función aislada | &lt;1ms | Bajo | Alta | Siempre, en gran cantidad |
| **Integración** | Varias partes juntas | Segundos | Medio | Media | Flujo principal, API, BD |
| **Funcional (E2E)** | Flujo completo | Minutos | Alto | Baja | Flujos críticos, pocas |
| **Manual** | Experiencia del usuario | Variable | Alto | Subjetiva | Siempre antes de entregar |

## La pirámide en la práctica

### Ejemplo: una app de reservas

**Unitarios (20 tests):**
- Validar fecha de reserva
- Calcular precio total
- Verificar disponibilidad de sala
- Generar código de confirmación

**Integración (5 tests):**
- Crear reserva → guardar en BD → devolver confirmación
- Login → obtener perfil → mostrar reservas
- Eliminar reserva → actualizar disponibilidad

**E2E (3 tests):**
- Flujo completo: login → buscar sala → reservar → confirmar
- Flujo de cancelación: login → ver reserva → cancelar
- Flujo de error: intentar reservar sala ocupada → mostrar error

**Manual:**
- Abrir en Chrome, Firefox, Safari
- Probar en móvil y tablet
- Verificar emails de confirmación
- Comprobar mensajes de error comprensibles

## Caso práctico

<CasoPractico titulo="La pirámide invertida que costó una semana">

  El equipo de EventApp invirtió la pirámide: 50 tests E2E y solo 3
  unitarios. Los E2E tardaban 15 minutos en ejecutarse. Cada cambio
  pequeño requería ejecutar toda la batería y esperar.

  Cuando el frontend se refactorizó para mejorar el diseño, 30 de los
  50 E2E fallaron. El equipo pasó **una semana** arreglando tests que
  fallaban por cambios en clases CSS, no por bugs reales.

  Reorganizaron la pirámide: 40 unitarios rápidos, 8 de integración
  y 5 E2E críticos. Ahora los tests completos tardan 30 segundos.
  Y cuando algo falla, saben exactamente qué está roto.

  **Lección**: la pirámide de tests no es una sugerencia. Es una
  estrategia para ahorrar tiempo y detectar errores reales.

</CasoPractico>

## Mini-chequeo

**Pregunta 1.** ¿Qué tipo de test es más rápido?

A) E2E · B) Integración · C) Unitario

**Pregunta 2.** ¿Cuántos tests E2E deberías tener comparado con unitarios?

A) Muchos más E2E que unitarios
B) Los mismos de cada tipo
C) Muchos más unitarios que E2E

<details>
<summary>...Respuestas...</summary>

1. **C**. Los tests unitarios son los más rápidos porque prueban una
   función aislada sin dependencias externas.
2. **C**. La pirámide de tests indica que deberías tener muchos
   unitarios (base), algunos de integración (medio) y pocos E2E (cima).

</details>

## Resumen en 3 frases

1. La pirámide de tests indica: muchos unitarios, algunos de integración
   y pocos E2E.
2. Cada tipo cumple una función distinta: unitario para lógica aislada,
   integración para unión de partes, E2E para flujos completos.
3. Los tests manuales son complementarios, no inferiores: detectan
   problemas que la automatización no ve.

> 🐛 **Vocabulario rápido**

| Término | Idea general |
|---|---|
| **Unitario** | Test de una función o método aislado |
| **Integración** | Test de varias partes trabajando juntas |
| **E2E (End-to-End)** | Test de flujo completo del usuario |
| **Manual** | Prueba realizada por una persona, no automatizada |
| **Pirámide de tests** | Guía de distribución: muchos unitarios, pocos E2E |
